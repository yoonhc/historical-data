현재 시각 하한과 완료 상한 사이에 72시간에 추가 보존 여유 1분까지 확보될 때만 정리를 검토한다.**

설계 보완 전 고정 후보는 `t05-clock-retirement-20261011-3618649f76cfd2f4`다.

기존 문서와 다음 후보의 정책이 다른 부분은 이 문서의 결정을 따른다.

## 1. 범위와 현재 상태

대상은 `/mnt/backup/marketdata-historical/automatic/` 아래 기존 관리 범위에 편입된
로컬 checkpoint 사본이다. 기존 정리기·검증·공통 잠금·계획/진행 기록을 재사용한다.
시장 원본, 운영 catalog, restic 저장소의 snapshot/pack, 편입 전 사본, 시험 폴더와 복구 키트는
이 정리의 삭제 대상이 아니다.

| 항목 | 보완 전 구현 | 보완 후보의 범위 |
|---|---|---|
| 현재 시각 검사 | 개별 보정량 100ms·오차 500ms·skew 100ppm, reference age 비차단 | 총 불확실성 U ≤ 5초로 개별 세 기준 대체 |
| 관측 시각 범위 | 조회 후 표본 중심, 관측 하한을 앞으로 이동시키지 않음 | 조회 전후 표본·여유 성분을 명시적으로 보존 |
| 기간 조건 | 보수적 72시간 | 기존 기간에 고정 보존 여유 60초 추가. 작은 시각 이동의 추가 정밀 모델은 보류 |
| 실제 삭제 직전 검사 | 주기적 재조회와 관측 만료·변경 검사 | 긴 무결성 검사 종료 후 최초 삭제 직전 강제 재조회 |
| 완료 상한 | 정리 평가에서 검증 사본을 사후 확인하고 첫 근거 재사용 | 새 백업의 완료 확정 직후 근거 연결 |
| 근거의 백업 | T05 별도 control state의 자동 백업은 미완료 | 완료·순서 근거를 restic에 보존하고 복원 조회 검증 |
| 최신 3개 | `checkpoint_at`·backup ID로 정렬 | 확인한 기존 집합과 이후 실제 생성 순서로 보호 판단 |
| 실행 환경 | 시스템 유닛 후보·관리자 접근 시험 완료 | 보완 후보의 전체 미리보기와 최종 설치 경로 확인 |
| 실제 정리 | 기존 사용자 유닛 masked, 시스템 운영 유닛 미설치 | 한 계획 수동 삭제와 반복 자동화는 각각 별도 승인 |

이번 보완에는 **백업 완료 후처리와 근거의 archive/restore 연결**이 포함된다.
따라서 예전 후보의 “백업 생성 코드는 변경하지 않음”이라는 범위를 그대로 적용하지 않는다.
변경된 백업 경로·정리기·근거 입출력 코드를 새 후보와 적용 목록에 함께 명시한다.
기존 backup 예약 업무의 system manager 이전까지 포함하는 것은 아니다.

두 실시간 수집기, 기존 8개 업무의 시작 정책, T13 예약·재시도, Chrony 시간원·poll·윤초 정책,
RTC, 부팅 보정 권한, restic 전체 검사 주기는 변경하지 않는다. `reference_stale`의 전역 제거,
과거 수신 시각 수정, 범용 시계 예측기, 과거 모든 사본의 순서 복원도 이번 범위에 넣지 않는다.

## 2. 정리 허용 조건

다음 조건을 **모두** 만족해야 한다.

1. 현재 관측이 유효하고 그 관측의 총 불확실성 U가 5초 이하이다.
2. 사본의 유효한 완료 상한이 있고, `현재 관측 하한 − 완료 상한 ≥ 72시간 + 1분`이다.
3. 해당 사본보다 확실히 뒤에 생성된, 같은 관리 범위의 서로 다른 검증 사본 3개 이상을
   최종 유지 목록에 남긴다. 순서가 불명확하면 추가 보호한다.
4. 기존 manifest·파일·source root·repository/scope·restic 저장/전체 검사·복구 근거가 맞는다.
5. 당일 checkpoint 생성용 maintenance daily와 **같은 backup ID**의 restic 저장·전체 검사가
   실제로 완료됐다. T13 자료 갱신 완료나 예약 시각 경과로 대신하지 않는다.
6. 필요한 공유/배타 잠금, 코드·설정·계획·승인 일치, 미완료 정리 없음 등의 기존 조건을 통과한다.

**5초는 자동 판단에 사용할 관측의 운영 상한이고, 72시간은 개별 사본의 기본 보호 기간이다.
여기에 고정 보존 여유 1분을 더한다.** 정책의 `retention_margin_seconds=60`을 계획·승인 해시에
포함하며 총 기간 기준은 259,260초다. 1분을 U에 더하거나 원래 완료 시각을 고쳐 기록하지 않는다.
5.1초가 물리적인 위험 경계라는 뜻은 아니다. 불확실성이 크면 자동 정리를 보류하는 초기 정책값이다.
정상 관측이라고 바로 삭제하지 않으며, 날짜상 오래됐다는 이유로 관측 조건을 생략하지 않는다.
추가 1분은 운영상 더 기다리는 여유이며, 검출하지 못한 모든 시각 이동을 보장하는 오차 상한은 아니다.

| 두 표시 시각의 차이 | 현재·완료 관측이 각각 ±2초일 때 최소 경과시간 | 기간 조건 |
|---|---|---|
| 72시간 3초 | 72시간 − 1초 | 보류 |
| 72시간 4초 | 72시간 | 보류: 추가 1분 미충족 |
| 72시간 1분 3초 | 72시간 59초 | 보류 |
| 72시간 1분 4초 | 72시간 1분 | 통과 가능 |
| 73시간 | 72시간 59분 56초 | 통과 가능 |

## 3. 시각 관측과 총 불확실성

### 3.1 계산과 기록

Chrony의 조건부 오차식은 다음과 같다. 기준 시간원이 올바르다는 등의 전제에 의존하며,
독립적으로 인증된 절대 UTC 오차를 뜻하지 않는다.
[Chrony 4.5 tracking 문서](https://chrony-project.org/doc/4.5/chronyc.html).

```text
E_chrony = |System time| + Root dispersion + Root delay / 2

E_used = |System time| + Root dispersion + max(0, Root delay) / 2
U = E_used + query_alignment_margin + sampling_margin

L_observed = W_after − U
H_observed = W_after + U
```

음수 Root delay가 불확실성을 줄이지 않도록 기존 후보의 보수적인 `max(0, ...)` 처리를 유지하고
원값은 남긴다. `W_after`는 **조회 응답을 받은 뒤 획득한 UTC 표본**이다.
기록의 `chrony_error_estimate`는 E_used이며, 원래 수치로 공식식의 E_chrony도 구분해 재계산할 수 있다.
나노초 정수 계산에서 불확실성은 위로 반올림하고, 하한·상한을 안쪽으로 반올림하지 않는다.

관측은 다음 순서로 만든다.

1. 조회 전 표본 S0를 얻고 부팅·Chrony invocation/PID·설정·bootstrap 연결을 확인한다.
2. 읽기 전용 tracking을 조회한다. 응답 파싱과 조회 후 동일 provider 확인까지 수행한다.
3. 조회 후 표본 S1을 얻고 전후 UTC/monotonic/boottime의 연속성을 검사한다.
4. S1의 UTC를 중심으로 E_used와 두 여유를 합산해 U·L_observed·H_observed를 확정한다.

`query_alignment_margin`은 S0부터 S1까지의 **전체 단조 시각 경과**를 사용한다.
이는 조회시간만큼 시계가 틀렸다는 판단이 아니라, 응답 계산 시점과 중심 표본의 시점 차이를
보수적으로 흡수하는 애플리케이션 여유다. `sampling_margin`은 S0·S1의 취득 폭 합계이며,
전체 경과와 일부 중첩되는 여유도 초기 구현에서는 차감하지 않는다.
이 여유는 Chrony 공식식과 분리한 운영 모델이며 모든 임의의 시각 변화에 대한 수학적 보장은 아니다.
이번에는 조회 중 작은 전진·후진을 별도로 추정하거나 U와 대조하는 추가 정밀 모델을 만들지 않는다.
기존 불연속 검사를 통과했다는 이유로 검출하지 못한 작은 이동까지 U에 포함됐다고 주장하지 않는다.
기존 검사와 위 모델을 유지하고 기간 조건에 1분을 더하는 단순한 운영 정책을 채택한다.

한 관측에는 아래 내용을 함께 저장한다.

| 기록 | 내용 |
|---|---|
| 원응답·수치 | tracking CSV, correction·root delay·dispersion·skew·stratum·leap·reference time |
| 시점 | 조회 전후 UTC·monotonic·boottime·표본 폭, 조회 시작/종료, 중심 표본 |
| 불확실성 | `chrony_error_estimate`, `query_alignment_margin`, `sampling_margin`, `total_uncertainty` |
| 구간 | 관측 당시 UTC 하한·상한, reference age 원값 |
| 신원 | boot ID, provider PID/invocation, 설정·profile·bootstrap 근거 해시 |
| 계약 | schema·정책 버전과 해시, 생성 코드 식별자, 판정·거부 사유 |

Chrony 4.5의 dispersion 증가에는 skew·잔여 주파수 오차·설정된 clock error가 반영된다.
별도 애플리케이션 skew 100ppm 차단은 제거하되 원값은 보존한다.
Chrony 자체의 `maxupdateskew` 등 설정은 건드리지 않는다.
[Chrony 4.5 구현](https://raw.githubusercontent.com/mlichvar/chrony/4.5/reference.c).

### 3.2 관측의 유효성

| 조건 | 보완 정책 |
|---|---|
| 총 불확실성 | U ≤ 5초 |
| 보정량 100ms·오차 500ms·skew 100ppm | T05의 독립 차단에서 제거하고 U 판단으로 대체 |
| reference age 600초 | 차단·품질 등급에 사용하지 않음. `reference_stale` 판정 없이 원값 보존 |
| 조회 전체 소요 | 최대 3초 |
| 관측 사용 수명 | 중심 표본 이후 최대 15초, 단조 시각으로 판단 |
| provider 재조회 / 표본 감시 | 약 10초 / 1초 |
| 표본 사이 공백 | 최대 5초 |
| 시각 불연속 | 기존 약 250ms 및 표본 폭을 반영한 검사 유지 |
| 단일 표본 취득 폭 | 기존 후보의 최대 50ms 유효성 검사 유지. UTC 오차 한도로 표현하지 않음 |

현재 외부 시간원에 동기화된 정상 응답, stratum 1–15, `Leap status=Normal`, 유효한 유한 수치,
검증된 현재 부팅 준비와 실제 시각 제어 중인 provider를 요구한다. 조회 실패·NaN/무한대·음수
dispersion/skew·provider 또는 설정 변경·부팅 불일치는 거부한다. 이전 응답을 현재 응답으로 대신하지 않는다.

reference time은 유효한 양수여야 하며 관측 UTC 상한을 초과하면 정합성 실패로 보류한다.
작은 음수 reference age만을 삭제한 100ms 한계로 계속 차단하지 않는다.
응답이 현재 불확실성 범위와 맞는지 판단하고 원래 값과 이유를 남긴다.

고정된 UTC 오차와 실행 중 점프는 별개다. U가 5초 이하여도 기존 검사에서 시각 불연속·역행·
suspend 정황을 검출하면 해당 정리 실행을 중단한다. U나 추가 보존 여유로 그 실패를 통과시키지 않는다.
250ms 미만이라는 이유만으로 모든 변화가 무해하거나 U 안에 있다고 해석하지 않는다.
1초 표본 감시가 표본 사이 모든 변화를 검출한다고 보장하지 않는다.
monotonic/boottime은 경과·공백 검사에 사용하며 독립적인 UTC 정확도 근거가 아니다.
[Linux timekeeping 문서](https://docs.kernel.org/core-api/timekeeping.html).

### 3.3 관측을 현재 시각으로 옮기지 않는다

**15초는 사용 기한이며 U가 15초 동안 일정하다는 보장이 아니다.**
13:00:00의 U를 13:00:14에 새로 읽은 wall clock에 붙이지 않는다.
최대 수명 안에서도 실제 관측 당시의 L_observed 자체로 이미 72시간 + 1분이 지났는지 판단한다.
표본 사이 경과 시간을 더해 삭제 가능 시각을 앞당기는 외삽은 구현하지 않는다.

긴 유지 사본 무결성 검사와 대상 inventory 확정이 끝난 뒤, **첫 rename/unlink 등 삭제 단계에
들어가기 직전에 새 관측을 강제로 확보**한다. 이후에도 감시·정기 재조회와 각 변경 직전 검사를 유지한다.
정상적인 재조회 때는 새 관측의 하한으로 전체 조건을 재평가한다. 만료된 근거만 남거나 이상이 발생하면
중단하며, 같은 실행의 실패를 조용히 지우고 자동 재개하지 않는다.

## 4. 실제 완료 직후의 근거

### 4.1 새 checkpoint

현재 [backup.py](../packages/marketdata/src/marketdata/backup.py)는 `completed_at`을 만든 뒤
최종 `backup.json`을 저장한다. 기존 필드 옆에 Chrony 값만 넣으면 완료 후 관측이 되지 않는다.
새 경로는 다음 순서를 지킨다.

```text
기존 파일·catalog 사본 생성과 검증
→ 기존 backup ID·manifest 생성
→ backup.json 원자적 저장 및 파일·디렉터리 내구성 확정
→ 완료된 동일 manifest 신원 확인
→ 새 시각 관측
→ C_upper = 관측 당시 H_observed
→ 별도 근거 파일 저장·fsync 및 부모 디렉터리 확정
→ 근거 결과를 포함해 백업 작업 결과 반환
→ 기존 예약 archiver가 같은 데이터와 근거를 보관
```

완료 전의 캐시 관측이나 수집기 시각 로그를 재사용하지 않는다. 데이터 쓰기·검증이 끝난 뒤
이미 필요한 완료 사실을 확인하고 즉시 관측하며, 시각 근거 때문에 전체 데이터 검사를 다시 실행하지 않는다.
근거에는 backup ID·**원본 manifest 바이트 해시**·source root/관리 범위·완료 확인 방식·관측·정책을 묶는다.

| 결과 | 백업 결과와 T05 처리 |
|---|---|
| 데이터 완료·유효한 시각 근거 저장 | 데이터 성공, 완료 직후 상한 사용 가능 |
| 데이터 완료·시각 조회/근거 기록 실패 | 데이터 성공은 유지, 미확보 사유 표시, 후속 사후 확인으로 보호 |
| 데이터 미완료 | 기존대로 완료 사본 불인정, 시각 근거만으로 성공 처리하지 않음 |

새 결과는 기존 데이터 백업의 `ok`와 `clock_evidence_state`를 구분한다.
근거 실패 때문에 유효한 백업을 삭제·재생성하거나 원래 완료 기록을 수정하지 않는다.
로그 쓰기까지 실패하면 근거 없음 자체가 미확인 상태이며 정상으로 간주하지 않는다.

### 4.2 기존 사본과 근거 없는 사본

동일 사본의 완료·신원·기존 검증 연결을 잠금 아래 확인한 **뒤** 새 유효 관측을 얻는다.
그 상한을 `posthoc` 근거로 최초 한 번 확정한다. 원래 `completed_at`의 정확도를 소급 인증하지 않는다.

10/11 14시에 처음 확인했다면 실제 완료는 그 관측 상한보다 늦을 수 없으므로,
해당 상한부터 최소 72시간 + 1분을 추가 보호한다. 매 평가 때 상한을 오늘 시각으로 바꾸지 않는다.
같은 backup ID·manifest·정책에 연결된 첫 유효 근거를 재사용하고, 재실행으로 보호 시작을 계속 미루지 않는다.
유실 시에는 복원한 유효 근거를 먼저 사용하고, 없으면 새로운 사후 근거로 더 보호한다.

새 사본도 완료 직후 근거를 얻지 못하면 같은 방식으로 처리한다. 오래된 근거가 현재와 다른
boot/provider에 속한다는 사실만으로 무효화하지는 않는다. 과거에 유효하게 확정된 완료 상한과,
현재 삭제 관측의 부팅·provider 유효성은 서로 다른 검사다.

## 5. 최신 3개 보호를 단순하게 이어가는 방법

**완료 상한은 보존 기간의 근거이고, 생성 순서는 실제 작업의 선후관계로 확인한다.**
두 완료 상한의 숫자 크기, 기존 `checkpoint_at`, 파일 mtime, restic 저장 순서만으로 순서를 확정하지 않는다.
현재 restic snapshot 시각도 `checkpoint_at`에서 지정하므로 독립적인 시각 근거가 아니다.

### 5.1 기존 집합 확인 → 이후 새 사본

1. 보완 적용 시 관리 대상인 완료 사본들의 ID·manifest 해시·관리 범위를 잠금 아래 확인하고
   불변 **기존 사본 목록**으로 남긴다. 그 사본들의 내부 순위를 복원하지 않는다.
2. 각 기존 사본의 최초 유효 사후 완료 상한을 연결한다. 작업 중인 미완료 사본은 완료 집합에 넣지 않는다.
3. 목록 확정 **이후 생성을 시작한** 새 checkpoint에 그 목록의 해시와 실제 생성 실행을 연결한다.
   목록 확정 전에 시작해 나중에 끝난 작업은 새 정책 이후 생성된 사본으로 자동 산입하지 않는다.
4. 이후 새 사본은 기존 유지보수 직렬 실행·잠금 아래, 생성 전에 확인한 선행 완료 사본과
   자기 실행·backup ID를 연결한다. 완료 시각 근거가 없어도 생성 선후관계와 데이터 완료 여부는 구분한다.
5. 기존 집합보다 후행임이 확인된 새 사본 3개가 완료·검증·restic 조건을 충족하고 최종 유지된다면,
   기존 사본들 사이의 순서를 몰라도 최신 3개 보호를 새 사본들로 이어갈 수 있다.

별도 분산 순번 서비스나 과거 전체 계보 복원기는 만들지 않는다. 기존 완료/실행 근거에
기준 목록 해시와 선행 ID를 붙이는 최소 기록으로 구현한다. `storage.reuse_backup_id`의
검증된 연결은 재사용할 수 있지만, 그 연결만이 유일한 순서 근거가 되도록 제한하지 않는다.
새 사본의 완료 후 뒤늦게 목록을 연결하여 “목록 이후 시작”을 만들어내지는 않는다.

```text
기존 완료 사본들 확인·목록 확정
        ↓ 그 뒤 생성 시작
새 N1 완료 → 새 N2 완료 → 새 N3 완료

N1·N2·N3 검증/보관·유지 + 기존 사본의 보수적 72시간 + 1분 경과
        ↓
기존 사본은 나머지 정리 조건을 만족하면 후보가 될 수 있음
```

기존 wall-clock 정렬이 골랐던 3개는 전환 초기에 보호하되 **영구 고정하지 않는다**.
명확히 후행인 새 3개가 확인되면 실제 새 사본으로 보호를 이어간다.
“최근 검증 사본 3개 유지” 정책은 계속 적용하며, 잘못된 옛 표시 시각 때문에 특정 3개를 영구 보존하지 않는다.

### 5.2 불명확한 경우

사본 X를 후보로 삼으려면 **X보다 후행임이 입증된 서로 다른 검증 사본 3개가 최종 유지 목록에 있어야 한다.**
같은 backup ID의 복제본·복원본·restic 재저장을 새 checkpoint로 세지 않는다.
단순히 “폴더가 3개 늘었다”는 사실도 충분하지 않다.

관계가 없는 독립/동시 생성, 실행 기록 누락, 뒤늦게 발견한 기존 사본은 추가 보호한다.
필요하면 해당 사본을 다음 새 백업 시작 전에 확인하여 이후 사본과의 선후관계를 확보할 수 있다.
유효한 연결 없이 “나중에 발견됐으니 더 최신”으로 처리하지 않는다.
ID·manifest 불일치나 관계 충돌·순환은 보류하며 추정으로 고치지 않는다.

새 3개가 갖춰지더라도 72시간 + 1분이 지나지 않았으면 보호하고, 기간 조건을 충족해도 새 3개의
근거가 없으면 보호한다. 복구할 근거가 없으면 자동 해제를 보장하지 않으며 사유를 보고한다.

## 6. 근거의 저장·restic 편입·복원

원래 manifest와 backup ID는 변경하지 않고 **별도의 버전 있는 불변 근거**를 보관한다.
새 checkpoint에는 `checkpoint-evidence.json`이라는 명시적 부속 파일을 두는 구성을 기준으로 한다.
완료 관측과 생성 순서를 독립 항목으로 기록하고, 한쪽 실패를 다른 쪽의 성공으로 덮지 않는다.
필수 참조인 기존 사본 목록·선행 근거도 묶어, 복원 후 운영 호스트의 현재 파일 없이 연결을 검증할 수 있게 한다.
**참조한 로컬 checkpoint가 삭제되고 원래 T05 control state도 보이지 않는 상태에서도**,
지정된 restic 지점에서 복원한 근거만으로 완료 상한과 생성 선후관계를 검증할 수 있어야 한다.
N3가 N2·N1을 참조할 때 삭제한 N2·N1 폴더를 다시 요구하지 않는다. 필요한 불변 목록·근거·
manifest 식별/연결 해시와 snapshot ID를 보존하며, 과거 checkpoint 전체를 계속 복제하는 구조는 만들지 않는다.

백업 완료 표시와 부속 파일 공개 사이에 archiver가 불완전한 조합을 저장하지 않도록 기존 잠금
순서를 지켜 공개 구간을 보호한다. 데이터 완료 후 후처리가 실패한 경우에는 미확보 결과 또는
중단 사실을 확인하고 데이터 백업을 계속 보관할 수 있다. 부속 파일 부재를 정상 근거로 해석하지 않는다.

근거 파일은 임시 기록→검증→원자적 공개→fsync로 확정하고, 재실행 시 기존 유효 파일을 대조한다.
동일 입력은 재사용하며 내용 충돌·부분 파일을 덮어쓰지 않는다. 최초 archive에 포함된 근거는
이후 변경하지 않는다. 나중에 얻은 사후 근거는 별도 불변 기록으로 보존해 후속 정기 지점에 편입한다.

| 연결 지점 | 구현 계약 |
|---|---|
| 백업 생성 | 데이터 완료 결과와 근거 결과를 분리하고 정확한 ID·manifest 해시로 연결 |
| 기존 파일 검증 | 원래 manifest의 데이터 목록 검증을 유지하고 새 부속 근거는 별도로 검증 |
| 정리 inventory | 알려진 부속 파일과 해시만 명시적으로 포함. 예상 외 파일 거부를 완화하지 않음 |
| restic 저장 | 새 사본의 데이터·근거를 같은 snapshot에 포함하고 근거 해시를 archive receipt에 연결 |
| 사후 근거 | 기존 snapshot을 수정하지 않고 다음 정기 지점에 편입. 추가 전체 백업을 매번 실행하지 않음 |
| 추출·프로그램 복원 | 명시적 snapshot ID에서 별도 경로로 복원하고 근거와 원본 backup ID 연결 유지 |
| 구버전 호환 | 실제 사용할 이전 백업/조회 도구의 동작을 시험. 모르는 근거를 삭제하거나 정확하다고 추정하지 않음 |

현재 구형 프로그램 복원은 manifest에 등록된 데이터만 복사하고, 정리기는 예상 외 파일을 거부한다.
따라서 **부속 파일 저장만 추가해서 완료로 보지 않는다**. 복원 receipt/보존 위치와 정리 inventory까지
함께 구현·검증한다. 복원한 저장소의 새로운 백업은 새 ID를 가지며 이전 완료 시각을 승계하지 않는다.

삭제에 사용할 완료·순서 근거도 검증된 restic 지점에서 복원 가능해야 한다.
기존 사본의 데이터 snapshot과 사후 근거의 후속 snapshot이 다르면 두 정확한 ID와 연결 해시를 기록한다.
근거가 로컬에만 있으면 그 상태를 표시하고 정리를 더 보류한다.
진행 중인 삭제 journal이나 반복 승인 권한까지 복원 시 자동 활성화하는 기능은 추가하지 않는다.
복원한 근거로 후보·보호 판단을 재구성하는 것과 실제 삭제 재개는 구분한다. 실행 상태나 승인이
확인되지 않으면 삭제는 보류한다.

독립 복원 시험은 근거 생성·restic 보관 후 정리 대상 로컬 사본을 제거하고, 원래 control state를
시험 도구가 볼 수 없게 분리한 상태에서 수행한다. 명시적 snapshot ID로 별도 경로에 복원한 뒤
backup ID·manifest 해시·완료 상한·후행 관계와 다음 정리 판단이 일치하는지 대조한다.

향후 restic 만료 정책은 이 연결을 입력으로 삼아, 아직 필요한 완료·순서 근거의 snapshot을
함께 보존하거나 검증 가능한 후속 지점으로 이전해야 한다. `forget`/`prune` 구현·실행은 이번
범위 밖이며 [TODO의 조건부 검토](../TODO.md)에 남긴다.

## 7. 계획·실제 적용·중단

계획에는 현재 관측과 정책 해시·고정 보존 여유 60초, 각 사본의 완료 근거·근거 snapshot, 생성 순서 근거,
최종 유지/후보 목록과 사유, 유지할 더 새로운 사본 3개, 코드·설정·승인 범위를 포함한다.
재실행 시 최신 근거로 새 계획을 만들며, 이전의 관측이나 승인 계획을 임의로 수정하지 않는다.

실제 적용 순서는 다음과 같다.

1. 미완료 정리·당일 backup/restic·권한·코드·설정·현재 부팅/provider를 대조한다.
2. 기존 잠금 순서로 사본·archive·근거를 보호하고 계획과 현재 파일/manifest를 대조한다.
3. 유지 사본 무결성과 모든 후보의 정확한 inventory를 확인한다. 이 동안 시각 감시도 이어간다.
4. 최초 삭제 단계 직전에 **새 관측**을 얻어 U·72시간 + 1분·유지 3개·나머지 조건을 다시 확인한다.
5. 각 rename/unlink/rmdir 직전에 관측 수명·연속성·대상·승인을 확인하고 기존 journal에 결과를 남긴다.
6. 삭제·보존 결과와 부분 실패 여부를 확인한다. 이미 지운 것을 코드 원복으로 되살렸다고 표시하지 않는다.

근거 부족·조회 만료·선행 작업 미완료·잠금 경합은 사유를 남겨 보류한다.
삭제 도중 시각 이상·기록 오류가 있으면 해당 실행을 중단하고 미완료 journal을 남긴다.
새 자동 실행이나 새 계획으로 실패를 우회하지 않는다. 원래 계획의 실제 진행 상태를 확인한 뒤
현재 조건과 별도 명시적 복구 승인으로만 남은 작업을 진행한다.

## 8. 시스템 서비스와 적용 단계

최종 정리 실행은 시스템 systemd가 관리하되 `User=yoonhc`로 수행한다.
기존 후보의 capability 없음·`ProtectClock`·파일시스템 보호·localhost 읽기 전용 조회·공통 잠금을 유지한다.
수집 계정의 Chrony 제어 권한을 확대하거나 보호 옵션을 낮춰 통과시키지 않는다.

| 단계 | 완료 근거 | 운영 경계 |
|---|---|---|
| 1. 보완 후보·격리 검증 | 아래 검증 통과, 새 소스/정책/환경 해시 고정 | 운영 삭제 없음. 기존 후보와 구분 |
| 2. 설치 전 운영 미리보기 | 기존 사본 신원·근거 부족·보호 사유 확인 | 운영은 읽기 전용, 시험 상태는 격리. 삭제 후보 0개도 정상일 수 있음 |
| 3. 근거 생성 기능 설치·등록 | 고정 실행본, 완료 후처리/archiver, 시스템 실행 환경·권한 확인. 기존 목록 확정·사후 근거 등록 | 별도 설치·등록 승인에 따른 운영 상태 쓰기. 자동 정리는 masked 유지 |
| 4. 근거 축적 후 새 미리보기 | 실제 후행 검증 사본 3개·보수적 72시간 + 1분·데이터와 근거의 restic 보존·전체 검사 확인 | 정기 백업으로 축적, 여전히 삭제 없음 |
| 5. 첫 수동 적용 | 정확한 한 계획 승인 후 실제 삭제·보존·journal 대조 | 변경된 코드/정책에 과거 grant를 재사용하지 않음 |
| 6. 반복 자동화 | 첫 실제 결과 검토와 새 반복 승인 | 별도 승인 후 시스템 timer 활성화 |

**근거 생성 기능의 설치 승인에 삭제 가능한 후보를 요구하지 않는다.** 설치 전에는 새 완료·순서
근거가 없으므로 보호되는 것이 정상일 수 있다. 설치 전 미리보기에서 만든 시험 상태를 운영에
복사해 확정하지 않으며, 기존 목록 확정과 최초 사후 근거 등록은 3단계의 승인된 쓰기로 수행한다.
설치 후 실제 조건이 갖춰지면 당일 maintenance daily와 같은 backup ID의 restic 저장·전체 검사까지
확인한 새 미리보기를 만든다. 선행 조건 미완료에 따른 보류와 근거 확인 후 후보 0개를 구분한다.

후행 사본 3개와 기간 조건은 기존 정기 백업으로 쌓는다. 조건을 앞당기려고 형식적인 백업을
연속 생성하거나 시스템 시각을 변경하지 않는다. 이 동안 수집·백업은 계속하고 정리만 보류한다.
기존 관리자 접근 시험은 재사용하되 근거 등록의 쓰기 경로와 최종 설치 접점의 확인을 대신하지 않는다.

15:40 KST 예약은 유지하되 `Persistent=false`, `Restart=no`로 보류 후 다음 날 평가한다.
13:10에 백업이 시작했어도 완료 시각을 가정하지 않는다. 데이터 갱신용 daily와 checkpoint용 daily를 구분한다.
기존 사용자 정리 service/timer는 계속 masked 상태를 유지해 중복 실행을 막는다.

원복은 자동 정리를 masked 상태로 둔 채 코드·설정을 되돌리는 절차다.
새 근거·원본 데이터·manifest·진행/실패 기록을 삭제하지 않는다. 구형 자동 정리를 다시 켜는 것을
원복의 기본 동작으로 삼지 않는다. 완료 근거 후처리를 되돌리면 이후 새 사본은 사후 확인으로 더 보호한다.

## 9. 필요한 검증과 종료 조건

이미 완료한 검사를 횟수만 늘려 반복하지 않고, 변경한 접점과 기존 안전 계약의 회귀를 확인한다.
최종 후보·실제 배포 버전 조합에서 실행한 결과만 새 후보의 근거로 삼는다.

| 검증 | 기대 결과 |
|---|---|
| U = 5초 / 5초 초과 | 경계대로 관측 적격·보류, 다른 조건 생략 없음 |
| 보정량·E·skew의 옛 개별 한계 초과 | 유효 관측·U 기준에 따라 판단, 옛 차단이 숨겨 남지 않음 |
| reference age 600초 초과 | 그것만으로 거부하지 않으며 원값 보존 |
| 현재 조회 실패·reference time이 관측 상한 초과·잘못된 수치 | 새 관측 거부, 오래된 값으로 대체하지 않음. 관측 상한 안의 작은 음수 age는 그 이유만으로 거부하지 않음 |
| 조회 중 provider 변경·기존 검사로 검출한 시각 불연속·관측 공백 | U나 보존 여유로 통과시키지 않고 중단. 작은 이동의 추가 정밀 모델은 이번 시험·구현 범위 밖 |
| 72시간 및 72시간 + 1분 경계, 양쪽 불확실성 | 기본 72시간만 충족하면 보류, 보수적 차이 ≥ 259,260초에서 기간 조건 통과. 안쪽 반올림 없음 |
| 14초 된 관측 + 새 wall clock | 옛 U로 새로운 하한을 만들지 않음 |
| 긴 유지 사본 검증 | 삭제 직전 강제 재조회 및 재평가 |
| 완료 표시 전/후 강제 종료 | 전자는 미완료, 후자는 유효 데이터와 누락 근거를 구분 |
| 근거 기록 실패·반복·중간 파일 | 데이터 백업 유지, 첫 유효 근거 재사용, 충돌/부분 파일 보류 |
| 기존 목록 확정 전에 시작한 작업 | 이후 새 사본 3개로 잘못 계산하지 않음 |
| 기존 표시 시각 역전·내부 순서 불명 | 이후 순차 생성한 새 3개와 보수적 72시간 + 1분으로 판단 가능 |
| 새 사본 2개 / 3개 | 2개는 보호, 검증된 유지 3개에서만 순서 조건 통과 가능 |
| 중복 ID·복원본·동시/독립 생성 | 개수 부풀리기 없음, 근거 없는 순서는 보호 |
| archive와 완료 후처리 경합 | 불완전 조합·나중에 변한 근거를 저장 성공으로 오인하지 않음 |
| 새 근거가 있는 실제 restic snapshot | 전체 읽기 검사·별도 복원 후 파일 해시/ID/완료 상한/순서 연결 일치 |
| 정리 대상 로컬 사본 제거·원래 control state 분리 후 복원 | 지정한 restic 지점의 근거로 완료 상한·후행 관계·다음 정리 판단 재구성. 승인·미완료 journal 자동 활성화 없음 |
| 설치 전 근거 부족 / 설치 후 축적 | 전자는 보호 사유 표시·운영 쓰기 없음, 후자는 승인된 등록 후 실제 조건에 따라 새 미리보기. 설치 승인에 삭제 후보 존재를 요구하지 않음 |
| 기존 backup/restore·정리 원복 조합 | 데이터 유지, 근거 손실이나 모르는 파일 자동 삭제 없음 |
| 최종 systemd 권한·중지·미완료 재개 | 보호 옵션 유지, 기록/잠금/실제 진행 상태와 승인 일치 |

제출물은 새 고정 후보 ID·파일별 해시, 정책 버전·해시, 검증 결과, 원래 후보와의 차이,
설치 전 미리보기, 정확한 근거 생성 기능 설치·등록/첫 수동 적용/원복 범위다.
실제 삭제 가능한 미리보기는 설치 승인 후 운영에서 근거가 쌓이고 조건이 충족된 뒤 별도로 제출한다.
완료 직후 근거 저장·restic/복원·최신 3개 전환까지 확인하기 전에는 보완 완료로 표시하지 않는다.
운영 설치·첫 수동 삭제·반복 자동화의 완료는 각각 실제 결과와 승인으로 따로 기록한다.
