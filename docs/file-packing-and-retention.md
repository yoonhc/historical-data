# 이벤트 파일 묶음 저장과 무기한 보관

원문과 표준 데이터는 **기간 제한 없이 보존**한다. 날짜가 오래됐다는 이유로 데이터나 수집
이력을 삭제하지 않는다. 이번 단계는 종료된 aggTrade·depth 수집에서 생긴 작은 파일들을
묶고, 묶음 안에서 바이트 일치가 검증된 개별 사본을 정리하는 기능이다.

## 저장 정책

| 대상 | 정책 |
|---|---|
| 원문·Parquet·수집 이력 | 무기한 보존. source ID, 파일 해시, 행, 수신 시각, 오류 기록 유지 |
| 실행 중인 수집 | 현재의 작은 파일 확정 방식 유지. 묶음 대상에서 제외 |
| 종료된 수집 | 기본 종료 후 1시간이 지난 자료를 데이터셋·UTC 날짜별로 묶음 |
| 묶음 크기 | 기본 원본 바이트 합계 최대 64 MiB 또는 1,024개 멤버 |
| 처리량 | 기본 실행당 최대 20,000개 후보 파일. 나머지는 다음 실행에서 처리 |
| 작은 마지막 묶음 | 파일 2개 이상이면 저장. 단독 파일은 그대로 유지 |
| 묶음보다 큰 단일 파일 | 건너뛰고 보고서에 기록 |
| 원래 개별 사본 | 별도 `pack-prune --apply`에서 검증된 중복 사본만 정리 |
| 캔들·OI 표준 자료와 연구 스냅샷 | 현재 저장 방식 유지 |
| 용량 부족 | 기본 10 GiB 여유 공간을 보존하고 묶음 생성을 거부. 데이터 자동 삭제 없음 |

각 묶음은 `data/packs/<prefix>/<sha256>.zip`의 불변 **ZIP_STORED** 파일이다. 이미 압축된
원문 gzip과 Parquet도 해당 파일의 바이트 그대로 멤버로 저장한다. ZIP의 멤버 이름은 원래의
상대 경로다. ZIP 전체 해시와 멤버별 해시·길이를 모두 검사한다.

`event_segments`와 `artifacts`의 기존 경로는 논리적 식별자로 유지한다. 카탈로그의
`file_packs`와 `packed_files`가 물리적인 묶음 위치를 가리킨다. 기존 검증 보고서의 세그먼트
ID와 스냅샷 manifest가 그대로 유효하며, 중복 제거·정렬 변경·수량 변환도 하지 않는다.

묶음은 파일 수와 inode 사용을 줄이기 위한 것이다. ZIP 헤더가 추가되므로 논리적인 데이터
바이트가 더 작아진다고 보장하지 않는다. 저장 용량은 데이터량에 따라 계속 증가한다.
무기한 보존에는 용량 확장·외부 백업 계획이 필요하며, 아직 외부 저장소나 자동 이전은 연결하지 않았다.

## 명령

먼저 계획을 확인한다. `--before`를 생략하면 현재 시각보다 1시간 이전에 종료한 수집을 고른다.
범위를 좁히려면 `--collection-id`를 반복 지정할 수 있다.

```bash
.venv/bin/marketdata pack-events --report reports/pack-plan.json

# 원문은 유지한 채 묶음을 만들고 검증한 다음 읽기 경로를 전환한다.
.venv/bin/marketdata pack-events --apply --report reports/pack-published.json
.venv/bin/marketdata pack-verify --report reports/pack-verification.json

# 실제 정리 전에 사라질 개별 사본과 이미 보존된 묶음 ID를 확인한다.
.venv/bin/marketdata pack-prune --report reports/pack-prune-plan.json
.venv/bin/marketdata pack-prune --apply --report reports/pack-pruned.json
.venv/bin/marketdata validate
```

`pack-prune --pack-id PACK_ID`로 정리할 묶음을 제한할 수도 있다. 기본 실행은 계획만 반환하며,
`--apply`가 있어야 개별 사본을 제거한다. 논리적 데이터·묶음·카탈로그 레코드는 삭제하지 않는다.
두 명령 모두 재실행 가능하다. 이미 묶인 논리 파일은 다시 묶지 않고, 이미 정리한 개별 사본도
다시 정리하지 않는다. 아직 검증하지 않은 고아 파일을 자동 삭제하는 기능은 없다.

형식·용량·잠금 문제는 종료 코드 1로 알린다. 조회나 백업이 파일 배치를 사용 중이면 변경은
안전하게 실패하며 이후 다시 실행한다. 부분적으로 완료한 묶음은 보존되고 다음 계획에서 제외된다.

## 조회와 호환성

`Store.raw()`, aggTrade 조회, depth 재생·원문 검사, `validate`는 개별 파일과 묶음을 함께 읽는다.
파일의 바이트가 직접 필요하면 `Store.file_bytes(relative_path)`를 사용한다. 묶인 논리 경로에
`Path.read_bytes()`나 `pyarrow.read_table(path)`를 직접 호출하면 개별 사본 정리 후에는 읽을 수 없다.
외부 소비자가 직접 경로를 사용하고 있다면 먼저 이 읽기 경로로 전환해야 한다.

현재 Freqtrade의 캔들·OI 출력은 이 이벤트 파일들을 직접 읽지 않는다. 기존 설정과 출력은
변경하지 않는다. 묶음에 들어간 Parquet은 일반 ZIP 도구로 바이트 그대로 꺼낼 수도 있다.

묶음 생성 후에는 등록된 묶음을 우선 읽는다. 묶음이 손상되면 남아 있는 개별 사본으로
조용히 우회하지 않고 오류로 보고한다. 정상적인 백업에서 복원하거나 손상 원인을 확인해야 한다.
멤버 읽기는 길이·CRC·SHA-256을, `pack-verify`·`validate`·백업 검증은 ZIP 전체 해시와
멤버 목록·카탈로그 대응도 검사한다.

## 중단과 동시 실행

1. 새 ZIP을 쓰고 fsync한 뒤 전체·멤버 해시를 검증한다. 이 단계에서 중단되면 기존 개별 파일은 남는다.
2. 짧은 writer 잠금과 배치 변경 잠금 안에서 카탈로그를 원자적으로 전환한다.
3. 별도 정리 단계는 묶음을 다시 검사하고, 해당 묶음의 모든 개별 사본을 대조한 뒤 제거한다.
   중간에 멈춰도 등록된 묶음으로 전체 자료를 읽을 수 있으며 재실행으로 남은 사본만 정리한다.

조회는 파일을 읽는 동안 공유 배치 잠금을 잡는다. 백업은 카탈로그 고정부터 전체 파일 복사가
끝날 때까지 배치를 고정한다. 묶음 등록·사본 정리는 이 잠금과 충돌하면 writer를 잡고 기다리지
않고 실패한다. 백업 복사 중에도 일반 수집 writer는 작업할 수 있다.

정리는 묶음 하나씩 수행하며, 해당 묶음 검증과 개별 사본 제거 동안에는 writer 잠금을 유지한다.
대상 멤버 수·크기를 제한하는 이유이기도 하다. 새 읽기 구현을 사용하는 프로세스 사이의 잠금이며,
이전 버전 소비자는 묶음 적용 전에 갱신·재시작해야 한다.

## 백업과 운영 범위

묶음이 있는 저장소의 새 백업은 **format_version=2**다. 논리 파일마다 개별 사본을 다시 만드는
대신 ZIP과 이를 참조하는 일관된 카탈로그를 복사한다. 전체 파일·멤버·참조를 검사한 후 완료
표시를 남기고, 복원본도 동일한 조회 명령으로 읽는다. 이전 format 1 백업의 검증·복원은 지원한다.
묶음 백업의 조회·복원에는 이 기능을 포함한 코드를 사용한다.

`marketdata storage`는 `data/packs`를 물리 저장량에 포함한다. 묶음 여러 개체가 파일 하나를
공유할 수 있어, 수집별 보고서는 논리 바이트와 물리 할당량을 구분한다. 이미 고정한 과거 기준
보고서의 당시 파일 수·할당량은 수정하지 않는다.

[후속 자동화](stream-services.md)에서 1시간 수집 세션, 매시간 묶음 저장과 일별 전체 검증·백업을
연결했다. 위 개별 명령도 계속 사용할 수 있다. `aggtrade-stream --seconds 0`처럼 닫히지 않는
수집은 묶음 대상이 되지 않는다. 원격 보관은 아직 연결하지 않았다.
