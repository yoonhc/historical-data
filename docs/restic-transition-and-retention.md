# restic 전환 전 복구 확인과 보관 정책

2026-10-03 정책 검토, **10/5 첫 수동 정리·후속 새 예약 백업·자동 정리 예약 활성화 반영**. 사용자가 선택한
**작업용 완료 사본 최근 3개 + 날짜별 장기 보관**을 아래 정책으로 구체화한다.
10/5에는 승인된 특정 계획의 작업용 사본 5개를 수동 정리했고, 19:38에는 별도 승인한
15:40 KST 자동 정리 타이머를 활성화했다. 첫 실제 예약은 10/6 15:40이며 예약 삭제는 아직 0건이다.
restic `forget`·`prune`, 기존 daily 대체는 적용하지 않았다. 기존 수집·daily·restic 예약은
계속 유지한다. [독립 복구 및 용량 근거](../reports/baseline/restic-transition-2026-10-03/summary.md)는
10/3 시점의 기록이며, 미래 실행 때 그대로 재사용할 삭제 목록이 아니다.
전환 후에도 daily는 검증된 checkpoint 생성기로 유지하고, 장기 복구 지점의 보관을 restic
정책으로 관리한다. daily의 카탈로그 사본 생성·전체 검증 비용까지 없애는 변경은 포함하지 않는다.

[정리기 구현·격리 시험·운영 미리보기](../reports/baseline/checkpoint-retention-2026-10-03/summary.md)까지
완료한 뒤, [10/4 새 daily·예약 restic 확인 및 최종 계획](../reports/baseline/checkpoint-retention-readiness-2026-10-05/summary.md)을
검토·승인해 [첫 수동 정리](../reports/baseline/checkpoint-retirement-apply-2026-10-05/summary.md)를 마쳤다.
수동 승인용 별도 정책 파일과 자동화용 최종 정책은 `apply_enabled=true`이며,
자동화의 별도 반복 승인 파일도 이번 사용자 승인에 따라 `enabled=true`로 기록했다.
[활성화·실행 환경 점검·새 예약만 중지하는 절차](../reports/baseline/checkpoint-automation-activation-2026-10-05/summary.md)에
고정 승인 범위와 첫 예약·정리 후 다음 백업 연결의 미완료 관찰을 남겼다.
정리 후 첫 새 daily는 10/5 13:58 완료했고, 같은 사본의 예약 restic 저장·전체 읽기 검사는
14:10 완료했다. [후속 확인](../reports/baseline/checkpoint-retirement-followup-2026-10-05/summary.md)에서
backup/snapshot ID·journal·실제 저장소를 연결했고 기존 restic 8개와 로컬 사본 6개 보존,
새 사본·snapshot 각각 1개 추가 및 14:35 재실행의 중복 없음까지 확인했다.
[10/4 후속 보강](../reports/baseline/checkpoint-retention-guards-2026-10-04/summary.md)은 계획의
코드 식별자·판정 시각·경과시간, 사본과 snapshot 연결, 적용 전후 공간 관측을 추가한다.

## 보존할 내용과 복구 날짜

| 대상 | 초기 정책 | 의미 |
|---|---|---|
| 원본 시장 데이터·등록된 모든 revision | 기간 제한 없이 보존 | 오래된 시장 데이터 자체를 지우지 않음 |
| 작업용 완료 checkpoint | 검증된 최근 3개 유지 | daily의 일관된 사본 생성과 최근 복원에 사용 |
| restic 복구 지점 | 최근 3개 + 일별 30개·주별 12개·월별 12개·연별 무제한 | 각 규칙의 합집합, 중복은 하나로 계산 |
| 전환 검증용 restic 지점 | 9/28·10/3의 명시적 ID를 초기 전환 동안 추가 보존 | 새 복구 증거를 검토한 후 별도로 해제 결정 |
| 편입 이전 사본·시험 자료·복구 키트 | 이번 자동 정리 범위에서 제외 | 별도 목록과 결정 없이는 정리하지 않음 |

초기 전환 동안 보호할 전체 restic ID는 다음 두 개다. 기존 snapshot에 태그를 추가해 ID를
바꾸지 않고, 향후 정리 후보 계산에서 명시적으로 제외한다.

- 9/28: `7ddea5243f9262eb058b15e97df1976eb5c369de386010c736b449a10a250713`
- 10/3: `d27a0a557e1795a4651132016491f1b2c6735e8181b71303f3adccd414f0f8ad`

연별 무제한은 **각 연도에서 가장 나중의 복구 지점 하나를 연도 수 제한 없이 남긴다**는 뜻이다.
매일의 복구 지점을 영원히 보관한다는 뜻은 아니다. 일별·주별·월별은 데이터가 있는 달력 구간을
세므로, 수집 중단으로 빈 날짜가 있으면 30개 일별 지점이 최근 30일보다 오래 걸칠 수 있다.
한 스냅샷이 여러 규칙을 만족할 수 있다. 주 경계는 월요일부터 일요일이며 UTC를 사용한다.
[restic 0.19.1의 기간·합집합·그룹 규칙](https://raw.githubusercontent.com/restic/restic/v0.19.1/doc/060_forget.rst)

최근 checkpoint도 그때 등록된 과거 원문·revision·연구 snapshot을 모두 포함한다.
따라서 옛 **백업 날짜**를 정리하는 것과 2019년 같은 옛 **시장 자료**를 삭제하는 것은 다른 작업이다.
다만 미등록 파일·파생 출력·코드·설정은 기존 [백업 계약](backup-and-storage.md)의 제외 대상이다.
데이터의 결측·격리·partial 판정은 복구 후에도 보존한다.

## 날짜와 그룹 선택

- 기준 시각은 검증된 `backup.json`의 `checkpoint_finished_at`이며, restic snapshot `time`과 일치해야 한다.
  처리 시작·완료 시각과 폴더 날짜를 보관 날짜로 사용하지 않는다. 자식 프로세스의 `TZ=UTC`를 고정한다.
- 현재 범위는 저장소 ID
  `b5a4434c95fcf4a9eb1339689cdea42c1da08bd34b845193dffce2aa8203e558`,
  `archive_scope=historical-data-original-v1`, 기존 `source_root`의 조합이다.
- `marketdata-archive-v1`과 위 scope 태그를 **모두** 만족하는 단일 범위를 먼저 선택한다.
  각 snapshot의 전체 ID·유일한 scope/backup/attempt 태그·절대 입력 경로·원래 manifest를 대조한다.
- 해당 단일 범위 안에서만 `group_by=""`를 사용한다. 날짜마다 달라지는 `paths`나 전체 `tags`로
  묶지 않는다. `--parent`는 보관 그룹을 대신하지 않는다. 범위 필터 없는 그룹 해제는 허용하지 않는다.
- Proxmox 이전 후 새 root에서 만든 백업은 새 전용 입력 폴더·새 scope로 분리한다. 옛 manifest와
  출처 검사를 바꾸지 않는다. 두 scope의 장기 보관 통합은 이 초기 정책에 포함하지 않는다.

위 옵션은 **후속 restic 보관 기능의 계약**이다. restic 보관 도구에는 snapshot 삭제 실행
경로가 없으며, 작업용 checkpoint 정리는 별도 도구에서 다룬다. `forget`·`prune`은 실행하지 않았다.
[실제 7개 snapshot의 메타데이터 대조](../reports/baseline/restic-transition-2026-10-03/snapshot-group-review.json)에서
기본 `host,paths` 그룹도 7개, 전체 태그 그룹도 7개로 갈리는 것을 확인했다.

## 작업용 사본의 정리 조건

실행할 때 다음 조건을 모두 새로 확인해야 한다. 하나라도 확인할 수 없으면 해당 실행은 정리하지 않는다.

1. 프로필의 마운트·파일시스템 UUID·restic 저장소 ID·scope·source root가 모두 일치한다.
   암호 사본으로 독립 복구가 성공했고 그 근거와 복구 지점이 보존돼 있어야 한다.
2. daily가 정상 주기로 완료되고(`daily_stale=false`, 현재 36시간 기준), 미보관 사본·검사 대기·
   **현재 미해결 오류**가 없어야 한다. 복구된 과거 실패 이력은 유지하며 정리를 영구 차단하지 않는다.
   마지막 전체 `check --read-data` 성공에는 보존할 최신 사본과 모든 정리
   후보의 restic ID가 포함돼야 한다. 그 검사 이후 저장소 오류가 발생했다면 정리를 중지한다.
3. 후보는 전용 `backup_dir` 내부의 정상 완료 사본으로 제한한다. 기존 프로그램의 manifest 해시·
   source root 검사, 입력 검증·저장 성공 기록과 restic 실제 snapshot 대조가 모두 일치해야 한다.
4. 정렬 기준은 checkpoint UTC 시각과 backup ID다. 최근의 검증된 완료 사본 3개를 보호하고,
   **완료 후 72시간 미만인 사본도 보호한다**. 수동 사본이 몰리는 경우 3개보다 많이 남을 수 있다.
5. 9/27 편입 이전 사본, 미완료 폴더, 출처 불명·중복 ID·미검증 사본, 심볼릭 링크·예상 외 파일은
   나이가 오래돼도 자동 삭제하지 않는다. 이상 항목은 보고하고 정상 사본으로 조용히 채택하지 않는다.
6. daily가 하드링크 재사용 중인 사본과 archiver·복원·검증 작업이 읽는 사본을 보호한다.
   아래 공통 잠금 규칙을 사용하며, 장시간 원본 수집의 writer/layout 잠금을 잡지 않는다.
   잠금에 참여하지 않는 직접 복사·조회 프로그램이 실행 중이면 운영자가 그 작업을 마친 후 적용한다.
   협력적 잠금으로 임의의 외부 프로그램 사용까지 자동 감지할 수 있다고 가정하지 않는다.
7. 미리보기의 경로·backup ID·manifest 해시·restic 전체 ID·정책 해시·코드 식별자를 기록하고,
   실제 적용 직전에 재대조한다. 중간에 상태가 바뀌면 새 목록을 만든다. 실패·중단 후 재개도
   완료/미완료를 구분해야 하며, 사본 폴더만 지운 뒤 정상 처리됐다고 추정해서는 안 된다.

첫 실제 정리는 위 조건을 구현·격리 시험한 다음 **구체적인 목록을 승인받아 수동으로** 진행했다.
추가 수동 정리도 당시 상태의 새 계획을 검토하며, 이번 승인을 다른 날짜·대상으로 확대하지 않는다.
원본 `data/`, live catalog, restic 저장소 파일, 시험 폴더는 이 정리기의 대상이 아니다.
여유 공간 부족도 보호 조건을 완화하거나 임의의 오래된 폴더를 지우는 사유로 사용하지 않는다.

## 작업용 정리 도구와 실행 계약

`scripts.retire_checkpoints`의 `plan`·`status`·`apply --plan-id FULL_64_HEX_ID`를 구현했다.
[정책 설정 예시](../configs/checkpoint-retention.example.toml)는 기존 archive 프로필을 참조하므로
이전할 때 호스트 경로·UUID·저장소 ID·암호 경로를 기존 방식대로 관리한다. 복구 결과 파일과
검토한 SHA-256을 지정하며, 암호 자체의 값·해시를 이 정책 파일에 넣지 않는다.
기본 `apply_enabled=false`에서는 실제 정리를 거부한다. 설정을 바꾸면 정책 해시가 바뀌므로
예전 계획을 재사용할 수 없고 새 미리보기를 만들어 검토해야 한다. 별도 자동 정리 타이머는
아래의 고정 배포본과 반복 승인 범위를 사용하며, 이 수동 명령의 과거 승인을 이어 쓰지 않는다.

```bash
.venv/bin/python -m scripts.retire_checkpoints --policy /path/to/checkpoint-retention.toml plan
.venv/bin/python -m scripts.retire_checkpoints --policy /path/to/checkpoint-retention.toml status
# 아래 apply는 최종 정책(apply_enabled=true)의 새 plan 전체 ID와 목록을 승인받은 후에만 실행한다.
.venv/bin/python -m scripts.retire_checkpoints --policy /path/to/checkpoint-retention.toml apply --plan-id FULL_64_HEX_ID
```

계획·진행 기록은 `state_root/<repository_id>/<archive_scope>/working-retention/`에 보존한다.
계획은 내용 해시로 고정하며 출처·정책·코드·대상 목록·manifest·restic ID·파일의 inode/크기/mtime을
적용 전에 재대조한다. 하드링크가 추가될 때 달라지는 nlink/ctime은 계획 유효성 기준에서 제외한다.
계획에 없는 파일·심볼릭 링크·특수 파일·다른 파일시스템이 있으면 중단한다.

계획 schema 2의 `code`에는 Git commit, 관련 소스와 의존성 선언의 파일별 SHA-256,
전체 소스 해시, 실행 경로·Python 버전과 이를 묶은 `code_id`를 기록한다. 수동 CLI의 계획 작성·적용은
각각 새 Python 프로세스로 실행한다. 계획 후 commit·소스·실행 환경이 바뀌면 새 계획이 필요하며,
같은 프로세스에서 import 후 소스가 바뀌어도 적용을 거부한다. 코드 식별자가 없는 schema 1
계획은 과거 증거 조회만 허용하고 적용하지 않는다. `assessed_at`은 공통 판정 시각(UTC),
`age_seconds`는 그 시각에서 완료 시각을 뺀 값이다. 유지 사본도 보호 사유와 snapshot ID를
명시하며, 유지·후보 모두 계획 당시의 backup/snapshot 연결이 달라지면 적용을 거부한다.
기록 파일 추가는 소스 해시를 바꾸지 않지만, 그 기록을 새 commit으로 만들면 commit이 바뀐다.
따라서 Git이 있는 수동 실행 경로는 최종 계획 전에 코드를 커밋하고 적용까지 고정한다.
별도 자동화 배포본은 실행마다 새 프로세스에서 plan·apply를 수행하고 그 사이에도 코드를 재검사한다.
Git 없는 배포본의 commit은 `null`로 기록하고 파일별 해시와 배포본 식별자로 고정한다.

적용은 대상별 원래 목록과 진행 기록을 먼저 fsync하고, 같은 SSD의
`backup_dir.parent/.<backup_dir.name>.retiring/<scope>/<plan_id>/<backup_id>`로 원자적 이동한다.
이후 기록된 파일만 제거한다. 중단되면 같은 계획 ID로 재개하며, 이미 옮긴 폴더를 다음 daily가
완료 사본으로 오인하지 않는다. 단계는 prepared → deleting → removing_root → complete이며,
원래 위치·이동 위치가 둘 다 있거나 설명 없이 없어지면 중단한다. 프로세스 강제 종료 후 재개 시
이미 사라진 파일 수와 이번 프로세스가 확인한 unlink 수는 구분한다. 예외·미완료 시도 기록은 남긴다.
원래 manifest/source_root·archiver 상태는 수정하지 않는다. 알려진 로컬 정리 이력과 restic
snapshot 유실은 별개이며, 설명 없는 snapshot 소실은 기존 archiver에서도 계속 오류다.

10/5에는 [15:40 KST 자동화 후보](../reports/baseline/checkpoint-automation-2026-10-05/summary.md)의
구현·관련 69개 격리 시험·운영 미리보기를 마쳤다. 운영 소스와 분리한 고정 배포본이며,
당일 daily와 같은 backup ID의 restic 저장·전체 검사 근거를 원래 정리 조건에 추가한다.
기존 수동 승인은 자동 삭제 권한으로 사용하지 않는다. 별도로 받은 반복 승인은
[고정 코드·정책·경로·scope](../reports/baseline/checkpoint-automation-2026-10-05/approval-review.md)에만
연결하며, 매 실행의 새 계획과 정확한 후보·보호 목록을 남긴다. 미완료 정리·잠금 경합·선행 작업
미완료는 보류하고 다음 날 재평가하며, 미완료 정리는 수동 점검이 필요하다.
이번 운영 미리보기는 후보 10/2 1개·보호 10/3~10/5 3개·편입 전 제외 3개, 삭제 0건이었다.
이후 사용자 승인에 따라 19:38에 타이머와 반복 권한을 활성화했다. 첫 예약의 실제 정리와
그 뒤 다음 daily/restic 연결은 [후속 관찰](../reports/baseline/checkpoint-automation-activation-2026-10-05/observation.json)로 남아 있다.

잠금 순서는 **maintenance → 저장소 archive → 사본 부모 디렉터리 → live layout → writer**다.
정리기는 앞의 세 잠금만 사용하고, 여러 사본 부모는 경로순으로 획득한다. `backup --reuse-from`,
`backup-verify`, `restore`, restic 보관과 시험 도구, `ArchiveReader`는 입력을 사용하는 동안
부모 디렉터리에 공유 flock을 유지한다. 정리기는 배타 flock을 비차단으로 요청해 사용 중이면
중단한다. 백업 내부에 잠금 파일을 만들지 않으므로 원래 manifest·읽기 전용 사본을 유지한다.
날짜별 부모 디렉터리와 이동 영역의 부모는 제거하지 않아 잠금 inode가 바뀌지 않는다.
같은 날짜의 여러 사본이 함께 잠기므로 날짜 하나의 복원 중에는 그 날짜의 정리도 보류된다.

특정 계획을 수동 승인하여 운영에 적용하는 절차는 다음과 같다. 자동화 후보의 반복 승인·실행
계약은 위 별도 문서를 따르며, 이 수동 승인 절차를 과거 승인만으로 생략하는 방식이 아니다.

1. 최종 반영 이후 **정기 daily가 새 사본을 생성·검증하고 정기 restic이 같은 ID를 저장·검사**한
   실제 실행 기록을 확인한다. 새 사본 없는 `processed=0`이나 이전 코드의 성공은 대신하지 않는다.
2. checkpoint를 읽는 프로세스의 시작 시각·실행 경로와 공통 잠금 사용을 확인한다. Python의
   기존 import는 파일 교체만으로 갱신되지 않는다. 오래된 장기 reader나 잠금에 참여하지 않는
   외부 복사가 있으면 끝날 때까지 보류하거나 해당 reader만 별도로 갱신한다. 수집 서비스 전체를
   재시작하지 않는다. 코드 해시는 다른 프로세스의 메모리나 잠금 준수를 증명하지 않는다.
3. 최종 적용 정책으로 새 plan을 만들고 경로·backup/snapshot ID, 기준/완료/판정 시각·경과시간,
   유지 사유, 정책 해시·전체 계획 ID·코드 ID를 제시한다. 이 **특정 계획에 대한 승인** 후 적용한다.
   설정의 `apply_enabled` 변경 자체는 실행이나 승인으로 간주하지 않는다.

매 정리마다 54분 독립 복구 시험을 반복하지 않는다. 검토한 복구 receipt와 해당 restic 지점의
존재·manifest, 현재 UUID/저장소 ID와 마지막 전체 저장소 검사 범위를 재확인한다. 미리보기는
사본 파일의 메타데이터 목록을 대조하고, 실제 적용 직전에는 **남길 작업용 사본의 파일 해시·
카탈로그·pack 무결성**을 검사한다. 이 비용과 전체 source 논리 검사·추출·재백업 비용은 별개다.
중단 후 재개도 현재 보호 조건과 남길 사본 검사를 통과해야 한다.

## 첫 정리 결과와 회수 용량 계산

10/5 승인 계획 `720264ba82bd7a994c0ac3dc73e157b814a7b63042b3a56cb5c96da1b787a200`의

참조한다. 다음 표는 정책 검토 당시의 과거 조사이며 현재 삭제 목록으로 재사용하지 않는다.

10/3 시점의 완료 사본은 10개다. 후보 목록과 정확한 ID는
[읽기 전용 조사 결과](../reports/baseline/restic-transition-2026-10-03/retention-inventory.json)에 있다.

| 구분 | 날짜·개수 | 이번 동작 |
|---|---|---|

하드링크 사본의 파일 크기를 합한 값은 디스크에서 회수할 수 있는 용량이 아니다.
조사는 `(device, inode)`별 실제 할당 블록을 한 번만 세고, 그 inode의 **모든 하드링크가
후보에 속할 때만** 회수 가능량으로 계산한다. 유지할 사본이나 범위 밖에서 참조하면 회수량에 넣지 않는다.
디렉터리 블록은 따로 표시하고 파일시스템 journal·부모 디렉터리 오버헤드는 제외한다.
이 값도 조사 시점의 예상치이며, 10/3에는 실제 삭제 후 여유 공간 증가를 측정하지 않았다.
당시 네 후보의 합계 파일 크기는 55.55 GB지만 회수 가능한 일반 파일 블록은 **3.64 GB**,
그 디렉터리 블록은 **0.53 GB**다. 두 값을 합한 조사상 예상은 약 **4.17 GB**다(십진 GB).
다른 하드링크가 참조해 남을 파일 블록 16.33 GB를 회수량에 중복 계산하지 않았다.

적용 시도별로 같은 UUID·장치의 `statvfs`를 전후 측정해 사용 가능 공간·전체 여유 공간과 변화량을
진행 기록에 남긴다. 수집 등 다른 쓰기도 포함하므로 음수도 그대로 기록하고 **정확한 정리 회수량은
`null`**로 남긴다. 예상 회수량과 관측 변화량은 별도 수치다. 종료 후 측정 실패는 기존 삭제 결과나
오류를 덮지 않고 별도 오류로 남긴다. 강제 종료로 사후 표본이 없으면 추정하지 않으며, 재개는
새 시도의 전후 표본으로 구분한다.

## restic 지점 만료 기능의 선행 작업

현재 `Archive.run()`은 로컬 checkpoint 폴더가 없어도 **모든 저장 성공 기록의 snapshot 존재**를
확인한다. 따라서 작업용 사본을 줄이는 것과 restic snapshot을 만료시키는 것은 별도 구현이다.
지금 바로 restic ID를 없애면 다음 예약은 올바르게 유실 오류를 보고한다.

후속 구현은 정식 보관 만료 기록을 추가해야 한다. 정책 버전·대상 ID·승인 목록·실행 전후 시각·
확인 결과를 남기고, 계획됨 → 적용 중 → 실제 부재 확인 → 만료 완료를 구분한다.
설명 없는 snapshot 소실은 계속 오류여야 한다. 상태 기록을 지우거나 누락 검사를 완화해 통과시키지 않는다.
parent 선택·검사 범위·상태 조회·재발견·복원 관찰 증거도 이 만료 상태를 일관되게 처리해야 한다.

우선 최신 3개·날짜별 정책과 명시적 보호 ID의 합집합으로 미리보기를 만들고, 다른 scope·
미확인/실패/중복 snapshot은 제외한다. 같은 날짜에 늦게 넣은 사본, 빈 기간·주/월/연도 경계,
출처가 다른 경로, 부분 실패와 중단 후 재개를 시험한다. 실제 `forget` 후에도 참조되지 않는 pack의
공간 회수는 별도 `prune` 작업이므로, 저장소 잠금·부하·후속 검사까지 설계하고 별도로 적용한다.
[restic의 snapshot 제거와 공간 회수 구분](https://raw.githubusercontent.com/restic/restic/v0.19.1/doc/060_forget.rst)

10/5 확인된 8개는 모두 보존 대상이어서 restic 만료를 서둘러 적용할 실익은 없다.
첫 작업용 사본 정리 뒤에도 daily의 전체 무결성 검사·카탈로그 checkpoint 생성 비용은 그대로 남는다.

## 독립 복구와 이전 준비의 범위

복구용 암호는 사용자 선택에 따라 두 번째 SSD의 별도 키트에 준비한다.
키트 폴더는 0700, 암호 파일은 0600으로 두며 값이나 해시는 Git·로그에 기록하지 않는다.
경로는 `/mnt/backup/marketdata-recovery-kit-20261003/secrets/restic-password`다.
키트에는 고정 커밋의 프로그램 코드·Python 패키지·고정 restic 실행 파일·출처 프로필을 함께 보존한다.
Python 인터프리터·OS까지 이식 가능한 설치 이미지로 만든 것은 아니다.

시험은 두 번째 SSD에 별도로 복제한 restic 저장소와 이 암호만으로, 원본 root·기존 checkpoint·
운영 설정·처리 상태·캐시가 보이지 않는 namespace에서 수행한다. 네트워크도 분리하고 상태·캐시를
빈 상태에서 시작한다. 저장소 ID·UUID·원래 source root 검사는 기존 프로그램 그대로 사용한다.
명시적 ID 추출 → 프로그램 복원 → 전체 무결성·표본 조회 대조 → 독립 새 백업·검증을 확인한다.

이는 현재 호스트에서 원본 경로에 의존하지 않는 복구를 확인하는 시험이다.
**다른 PC에서의 복구·SSD 자체 고장·Proxmox VM 부팅/마운트/서비스 재개 시험은 미완료**다.
암호의 PC 외부 보관도 사용자 결정대로 후속으로 남긴다. 같은 SSD에 저장소와 암호가 있어
그 디스크의 고장·분실을 함께 견디는 구성은 아니다.

0700·0600은 파일 접근 권한이며 디스크 암호화가 아니다. 관리자 권한이나 오프라인 접근으로
저장소와 암호를 모두 읽을 수 있으면 복호화가 가능하다. **PC 외부의 암호 보관**과 **다른 장비의
데이터 사본**은 별도의 후속 과제다. 암호만 밖에 보관해도 백업 SSD 고장을 견디는 데이터 사본이
생기는 것은 아니다.

기존 사본·시험 저장소·새 복구 키트·이번 추출/복원/재백업 결과는 현재 모두 보존한다.
시험 산출물 약 93GB를 영구 보관 정책으로 확정한 것은 아니다. 복구 키트·코드·문서·검증 근거는
보존하고, 재생성 가능한 저장소 복제본·추출본·복원본·재백업본은 구성별 **별도 수동 정리 후보**로
검토한다. 작업용 checkpoint 정리기에 포함하지 않으며, 93GB 전부가 회수 가능하다고 계산하지 않는다.
첫 정리 다음 새 daily·예약 restic 연결 확인은 완료했다. 추가 정리·자동화는 별도로 검토한다.
외부 복구 키 보관 및 실제 VM 이전 검증, 필요 시 restic 만료·공간 회수 기능도 후속으로 남긴다.
