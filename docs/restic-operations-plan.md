구현·격리 시험·실제 사본 수동 처리 결과 확인 후 승인받아 타이머를 적용했다.

[전환 전 복구 및 보관 정책](restic-transition-and-retention.md)에 정리한다. 실제 삭제는 적용하지 않았다.

## 결정과 단계

첫 단계는 기존 일일 백업이 만든 **완료된 사본을 별도 작업이 restic에 추가 보관**하는 방식이다.
일관된 SQLite 사본을 만드는 검증된 절차를 재사용하고, restic 전송 실패는 독립적으로 재시도한다.
기존 daily 작업의 전체 검증·카탈로그 복사 비용도 계속 발생한다.

| 단계 | 구현·관찰 범위 | 보관 정책 |
|---|---|---|
| 1. 연결 구현 | 완료 사본 식별, restic 저장, 중단 후 재개, 별도 상태 조회 | 기존 사본·restic snapshot 모두 보존 |
| 2. 예약 관찰 | 새 날짜 3회 이상, 저장소 검사, 새 사본의 복원 검증, 수집 부하 확인 | 삭제·기간 제한 없음 |
| 3. 보관 정책·전환 검토 | 작업용 완료 사본 수명과 장기 보관할 restic 복구 날짜 결정부터 시작 | 최종 보관 기간·중복 사본 정리를 별도로 결정 |

3회는 첫 운영 관찰의 기준이며 보관 기간이 아니다. 장기 안정성이나 미래 저장 증가율을
확정하는 기준도 아니다. **1·2단계에서는 안전한 비교와 전환을 위해 어떤 사본도 삭제하지 않는다.**
원본 데이터·수정 이력의 보존 정책과 날짜별 백업 복구 지점의 보관 정책은 별도로 취급한다.
원본·revision 보존 원칙은 유지하고, 최종 백업 보관 기간과 작업용·중복 사본 정리는 3단계에서 결정한다.
모든 날짜의 복구 지점을 영구 보관하는 것을 최종 정책으로 확정하지 않는다.
1·2단계에서는 전체 디스크 사용량이 늘어난다. 실제 공간 절감은 중복 사본을 어떻게 보관할지
정하는 3단계에서 다룬다. 현재 약 59 GB의 시험 작업 공간도 이번 연결 구현에서 지우지 않는다.

## 데이터와 실행 경계

```mermaid
flowchart LR
    A["기존 daily: 검증·일관된 사본 생성"] --> B["완료된 backup.json과 불변 파일"]
    T["별도 타이머: 미보관 사본 탐색"] --> C["사본 ID·출처·전체 무결성 확인"]
    B --> C
    C --> D["restic 저장·명시적 snapshot ID 기록"]
    D --> E["저장소 검사·독립 상태 기록"]
    E --> F["정해진 사본의 별도 경로 복원 시험"]
```

새 작업은 저장소의 실시간 `data/`와 열려 있는 SQLite를 직접 restic에 넣지 않는다.
원본의 `Store`를 초기화하지 않고, 완료된 사본은 기존 `load_backup`·`verify_backup`으로 읽는다.
조회·재백업용 `Store`는 프로그램으로 복원한 별도 경로에서만 연다.

후보는 프로필의 전용 `backup_dir`에서만 찾는다. 명시한 시작 UTC 날짜부터의
`<날짜>/<시도 ID>/backup.json`을 발견하고, 실제 처리 직전에 해당 ID·manifest 해시·
`source_root`와 카탈로그·파일을 검증한다. 편입 날짜는 manifest의 checkpoint 기준 시각을 UTC로
환산한 날짜다. 폴더의 날짜나 업로드 날짜로 대체하지 않는다. 다른 출처 사본은 오류로 남기고 자동 채택하지 않는다.
완료 표시가 없는 디렉터리는 처리 대상에서 제외하고 보존한다. 날짜만 보고 성공을 판단하지 않는다.

시작 날짜는 **운영 restic에 넣을 복구 지점의 범위**다. 첫 사본에도 그 시점에 등록된 과거 원자료와
모든 revision이 포함된다. 2019년 자료를 제외한다는 뜻은 아니다. 이전 날짜 복구 지점을
추가할 때는 별도 입력 목록을 지정한다. 시험용 restic 저장소와 원래 하드링크 사본은 유지한다.

## 예약과 잠금

유닛 이름은 `marketdata-restic-archive.service`와 `.timer`다.
기존 daily 유닛에 restic을 붙여 실패 때 전체 유지보수를 반복하는 구조로 만들지 않는다.

- 독립 oneshot 작업은 활성화 5초 뒤(`OnActiveSec=5s`) 최초 탐색하고, 매시 UTC 05분·35분에
  완료된 미보관 사본을 찾는다. `OnCalendar=*-*-* *:05,35:00 UTC`, `Persistent=true`, `AccuracySec=1s`다.
- 13:10 KST daily 완료 시각을 고정으로 가정하지 않는다. 사본이 늦게 완성돼도 다음 탐색에서 찾는다.
  정상 시 탐색 대기는 약 30분 이내이며, 전송·검사·백로그 처리 시간은 별도로 더해진다.
- 한 번에 오래된 순서로 최대 3개를 처리하고 남은 개수와 가장 오래된 대기 시간을 기록한다.
  재부팅 후에는 타이머가 놓친 횟수 대신 실제 미처리 사본 목록을 기준으로 따라잡는다.
- 같은 서비스가 실행 중이면 다음 만료가 새 인스턴스를 만들지 않는다. 수동 실행·검사와의
  경합은 저장소별 전용 `flock`으로 직렬화한다. 잠금 대기는 작업 실패와 구분해 기록한다.
- 유지보수의 `maintenance.lock`이나 수집 writer/layout 잠금을 restic 작업 동안 잡지 않는다.
  입력은 이미 완성된 불변 사본이며, restic 자체의 저장소 잠금도 유지한다.
- 첫 구현은 실패 시 다음 타이머 또는 명시적 수동 실행으로 재시도한다. 즉시 재시작을 반복하지 않는다.
  작업 전체 제한은 6시간, 종료는 SIGINT 후 최대 120초다.
  시간 초과 후에도 입력·실패 이력을 남기고 다음 실행에서 실제 상태를 확인한다.

현재 호스트의 systemd 255에서 위 calendar 식의 구문을 `systemd-analyze calendar`로 확인했다.
유닛 검증·설치 후 실제 사용자 서비스와 최초 타이머 기동을 확인했다.
로그인 여부·집계·한 차례 복원 실행 규칙은 [예약 운영 안내](restic-scheduled-operations.md)를 따른다.
[systemd 255 공식 타이머 설명](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd.timer.xml)

## 식별자와 성공 판정

원래 `backup.json`은 그대로 보관한다. 별도 처리 기록은 저장소 ID, 작업 범위 ID, marketdata
`backup_id`, manifest SHA-256, 원래 `source_root`, restic의 전체 snapshot ID와 시각을 연결한다.
프로필 해시·실행 도구 버전·시도 ID·종료 코드도 남기고 암호 값은 기록하지 않는다.

스냅샷의 `time`은 검증된 manifest의 **`checkpoint_finished_at`**으로 정한다. 이것은 일관된
SQLite 사본 생성 완료 시각을 복구 기준으로 삼는 규약이다. SQLite 사본 생성 구간의 시작과 끝도
보존하며, 포함된 시장 데이터의 최종 거래 시각이나 파일 복사 완료 시각을 뜻하지 않는다.
입력 시각은 시간대가 명시되어야 한다. UTC로 환산해 소수초까지 `backup --time`에 전달하고
restic 0.19.1의 시각 파서가 호스트 시간대에 의존하지 않도록 자식 프로세스의 `TZ=UTC`를 고정한다.
저장 후 snapshot metadata의 실제 time을 원래 기준 시각과 대조한다.

실제 restic 호출의 `archive_started_at`·`archive_finished_at`과 checkpoint 사본의 `completed_at`은
각각 별도 기록이다. 9/28·9/29 사본을 9/30에 함께 처리해도 스냅샷 time은 원래 두 날짜다.
중단 후 기록 복구 시 실제 호출 시각을 알 수 없으면 추정하지 않고 null과 `adopted_at`을 남긴다.
[restic 0.19.1 시각 파서](https://github.com/restic/restic/blob/v0.19.1/cmd/restic/cmd_backup.go)

| 상태 | 필요한 근거 |
|---|---|
| 발견 | 명시한 입력 범위 안의 완료 표시 존재 |
| 입력 검증 완료 | 기존 `verify_backup` 통과, ID·출처·manifest 일치 |
| 저장 완료 | restic 종료 코드 0, 성공 요약의 전체 snapshot ID, 그 snapshot의 manifest 일치 |
| 저장소 검사 완료 | 해당 저장 이후 `check --read-data` 성공 |
| 복원 시험 완료 | 명시적 ID 추출 → 프로그램 복원 → 무결성·표본 조회 → 새 전용 백업 검증 성공 |

위 상태를 한 개의 `ok=true`로 덮어쓰지 않는다. 저장됐으나 검사에 실패한 경우도 그대로 표시한다.
태그에는 작업 범위·backup ID·시도 ID를 넣되, 태그는 후보를 찾는 수단이다. 조회 결과의 모든
필요 태그와 manifest를 직접 대조한다. 호스트명이나 `latest`만으로 사본을 선택하지 않는다.
안정된 선택 태그는 `archive_scope=<범위>`이고, `backup_id=<ID>`·`attempt_id=<ID>`는 매번
달라지는 식별 태그다. 형식 표시 태그 `marketdata-archive-v1`도 확인한다.

백업은 시험과 같이 완료 사본을 작업 디렉터리로 삼아 상대 경로 `.`을 저장한다. 직전의 검증된
같은 범위 snapshot을 parent로 명시한다. 기본 압축 `auto`와 기본 파일 변경 검사를 유지한다.
원문을 제외하거나 inode·ctime 검사를 완화하는 옵션을 넣지 않는다.
[restic 경로·parent 설명](https://restic.readthedocs.io/en/stable/040_backup.html)

상대 경로 `.`은 복원 트리의 모양을 정한다. **snapshot metadata의 `paths`에는 입력의 절대 경로가
남는다.** 날짜별 폴더가 다르면 기본 `host,paths` 그룹이 갈리고, 전체 `tags`로 그룹화해도 개별
backup/attempt 태그 때문에 그룹이 갈린다. 명시적 parent 지정은 변경 탐지용이며 보관 그룹을
정하지 않는다. 첫 사본에는 parent 없이 전체 탐색을 하고, 이후 같은 범위의 검증된 ID를 명시한다.

향후 보관 정책은 먼저 안정된 단일 archive_scope로 대상을 엄격히 선택한 후 그 범위 안에서
날짜·시도별 paths/tags로 그룹을 쪼개지 않는 규칙을 검토한다. 예를 들어 범위 필터와 함께
그룹을 비우는 방식은 후보가 될 수 있지만 **이번 구현에는 forget/prune 명령도 보관 실행 기능도 없다.**
3단계에서 다른 범위·호스트·이전 이력을 섞지 않는지와 UTC 달력 기준 보관 결과를 dry-run으로
검증한 뒤 결정한다. `--keep-daily`·월별 규칙은 실행 날짜가 아니라 snapshot의 달력 시각을 따른다.
[공식 보관 그룹·달력 규칙](https://restic.readthedocs.io/en/stable/060_forget.html#removing-snapshots-according-to-a-policy)

restic 0.19.1의 `backup`은 종료 코드 3일 때도 불완전한 snapshot을 남길 수 있다.
0 이외의 종료 코드, 취소·시간 초과, 성공 요약 누락은 저장 완료로 처리하지 않는다.
알 수 없는 종료 코드도 실패로 처리한다.
[공식 종료 코드·JSON 출력 계약](https://restic.readthedocs.io/en/stable/075_scripting.html#exit-codes)

## 중단 후 재개와 중복 실행

외부 저장소 작업과 로컬 상태 기록은 하나의 트랜잭션이 아니다. 처음부터 정확히 한 번 실행된다고
가정하지 않는다. 시도 기록을 먼저 원자적으로 저장하고 restic을 호출한다.

| 중단 지점 | 다음 실행의 처리 |
|---|---|
| snapshot이 생기기 전 | 입력 검증 후 다시 시도. 실패 기록과 미참조 저장 객체는 보존 |
| snapshot 생성 후, 성공 기록 전 | 시도 ID로 후보를 찾아 명시적 ID로 추출·`backup-verify` 후 채택 |
| 종료 코드 3으로 snapshot 존재 | 실패 상태 보존. 파일 누락이 있는 사본을 성공으로 올리지 않음 |
| 저장 완료 기록 후, 저장소 검사 전 | 같은 ID를 검사. 백업을 다시 생성하지 않음 |
| 로컬 처리 기록 분실 | 저장소 ID·범위 태그·manifest로 후보 재발견 후 복원 검증으로 기록 재구성 |

종료 결과를 잃어버린 snapshot은 **태그와 manifest만 일치해도 성공으로 채택하지 않는다**.
불완전한 snapshot에도 `backup.json`은 들어 있을 수 있기 때문이다. 새 경로에 꺼내
파일·카탈로그·묶음 전체를 검사한 뒤 판단한다. 후보가 여러 개면 각각의 검증 결과와
선택한 전체 ID를 기록하고, 판별할 수 없으면 수동 점검이 필요한 상태로 남긴다.

일반 재실행에서는 기록된 snapshot ID의 존재·범위·manifest를 대조한다. 이전 성공 기록만
남고 실제 snapshot이 없으면 정상으로 건너뛰지 않는다. 저장소를 새로 만들거나 다른 ID로
조용히 바꾸지 않고 불일치를 보고한다. 실패한 후보·중복 snapshot은 자동 삭제하지 않는다.

## 호스트 설정과 VM 이전

현재 시험 프로필은 보존한다. 운영용 프로필은 별도 파일로 만들며 다음 항목을 분리한다.
아래는 별도 `restic-archive.example.toml`의 필드다. `restic_trial.py`의 프로필에 추가하지 않는다.

| 항목 | 역할 |
|---|---|
| `store_root`, `backup_dir` | 현 호스트의 원본과 그 출처 전용 완료 사본 폴더 |
| `backup_mount`, `backup_filesystem_uuid` | 필수 마운트와 현재 ext4 볼륨 신원 확인 |
| `restic_repository`, `expected_repository_id` | 운영 저장소 경로와 실제 restic 저장소 ID 대조 |
| `restic_binary`, `restic_password_file` | 고정 실행 파일·Git 밖의 0600 암호 파일 |
| `archive_scope`, `enroll_from_utc_date` | 안정된 작업 범위와 처음 편입할 복구 지점 날짜 |
| `state_root`, `reports_root`, `cache_root` | 처리 기록·보고서·재생성 가능한 캐시 |
| `restore_work_root`, `min_free_gib`, `max_checkpoints_per_run` | 독립 복원 공간·여유 공간·회당 처리 한도 |

운영 저장소의 제안 경로는 `/mnt/backup/marketdata-restic`이다. 시험 저장소
`marketdata-restic-pilot`과 분리하므로 첫 운영 사본의 저장 공간은 별도로 필요하다.
저장소 초기화는 준비 단계에서 한 번 수행하고 ID를 프로필에 고정한다. 정기 작업이 저장소
없음·잘못된 암호를 만났을 때 자동으로 `init`하지 않는다.
[저장소 존재 확인](https://restic.readthedocs.io/en/stable/075_scripting.html#checking-if-a-repository-is-already-initialized)

상태·오류 기록은 백업 SSD가 빠져도 쓸 수 있는 주 디스크에 둔다. cache도 별도 경로로 지정한다.
원본·완료 사본·restic 저장소·복원 작업 공간의 겹침과 심볼릭 링크를 거부하고, 암호는 이들
백업 입력 및 출력에 포함하지 않는다. 상속된 `RESTIC_*` 환경 변수로 프로필이 바뀌지 않게 한다.
호스트 프로필은 TOML로 읽고 외부 명령은 인자 배열로 호출한다.

마운트·볼륨 신원은 작업 전후 확인한다. 잘못된 디스크·마운트 누락·공간 부족은 기록 가능한
오류로 끝내며 로컬 경로로 대체하지 않는다. 마운트 준비는 호스트의 역할이고 프로그램도 반드시
직접 검사한다. VM에서 파일시스템을 새로 만들면 새 UUID를 호스트 프로필에 등록한다.

VM 이전 때는 옛 manifest를 수정하지 않고 명시적 snapshot을 꺼내 프로그램으로 복원한다.
새 `store_root`에서 생성할 첫 백업은 새 전용 `backup_dir`로 시작한다. 같은 restic 저장소를
연결할 경우 저장소 ID를 확인하고 새 출처의 작업 범위를 명시한다. 옛 범위의 사본과 ID는 유지한다.
restic을 주 백업으로 전환하기 전에는 독립된 장소의 암호 사본으로 저장소를 여는 절차도 확인한다.
현재 프로필 분리는 VM의 실제 마운트·부팅·서비스 재개 시험을 대신하지 않는다.

## 검사·상태·자원 관측

첫 관찰 단계에서는 새 사본을 저장한 배치마다 `restic check --read-data`를 수행한다.
검사 실패 시 저장 완료 사실은 남기되 저장소를 정상으로 표시하지 않고 후속 저장을 중단한다.
자동 `repair`·`unlock`·`forget`·`prune`으로 오류를 숨기지 않는다. 일반 `check`만으로 실제
데이터 pack 전체를 읽었다고 표시하지 않는다. 향후 저장소가 커져 검사 주기를 바꾸면
구조 검사·전체 검사·표본 검사의 시각과 범위를 구분한다.
[공식 저장소 검사 설명](https://restic.readthedocs.io/en/stable/045_working_with_repos.html#checking-integrity-and-consistency)

새 운영 사본의 복원 시험은 명시적으로 선택한 ID로 이번 시험과 같은 절차를 적용한다.
첫 예약 관찰 기간의 새 사본을 적어도 하나 끝까지 복원·재백업 검증한다.
장애 후 결과가 불명확한 snapshot의 채택에는 매번 추출·`backup-verify`를 요구한다.
복원 시험 폴더는 기존 폴더를 덮어쓰지 않으며, 장기 정기 복원 시험의 주기와 작업 공간
정리 정책은 별도로 정한 다음 예약한다.

도구는 `scripts/archive_backups.py`다. 기능 경계는 다음과 같다.

| 동작 | 역할 |
|---|---|
| `plan` | 프로필·후보·처리 기록을 읽어 처리할 ID를 보여줌. 저장소 생성·전송 없음 |
| `run` | 미처리 사본을 검증·저장·검사하고 단계별 결과 기록 |
| `status` | 기존 daily와 restic의 성공·대기·실패·최신 시각을 구분해 조회 |
| `verify` | 저장소 전체 검사 결과 기록. 전송 작업과 같은 전용 잠금 사용 |
| `restore-check` | 명시적 snapshot ID를 새 경로에 복원하고 응용 프로그램 검증 수행 |

시장 데이터·전략 코드에 restic 의존성을 넣지 않고,
기존 백업 API를 사용하는 운영 도구에서 외부 실행 파일을 호출한다.

현재 `maintenance-status`는 restic 상태를 알지 못한다. 기존 daily가 성공했다고 restic까지
성공했다고 해석하지 않도록 새 상태 조회에는 다음을 함께 표시한다.

- 최신 원본 checkpoint ID·시각, 마지막으로 restic에 저장·검사한 checkpoint ID·시각.
- 미처리 개수·최고 대기 시간, 처리 중인 단계·잠금 대기·실패 원인.
- 마지막 전체 저장소 검사와 복원 시험의 ID·시각·범위.
- 필수 마운트·저장소 ID·여유 공간·사용 inode 상태.

처리할 사본이 없는 정상 탐색은 새 전송 성공 시각으로 기록하지 않는다.
원본 daily가 36시간 넘게 갱신되지 않거나 새 checkpoint가 2시간 넘게 미보관 상태이면
지연으로 표시한다. 잠금·전송·검사 실패는 기한을 기다리지 않고 실패로 표시한다.
2시간은 첫 관찰용 기준이며 전송 완료 시간을 보장하는 값은 아니다.

우선 시험과 같은 `nice +10`, `ionice` best-effort 7, restic 동시성 2로 시작한다.
입력 검증·전송·저장소 검사·복원을 각각 측정하고 checkpoint 준비 비용도 별도로 기록한다.
실시간 수신 경과 시간과 오류·flush 실패를 관측한다. 신규 세션의 미보고 값은 미보고로 남기고,
예정된 세션 전환과 새로운 수집 문제를 구분한다. 동시성 설정을 강제 자원 상한으로 표현하지 않는다.

## 구현 순서와 완료 기준

9/27에 구현·격리 시험·실제 사본 수동 처리·재실행 검증까지 마쳤다.
[검증 기록](../reports/baseline/restic-archive-2026-09-27/summary.md)에 관련 테스트 70개와
실제 snapshot 1개 → 1개 재실행 결과를 남긴다. 이어서 별도 타이머 적용과 최초 실행 검증을 마쳤다.
[10/1 점검](../reports/baseline/restic-observation-2026-10-01/summary.md)에서 9/29·9/30·10/1의
실제 예약 저장·전체 검사 **3/3**과 새 운영 snapshot의 복원·독립 재백업 검증을 확인했다.
수동 실행·처리 0개 탐색은 날짜 집계에서 제외했다. 병행 예약을 유지하며 최종 보관 기간과
작업용·중복 사본 정리는 3단계에서 별도로 결정한다. 수집 품질의 후속 문제는 관찰 완료와 구분한다.

1. 운영 프로필 로딩과 전용 잠금, 읽기 전용 후보 탐색·상태 조회를 구현한다.
2. 검증된 사본의 restic 저장과 단계별 기록, 중단 후 재개를 구현한다.
3. 격리 테스트와 작은 실제 restic 저장소에서 아래 실패 조건을 검증한다.
4. 검토 가능한 유닛 파일을 작성하고 설치 전 구문·경로를 검사한다.
5. 실제 완료 사본 하나를 수동으로 처리하고 반복 실행 때 중복 snapshot이 생기지 않는지 확인한다.
6. 수동 처리·재실행 결과를 사용자와 확인한 뒤 운영 프로필·마운트를 점검하고 별도 타이머를 적용한다.
7. 새 날짜의 예약 성공 3회 이상과 새 사본 복원을 기록한 뒤 주 백업 전환 여부를 판단한다.

| 필수 시험 | 기대 결과 |
|---|---|
| source root가 다른 사본·손상된 manifest·미완료 사본 | 성공 처리 거부, 원본 보존 |
| 입력 파일 손상·누락 | 전송 전 실패, 검증 생략 없음 |
| 마운트·볼륨·저장소 ID 불일치, 암호 오류, 공간 부족 | 실패 기록, 자동 초기화·다른 경로 사용 없음 |
| 두 실행의 중첩 | 전용 잠금으로 직렬화, 수집·유지보수 잠금 장기 점유 없음 |
| 정상 완료한 ID를 다시 실행 | 같은 snapshot을 확인하고 새 snapshot 생성하지 않음 |
| 정상 snapshot 생성 직후 프로세스 중단 | 기존 ID의 실제 복원 검증 후 처리 기록 복구 |
| 일부 파일이 빠진 snapshot과 종료 코드 3 | manifest가 있어도 완료로 채택하지 않음 |
| 데이터는 저장됐지만 저장소 검사 실패 | 저장 사실과 실패를 함께 기록, 정상 상태로 덮어쓰지 않음 |
| 처리 기록 분실·중복 후보·snapshot 누락 | 실제 저장소와 대조, 불명확한 상태를 자동 정상화하지 않음 |
| 재부팅·정기 실행 누락 | 완료된 미처리 사본을 찾아 순서대로 재개 |
| 다른 경로에서 복원·새 첫 백업 | 옛 manifest 보존, 새 root·새 ID, 기존 source-root 검사 유지 |

첫 운영 연결에는 사본 삭제, 보관 기간 단축, 실시간 SQLite 직접 백업, 운영 검증 빈도 축소를
포함하지 않는다. 주 백업 전환 시에는 별도 문서로 checkpoint 준비 방식과 중복 사본 정리를
구체화한다. 같은 PC의 두 번째 SSD라는 장애 범위도 운영 연결만으로 달라지지 않는다.
