## 시각 문제를 수집 실행 구조에서 해결

[10/5 호가 후속](../../reports/baseline/depth-status-followup-2026-10-05/summary.md)은 종료 7개의
수신·저장 244,357건, REST 대조 2,464회 일치를 확인했다. 첫 정기 종료와 다음 기동은 완료했고,
선택한 3개 세션을 재생했다. interrupted/partial은 보존했으며 전체 24시간 전수 재생으로 확대하지 않았다.

그 점검에서 로컬 수신 시각 약 41초 역행을 발견했다. [기동 원인 대조](../../reports/baseline/stream-startup-readiness-2026-10-05/summary.md)는
같은 boot의 monotonic 기록으로 수집 시작 8.55초, 시스템 네트워크 준비 12.49초, 최초 NTP 동기화 111.37초를 구분했다.
거래소 ID 연결은 유지됐지만 로컬 시각은 보정됐으며, 당시 RTC도 시스템 시각보다 약 41초 빨랐다.
사용자 manager의 `network-online.target` 표기만으로 시스템 준비를 기다리지 못했던 경로를 확인했다.

장기 운영 구성을 현재 PC에서 먼저 만들고 향후 VM에서도 재사용하기로 했다.
고정 코드·비 editable venv·머신별 외부 설정을 분리하고, system systemd가 일반 계정 수집기를 관리한다.
Chrony가 시각을 제어하며 root bootstrap은 초기 보정·ledger를 관리한다. 수집 계정에는 시각 변경 권한을 주지 않는다.

최종 고정 ID는 **`system-bootstrap-20261007-f85eb8321a19c1ee`**다.

- 준비 실패 시 본 수집/업무를 시작하지 않고 조건 회복을 기다린다. 기존 업무 8개도 공통 대기·마지막 검사를 사용한다.
- 평상시 Chrony는 자동 step window를 두지 않는다. bootstrap이 닫힌 뒤 같은 부팅에서 보정 권한을 다시 열지 않는다.
- 같은 chronyc 프로세스에 `retries 0`을 적용한 인자 없는 `makestep`을 사용한다.
  응답 유실 시험에서 이전 호출은 2회, 보완 호출은 1회 전송이었다. 결과 불명 상태를 지우거나 자동 재전송하지 않는다.
- runtime은 UTC·monotonic·boottime과 현재 Chrony를 관측한다. 시각 이상을 기록하며 원문/Book 계산을 바꾸지 않는다.

[최종 후보와 재현](../../reports/baseline/system-runtime-bootstrap-revision-2026-10-07/summary.md)에
관련 **297건 통과 및 깨끗한 별도 경로 297건 재현**, 실제 user manager의 8개 업무 대기/재개 결과가 있다.
[root 접근 시험](../../reports/baseline/system-runtime-root-preflight-2026-10-07/summary.md)은 보호 옵션 아래의
Chrony Unix socket·응답 소켓·runuser 조회·fsync·공유 잠금을 확인했다. `-x` 시험을 실제 시각 동기화 성공으로 세지 않았다.

## 실제 전환과 설치 중단의 처리

[실제 전환 기록](../../reports/baseline/system-cutover-2026-10-08/summary.md)은 단계별 사용자 인계를 보존한다.

설치 중단 두 건도 성공 기록으로 덮지 않았다. 첫 원인은 로컬 `.deb` 설치를 막은 `--no-download`,

root 사전 시험의 `/run` noexec 배치 문제도 시험 코드 경로를 `/opt`로 옮겨 해결했으며 mount 보호는 유지했다.

23:52 고정 배포본과 Chrony 설치·실제 접근 검사가 끝났고, 23:57 시각 기준을 통과했다.

초기 남은 보정 약 67ms가 기준 안이어서 실제 큰 보정은 불필요했다. 시계를 일부러 틀려 시험하지 않았다.

[부팅 후 저장 점검](../../reports/baseline/system-cutover-2026-10-08/post-reboot-summary.md)은

## 복구 지점과 데이터 완전성을 분리

전환 준비 중 발견한 `marketdata-daily`의 `waiting_source`는 원천 갱신 미완료였다.
현재 공개된 ZIP을 확인해 기존 갱신 경로로 10/6 UTC 자료 4종 **4,608행**을 채웠다.
[10/8 정기 백업 후속](../../reports/baseline/system-cutover-backup-followup-2026-10-08/summary.md)에서
14:08 checkpoint 완료 → 14:35 예약 archiver → 14:40 저장 → 14:41 전체 읽기 검사를 연결했다.
명시적 snapshot에서 4개 파일을 읽어 실제 보강분 포함도 대조했다.

같은 날 새로 확인한 10/7 UTC 미완료도 전환 창에서 보강했다. 수집 종료 뒤의 최종 수동 복구 지점은 다음과 같다.

| 항목 | 식별자·실제 결과 |
|---|---|
| checkpoint 기준 시각 | 2026-10-08 21:43:04 KST |
| backup ID | `be6f6e493aa13931b3d0cddd03581f5b009c540b7560b7a9a7faf7006d5174a8` |
| restic snapshot ID | `da1af66eeece550548f2b6daf549ffa22b662a9d32155bf4485c20c6cae51ae2` |

수동 저장을 예약 성공 날짜로 세지 않았다. 전환 뒤 부팅 시 archiver의 `processed=0`도 새 백업으로 세지 않았다.
새 환경에서 쌓인 자료는 10/9 13:10 예약 checkpoint의 실제 완료와 같은 backup ID의 restic 결과를 확인해야 한다.

전환 수집 공백은 약 2시간 31분이다. 호가 공백은 과거 REST로 복구하지 않았고 새 anchor 이후 수집과 구분한다.
aggTrade 자동 복구는 기존 상한 20페이지로 20,000건을 저장했고 **`3478886750–3479150818`, 264,069개 ID**를 남겼다.
[전체 카탈로그 범위 확인](../../reports/baseline/aggtrade-coverage-2026-10-09/summary.md)에서는 상시 수집 이후 이 한 구간만 미복구였고,
상시 시작 전 표본 사이에는 별도로 4개 공백·1,901,391개 ID가 남았다. 모든 원문/행을 새로 전수 검사한 것은 아니다.
공식 일별/월별 아카이브 제공도 실제 확인했지만 importer·실제 보강은 아직 없다.
REST 48시간 제한을 모든 복구 경로의 영구 손실 마감으로 해석하지 않는다.

10/9 00:20:43에는 초기 검사 subset 뒤에 호가 범위 소진 1건이 있었다. 같은 소켓에서 복구했으나
손실·`partial`을 유지한다. 실패 상태 선행 공개 기록과 runtime 시각 정상은 확인했고, 이 사건의 근본 원인은 미확정이다.
