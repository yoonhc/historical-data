## 독립 복구와 보관 정책을 확정

이전 문서에서 남긴 10/3 daily의 잠금 경합은 기존 정책으로 자동 재시도했다.
13:50 사본 완료와 같은 backup ID의 14:05 예약 보관·14:09 전체 읽기 검사까지
[실제 기록으로 확인](../../reports/baseline/restic-observation-2026-10-03/summary.md)했다.
원문 감사와 시각이 겹쳤지만 잠금 소유 PID가 없어 감사만을 유일한 원인으로 확정하지 않았다.
새 사본 처리 1회와 처리 0개 탐색을 구분했고, 이미 끝난 날짜별 관찰 3/3에 중복 합산하지 않았다.

이어 [10/3 독립 복구](../../reports/baseline/restic-transition-2026-10-03/summary.md)는
원래 프로젝트·checkpoint·운영 저장소/프로필/암호·처리 상태·캐시를 숨긴 환경에서 수행했다.
별도 SSD의 복구 키트·암호 사본과 독립 inode의 복제 restic 저장소로 시작해 다음을 통과했다.

| 단계 | 실제 검증 |
|---|---|
| 명시적 snapshot 추출 | `d27a0a55…`의 `restore --verify`, 약 61초 |
| 기존 사본 검증·프로그램 복원 | 45,683개 파일, 원래 manifest·source_root 유지 |
| 전체 논리 무결성 | 865,619건·실패 0, 약 34분 36초 |
| 조회 대조 | 연구 snapshot 20개·표본 조회 107개와 원문/체결/호가 표본 일치 |
| 새 독립 백업 | 복원된 실제 root로 새 ID 생성·검증, 추출/복원/재백업 파일 inode 분리 |

전체 약 **54분 7초**는 추출부터 재백업까지의 시간이다. 새 처리 상태에서 알 수 없는 원래 보관 시각은
null로 남겼고 기존 실패·격리·호가 `continuous=false`도 유지했다. 같은 호스트의 격리 시험이며
다른 PC의 설치/부팅까지 검증한 것은 아니다. 두 번째 SSD의 키트와 그 암호의 실제 사용은 확인했지만
PC 외부 암호 보관과 다른 장비의 데이터 사본은 별개로 남았다.

이 결과를 바탕으로 [초기 보관 정책](../restic-transition-and-retention.md)을 구체화했다.

- 원본 시장 데이터·revision은 기간 제한 없이 보존한다.
- 작업용 완료 사본은 **검증된 최근 3개와 완료 후 72시간 미만의 합집합**을 보호한다.
- restic은 최근 3개·일별 30개·주별 12개·월별 12개·연별 무제한의 합집합을 보관하는 정책이다.
  모든 일별 지점을 영구 보존한다는 의미가 아니며, 실제 snapshot 만료/`prune`은 아직 미적용이다.
- 편입 전 사본·시험 공간·복구 키트와 초기 전환 복구 증거는 별도 보호한다.

실제 snapshot의 기본 `host,paths` 및 전체 태그 그룹이 날짜마다 나뉘는 것도 확인했다.
향후 단일 `archive_scope` 선택과 보관 그룹을 구분하고, 정상 만료 기록을 구현하기 전에는 snapshot 유실 검사를 완화하지 않는다.

## 작업용 사본 정리를 구현하고 수동 적용·자동화로 연결

[정리기 구현](../../reports/baseline/checkpoint-retention-2026-10-03/summary.md)은
plan/status와 전체 계획 ID를 지정하는 apply를 추가했다. 미해결 오류·미보관·검사 대기를 막되,
해결된 과거 실패 기록은 보존한다. maintenance → repository → 사본 부모의 잠금 순서를 사용하고,
backup/restore/조회/archiver도 같은 공유 잠금에 참여하게 했다. 원본 collector writer를 장시간 잠그지 않는다.

삭제 목록·진행 기록을 먼저 fsync하고 전용 영역으로 이동한 뒤 기록된 파일만 제거한다.
강제 종료 5개 지점의 재개, 예상 밖 파일 보존, 완료 사본 재등장 거부, restic 지점 유실,
정리 후 다음 daily/restic 연결을 격리 시험했다. 최종 434개 검사 통과 기록과 최초 Git 이력 부재로 인한 실패를 함께 남겼다.
[10/4 보강](../../reports/baseline/checkpoint-retention-guards-2026-10-04/summary.md)은 코드/정책 해시,
사본별 완료 시각·경과시간·보호 사유, snapshot 연결, 공간 전후 관측을 계획에 묶었고 관련 14건을 통과했다.
기존 434건을 다시 전부 실행한 결과로 합산하지 않았다.

실제 적용 순서는 다음과 같았다.

| 단계 | 실제 결과·근거 |
|---|---|
| 최종 코드의 새 예약 흐름 | [10/4 사본·예약 보관 확인](../../reports/baseline/checkpoint-retention-readiness-2026-10-05/summary.md): 948,193개 논리 검사, 13:51 사본 완료, 14:09 restic 전체 읽기 검사 |

첫 수동 정리의 후보 논리 크기는 **75.27 GB**, 하드링크를 고려한 예상 회수량과 여유 공간 관측 증가는
각각 **5.56 GB**였다. 다른 쓰기가 가능한 환경이므로 정리만의 정확한 회수량은 null로 유지했다.
같은 계획을 재실행해 추가 삭제가 없는 것도 확인했다. 당시 03:15 pack은 잠금을 기다린 뒤 정상 완료됐다.

자동화는 당일 daily와 **동일 backup ID의 restic 저장·전체 검사**를 확인한 뒤 새 계획을 만든다.
처리 0개·조건 미충족·실제 실패·정리 완료를 구분하며, 잠금 경합이나 선행 작업 미완료는 다음 날 다시 평가한다.
미완료 정리가 있으면 점검 필요로 남기고 새 정리나 자동 재개를 하지 않는다.
활성화 당시 첫 예약은 아직 발생 전이었고, 아래 10/8 실제 예약 결과와 별개다.

## 호가 보류 관찰과 두 범위 손실의 독립 계산

이전 마일스톤의 미완료 항목인 [첫 종료 세션 검증](../../reports/baseline/depth-decisions-followup-2026-10-03/summary.md)은
35,584행·원문 가격/수량 쌍 약 296만 개와 REST 대조 351회를 확인했다.
실제 보류 1회는 대조 대기·최소 간격이 함께 적용됐고 다음 증분에서 해소됐다. 연결 교체를 포함하므로 `continuous=false`는 유지했다.

[확대 관찰](../../reports/baseline/depth-decisions-observation-2026-10-05/summary.md)은
10/3 11:17부터 10/5 08:30까지 종료 45개 세션을 고정해 첫 24시간 관찰도 마무리했다.
43개 complete·2개 partial, 수신/저장 증분 1,585,267개, REST 동일 ID 대조 15,823회 일치였다.
47,955개 표준 segment의 해시·행 순서·연결을 확인했고, 실패 두 세션의 원문 71,187행을 대조했다.
종료 시점에 뒤따를 증분이 없던 REST 대기 1개는 미검증으로 유지했다.

보류 평가는 105회였으나 장애 105건이라는 뜻이 아니다. 문맥이 남은 67개는 이후 필요 조건이 해소됐고,
38개는 개별 문맥이 없어 전수 정상으로 확대하지 않았다. 추가 요청 예산 소진은 0회였다.
네트워크 표본 2,712개 중 REST TLS timeout 1개는 두 범위 손실과 시각이 달랐다.
09:15 pack의 잠금 실패도 자동 재시도로 09:18 정상 완료됐으며 잠금 소유 PID가 없어 감사만의 책임으로 단정하지 않았다.

두 사건은 [별도 독립 계산기](../../reports/baseline/depth-independent-2026-10-05/summary.md)로 좁혀 검증했다.
운영 `Book.apply`·`History.align`·`Session.compare`·parser·replay를 정답 계산에 재사용하지 않고,
고정한 실제 원문 8,221행에서 공식 ID/절대 수량 규칙과 프로젝트의 범위 정책을 분리했다.
81회 범위 채택 모두 공통 가격의 존재·수량이 일치했고 최종 Book 해시도 운영 보고서와 같았다.

| 실패 증분 뒤 부족한 쪽 | 마지막 범위 교체 생략 | 실제 새 범위 채택 |
|---|---:|---:|
| 10/4 06:05 매수 | 0개 | 0개 |
| 10/5 07:16 매도 | 0개 | 8개 |

두 번째 사건은 새 매도 범위가 기존 범위를 포함했고, 기존에 없던 추가 범위에서 8개가 남았다.
따라서 **기록된 두 사건에서 마지막 범위 교체 생략만으로 top 20 부족을 피할 수 없었다.**
더 자주 요청했을 때의 미관측 응답·거래소 내부 체결/취소 원인까지 규명한 것은 아니다.
현재 요청 예산·최소 간격·범위 채택을 유지했고 긴급 갱신용 예산 예약을 추가하지 않았다.

## 발견한 실패 상태 공개 지연을 수정·배포

독립 계산과 별개의 소비 경로 시험에서, 수집기는 실패를 감지했어도 대량 저장·보고서 커밋 전에는
외부 `depth-status`가 이전 정상 보고서를 읽는 순서를 확인했다. 한쪽 0개는 이전 Book을 보존한 채 예외가 나고,
8개는 새 Book을 반영한 뒤 호출부가 top 부족으로 처리한다. 저장 뒤에는 둘 다 거부 상태와 `partial`이 유지됐지만
저장 중 공개가 늦었다. 실제 두 사건의 지연 시간이나 거래 피해를 측정한 결과는 아니다.

[선행 공개 후보](../../reports/baseline/depth-status-candidate-2026-10-05/summary.md)는
마지막 DB 보고서에 실패 관측만 반영해 먼저 커밋하고, 이후 이벤트·상세 보고서를 저장하도록 바꿨다.
아직 저장하지 않은 ID·건수·epoch·수신 시각은 확정 범위로 올리지 않으며 재시도도 손실을 중복 증가시키지 않는다.
대량 저장을 장벽에서 멈춘 상태로 별도 SQLite 연결·실제 CLI의 실패 표시를 확인했고 관련 163건을 통과했다.

추가 검토에서는 `failure_notice`가 없는 일반 flush 지속 실패도 시험했다.
[최종 배포본](../../reports/baseline/depth-status-release-2026-10-05/summary.md)은
최종 flush 실패 시 항상 마지막 DB 보고서를 유지하고 종료 직전 메모리 관측을 별도 진단 필드로 남긴다.
저장 `OSError`가 소켓 오류 재연결로 처리되지 않게 했고, 일반 원문/JSON 오류 4건을 더한 **167건**과
깨끗한 경로 재현·역패치를 확인했다. Book 계산·원문 형식·요청/범위 정책·재생 기준은 유지했다.

[10/5 14:01 운영 적용](../../reports/baseline/depth-status-deploy-2026-10-05/summary.md)은
유지보수 완료 뒤 호가 서비스만 SIGINT로 종료하고 승인한 소스 2개·테스트 3개를 반영했다.
새 프로세스의 정상 저장·상태와 REST 대조를 확인했으며 기존 중단 경계는 interrupted로 남겼다.
첫 정기 세션과 저녁 후속 결과는 다음 절에서 이어진다.

DB/CLI가 상태 조회의 기준이며 JSON은 쓰기 실패 시 오래된 보조 사본일 수 있다.
DB 기록 자체가 실패하면 즉시 공개를 보장하지 못하고, 단일 JSON 오류도 해당 수집을 최종 failed로 남기는 정책이다.
이 제한을 숨기거나 실제 거래용 최신 호가 제공까지 검증한 것으로 확대하지 않았다.

## 시각 문제를 수집 실행 구조에서 해결

[10/5 호가 후속](../../reports/baseline/depth-status-followup-2026-10-05/summary.md)은 종료 7개의
수신·저장 244,357건, REST 대조 2,464회 일치를 확인했다. 첫 정기 종료와 다음 기동은 완료했고,
선택한 3개 세션을 재생했다. interrupted/partial은 보존했으며 전체 24시간 전수 재생으로 확대하지 않았다.

그 점검에서 로컬 수신 시각 약 41초 역행을 발견했다. [기동 원인 대조](../../reports/baseline/stream-startup-readiness-2026-10-05/summary.md)는
같은 boot의 monotonic 기록으로 수집 시작 8.55초, 시스템 네트워크 준비 12.49초, 최초 NTP 동기화 111.37초를 구분했다.
거래소 ID 연결은 유지됐지만 로컬 시각은 보정됐으며, 당시 RTC도 시스템 시각보다 약 41초 빨랐다.
사용자 manager의 `network-online.target` 표기만으로 시스템 준비를 기다리지 못했던 경로를 확인했다.

장기 운영 구성을 현재 PC에서 먼저 만들고 향후 VM에서도 재사용하기로 했다.
고정 코드·비 editable venv·머신별 외부 설정을 분리하고, system systemd가 일반 계정 수집기를 관리한다.
Chrony가 시각을 제어하며 root bootstrap은 초기 보정·ledger를 관리한다. 수집 계정에는 시각 변경 권한을 주지 않는다.

최종 고정 ID는 **`system-bootstrap-20261007-f85eb8321a19c1ee`**다.

- 준비 실패 시 본 수집/업무를 시작하지 않고 조건 회복을 기다린다. 기존 업무 8개도 공통 대기·마지막 검사를 사용한다.
- 평상시 Chrony는 자동 step window를 두지 않는다. bootstrap이 닫힌 뒤 같은 부팅에서 보정 권한을 다시 열지 않는다.
- 같은 chronyc 프로세스에 `retries 0`을 적용한 인자 없는 `makestep`을 사용한다.
  응답 유실 시험에서 이전 호출은 2회, 보완 호출은 1회 전송이었다. 결과 불명 상태를 지우거나 자동 재전송하지 않는다.
- runtime은 UTC·monotonic·boottime과 현재 Chrony를 관측한다. 시각 이상을 기록하며 원문/Book 계산을 바꾸지 않는다.

[최종 후보와 재현](../../reports/baseline/system-runtime-bootstrap-revision-2026-10-07/summary.md)에
관련 **297건 통과 및 깨끗한 별도 경로 297건 재현**, 실제 user manager의 8개 업무 대기/재개 결과가 있다.
[root 접근 시험](../../reports/baseline/system-runtime-root-preflight-2026-10-07/summary.md)은 보호 옵션 아래의
Chrony Unix socket·응답 소켓·runuser 조회·fsync·공유 잠금을 확인했다. `-x` 시험을 실제 시각 동기화 성공으로 세지 않았다.

## 실제 전환과 설치 중단의 처리

[실제 전환 기록](../../reports/baseline/system-cutover-2026-10-08/summary.md)은 단계별 사용자 인계를 보존한다.
10/8 21:40 두 수집기의 저장 종료와 20개 유닛 persistent mask를 확인한 뒤 Windows 작업으로 넘겼다.
Windows UTC flag·시간대·동기화는 사용자 확인, Linux RTC·설정·mask·마운트는 실제 조회로 구분했다.
22:53에는 동기화된 시스템 시각을 기준으로 RTC UTC 설정을 반영했고, 두 번째 왕복에서도 유지됨을 확인했다.

설치 중단 두 건도 성공 기록으로 덮지 않았다. 첫 원인은 로컬 `.deb` 설치를 막은 `--no-download`,
둘째는 `chronyd.service` alias 등록보다 먼저 의존 관계를 검사한 순서였다. 해당 단계만 수정·재개했고
고정 후보·보호 옵션·시각 품질 기준을 낮추거나 ledger를 재등록하지 않았다.
root 사전 시험의 `/run` noexec 배치 문제도 시험 코드 경로를 `/opt`로 옮겨 해결했으며 mount 보호는 유지했다.

23:52 고정 배포본과 Chrony 설치·실제 접근 검사가 끝났고, 23:57 시각 기준을 통과했다.
최종 Linux 부팅에서는 10/9 00:11:18에 bootstrap `closed`, **step 0회**로 수집 준비를 마쳤다.
초기 남은 보정 약 67ms가 기준 안이어서 실제 큰 보정은 불필요했다. 시계를 일부러 틀려 시험하지 않았다.

[부팅 후 저장 점검](../../reports/baseline/system-cutover-2026-10-08/post-reboot-summary.md)은
