**1. 실제 운영 자료를 감사하고 저장량 증가를 측정했다.**

22회, 가격 범위 소진 3회, 보존됐지만 정상 호가로 재구성되지 않은 증분 2,146개를 확인했다.

**2. 두 번째 SSD의 파일 단위 증분 백업과 독립 복원을 구현·검증했다.**

자동 백업 목적지는 사용자가 지정한 두 번째 SSD의
`/mnt/backup/marketdata-historical/automatic/`이다. 같은 PC 안의 별도 SSD이며,
별도 장비나 원격 백업은 아니다. 기존 로컬 전체 사본과 원문·표준 데이터의 무기한 보존은 유지한다.

이전 완료 사본과 경로·종류·크기·해시가 같은 불변 파일은 백업끼리 하드링크로 공유한다.
새 파일은 새로 저장하고, **SQLite 카탈로그는 일관된 전체 사본을 매번 독립적으로 만든다.**
원본과 복원본은 백업과 하드링크를 공유하지 않는다. 날짜별 복구 지점에는 독립 카탈로그와
전체 파일 목록이 있으며, 이전 백업 디렉터리의 경로에 의존하지 않고 복원할 수 있다.

| 사본 | 해당 복구 지점의 전체 내용 | 이전 사본과 공유 | 새로 저장 |
|---|---:|---:|---:|
| 9/25 두 번째 검증 사본 | 6.074 GB | 5.783 GB | 0.291 GB |
| 9/26 새 날짜 자동 사본 | 8.710 GB | 5.666 GB | 3.045 GB |
| 9/27 새 날짜 자동 사본 | 10.546 GB | 8.156 GB | 2.389 GB |

위 값은 반올림한 파일 내용 크기이며 manifest·디렉터리·파일시스템 메타데이터는 제외한다.
9/25 첫 사본은 약 6.072 GB를 새로 저장했고 두 번째 검증 사본은 약 2분 뒤 만들었다.
따라서 **291 MB는 기존 6 GB 전체가 압축된 크기도, 하루 신규 수집량도 아니다.**
대부분의 기존 파일을 공유한 뒤 카탈로그 전체 사본과 추가 파일을 저장한 양이다.

카탈로그의 새 사본만 9/26에는 439.116 MB, 9/27에는 568.586 MB였다. 새 저장량에는
기존 개별 파일을 ZIP으로 묶으면서 배치가 바뀐 자료도 포함된다. 파일 단위 재사용만으로는
이런 파일 내부의 중복까지 줄이지 못하므로 다음 restic 시험에서 비교할 대상이다.

9/25에는 두 번째 사본을 별도 경로에 독립 복사로 복원해 전체 파일·SQLite 참조·묶음을 검증했다.
파일 30,572개의 inode를 확인했고, 스냅샷 20개와 데이터셋별 표본 107개 구간·109,497행의
모든 열을 원본과 대조했다. 체결·호가 표본 4개 세그먼트·1,060행과 원문 표본 10개도 일치했다.
파일 전체 복원·무결성 검사와 조회 표본 검사를 수행한 것이며 모든 기간을 다시 조회한 것은 아니다.

9/26·9/27에는 기존 예약으로 새 날짜 사본이 생성되는 것을 확인했다. 생성기가 완료 표시 전에
파일 해시·묶음을 검증했고, 추가 검사로 전체 파일 크기·재사용 계산·공유 inode와 독립 카탈로그를
확인했다. 두 날짜 모두 체결·호가 파일 4개를 백업에서 다시 읽었다. 이 두 사본의 별도 전체
복원은 반복하지 않았으며 9/25 독립 복원 시험과 구분한다.

예약은 매일 13:10이다. 당일 완료 사본이 있으면 검증 후 재사용하고, 다음 날짜에 새 사본을
만든다. 목적지·필수 마운트 누락, 공간 부족, 하드링크 실패는 오류로 처리한다. 공유 파일 자체가
손상되면 이를 공유하는 여러 복구 지점이 영향을 받으며, 무결성 검사가 독립 사본을 대신하지는 않는다.

**3. 호가 동기화 문제를 두 단계로 나누어 수정했다.**

첫 번째 문제는 새 소켓을 열었어도 실제 증분이 도착하기 전에 REST를 요청할 수 있었다는 점이다.
그러면 스냅샷이 첫 증분보다 오래되어 엄격한 업데이트 ID 연결 조건을 만족하지 못할 수 있다.
9/25 11:16에 **실제 첫 증분을 수신·보존한 직후 최초 스냅샷을 요청**하도록 적용했다.
첫 수신 대기는 최대 2초이며 고정 2초 지연을 넣는 방식이 아니다.

전체 테스트 232개와 별도 실시간 표본을 검증했다. 다음 24시간에 시작한 새 연결 96회는
첫 수신 원문과 표준 이벤트를 직접 대조했고, 수신 뒤 REST 요청 순서와 최초 ID 연결 조건을
모두 만족했다. 다만 가격 범위 소진 2회와 같은 소켓의 복구 중 지연 anchor 1회가 남았다.
이는 새 연결 순서와 별개인, 이미 받은 이벤트의 재사용 문제로 구분했다.

두 번째 문제는 뒤처진 REST 스냅샷을 현재 ID까지 진행시키는 데 필요한 증분을 이미 받았어도
활용하지 못하던 경로다. 실제 실패 자료의 원문·재생·ID 연결을 조사한 뒤, 9/26 12:38에
**같은 소켓의 최근 이벤트를 제한된 버퍼로 보존하는 정책**을 적용했다.

- 뒤처진 검증 스냅샷은 이미 받은 증분으로 현재 ID까지 정렬하고, 양쪽 상위 20호가의
  가격·수량이 정확히 일치할 때만 가격 범위를 갱신한다.
- 같은 소켓에서 범위 소진·지연 anchor로 복원 구간을 다시 시작할 때도 최근 증분을 사용한다.
  새 소켓과 계획 회전·단절 후 재접속에서는 이력을 비운다.
- 버퍼는 128개 이벤트·50,000개 가격/수량 쌍·정규화 직렬화 크기 8 MiB로 제한한다.
  필요한 증분이 없거나 ID 연결을 증명하지 못하면 후보를 채택하지 않는다.
- 과거 오류·부분 완료 판정·미재구성 수량은 유지하고, 재사용한 증분을 신규 수신 건수에 더하지 않는다.
  정책과 한도를 기록해 과거 journal은 당시 규칙으로 재생한다.

해당 배포에서 전체 테스트 256개, 과거 세션 106,725행의 호환 재생, 실패 epoch 6개
18,892행의 원문 대조와 경로별 시나리오, 별도 3분 실시간 수집을 검증했다.
지연 check 3개와 같은 소켓의 anchor 1개는 실제 확보한 자료로 정렬할 수 있었다.
반면 더 최신 스냅샷이 필요했던 급격한 범위 소진 2개는 같은 이벤트에서 계속 실패했다.
이 결과를 운영 실패율의 4/6 감소나 과거 이력 복구로 해석하지 않는다.

추가 재검토에서는 운영 복원 엔진을 정답 계산에 사용하지 않는 테스트 33개를 만들었다.
32개 고정 seed의 가상 전체 호가장에서 총 5,120개 증분을 생성해 알려진 범위 전체를 대조하고,
후보 정렬 실패 시 기존 상태가 보존되는지도 검사했다. 기존 호가 테스트 64개와 함께 통과했다.
실제 원문의 정렬 성공 4개 지점도 별도 계산으로 확인했다. 이 테스트들은 이후 전체 295개 검사에 포함된다.

**4. 백업과 파일 정리가 겹칠 때의 재시도 소진을 수정하고 실제 예약에서 확인했다.**

9/26 13:10 백업이 13:21:57까지 이어지면서 13:15 파일 정리가 유지보수 잠금에 막혔다.
기존 구현은 충돌을 실패로 처리해 120초마다 재시도했고, 네 번 실패한 뒤 시작 제한에 걸렸다.
백업이 끝난 13:23에도 시작하지 못해 그날은 정리 서비스만 수동으로 복구했다.

이후 별도 작업 사본에서 수정·시험하고 9/26 13:51에 배포했다. 두 유지보수 서비스에
`maintenance --wait-for-lock`을 적용해 후발 작업이 같은 프로세스에서 OS 잠금을 기다리게 했다.
대기 중에는 수집용 writer·파일 배치 잠금이나 DB 트랜잭션을 잡지 않고 기존 완료 보고서를 유지한다.
잠금을 얻은 뒤 요청 시각·작업 시작 시각·대기 시간을 새 보고서에 남긴다.

검증·디스크 오류나 시간 초과는 계속 실패로 처리한다. 기존 6시간 서비스 제한은 대기와 작업을
합한 시간에 적용하고 SIGINT로 대기를 중단할 수 있다. 옵션 없는 수동 CLI의 즉시 충돌 오류와
타이머 시각·실패 재시도 정책은 유지했다. 단독 CLI의 잠금 대기에는 자체 시간 제한이 없다.

전체 테스트 **295개가 실패·건너뜀 없이 통과**했다. 실제 CLI 프로세스로 수집 쓰기 병행,
기존 보고서 보존, 잠금 해제 뒤 묶음·백업 실행, 취소·오류 전파를 검사했다. 격리한 사용자
systemd 유닛에서도 기존 시작 제한 재현, 수정된 hourly·daily 대기, 대기 중 시간 초과를 검증했다.
검증한 코드와 유닛을 적용하는 동안 체결·호가 수집기는 재시작하지 않았다.
