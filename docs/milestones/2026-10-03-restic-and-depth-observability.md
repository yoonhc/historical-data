# restic 병행 운영과 호가 수집·관측 보강 — 2026-10-03

9월 27일 정리 이후 restic의 저장량·복원 시험을 마치고 기존 daily 백업에 추가하는 병행
보관을 운영에 적용했다. 서로 다른 날짜의 예약 저장·검사 3회와 새 운영 사본의 복원 검증을
확인했다. 호가는 실제 실패 원문을 분석해 지연 스냅샷 재시도와 조기 갱신을 보강했고,
남은 실패를 구분할 네트워크 관측과 조회 보류 사유 기록을 추가했다.

이 문서는 [9/27 마일스톤](2026-09-27-collection-and-backup-stabilization.md)을 기록한
`7291ca8` 이후 **`bb54bf9`부터 `d783ec1`까지 9개 커밋**을 정리한다. 마지막 제품 변경은
`d783ec1`이며, 최신 수집 상태의 근거는 **10/3 11:23 KST에 고정한 표본**까지다.
시각은 별도 표기가 없으면 KST, GB는 10진수다. 커밋 날짜와 실제 적용·관찰 날짜는 구분한다.

작업 범위는 데이터 수집·보관·검증이다. 수집 코어는 Freqtrade와 독립적이며 전략 연구나
소비자 어댑터를 확장하지 않았다. 이번 문서 작성은 기존 증거를 종합한 것으로, 전체 테스트,
호가 원문 감사, 백업·복원 시험이나 이후 예약 결과 점검을 새로 실행한 것이 아니다.

**지난 기준과 달라진 점**은 다음과 같다.

**1. restic을 현재 하드링크 백업과 비교하고 다른 경로의 복원을 검증했다.**

9/26·9/27의 같은 두 복구 지점을 독립된 restic 시험 저장소에 보관했다. 비교 기준은
현재 하드링크 사본이며, 하드링크로 공유하는 파일의 할당량을 중복 계산하지 않았다.

| 파일시스템 실제 할당량 | 기존 하드링크 사본 | restic 저장소 |
|---|---:|---:|
| 첫 복구 지점 | 8.921 GB | 6.055 GB |
| 두 번째 복구 지점 추가분 | 2.543 GB | 1.097 GB |
| 두 복구 지점 합계 | 11.463 GB | 7.152 GB |

합계 차이는 **4,311,793,664바이트, 37.61%**다. 내용 기반 중복 제거·압축·저장 형식의
파일시스템 비용을 함께 반영한 값이며, 카탈로그만의 절감률이나 장기 평균 증가량은 아니다.
기존 사본을 유지하고 시험용 추출·복원·재백업 공간도 추가했으므로 실제 디스크에서 이만큼
공간이 비워졌다는 의미는 아니다. restic 명령 시간에는 기존 daily의 전체 검증·사본 준비
시간이 포함되지 않으므로 두 작업의 전체 소요 시간을 직접 비교하지 않았다.

두 날짜 모두 **restic 추출 → 원래 사본 검증 → 프로그램으로 별도 저장소 복원 → 무결성·조회
대조 → 새 전용 폴더의 독립 백업 생성·검증**을 통과했다. 원래 manifest·backup ID·
`source_root`를 수정하지 않았고, 새 백업에만 실제 복원된 저장소의 출처가 기록됐다.

복원본 전체 무결성은 각각 269,310건·353,674건 통과했다. 날짜별로 스냅샷 20개와
표본 조회 107개·109,497행을 대조했고, 체결·호가·원문 표본과 사본 사이 inode 독립성도
확인했다. 조회 표본의 일치는 모든 기간의 가능한 조회를 검사했다는 뜻이 아니다.
기존 OI 격리·호가 공백과 실패 판정은 복원본에서도 유지했다.

restic 0.19.1을 고정 버전·체크섬으로 설치하고 호스트 경로·필수 마운트·암호 파일 경로를
Git 밖 프로필로 분리했다. 암호 값은 출력·문서·Git에 넣지 않았다. 관련 테스트 41개와
실제 작은 restic 저장소의 복원·재백업도 통과했다. 이는 Proxmox VM 이전에 필요한 설정
분리와 다른 경로 복원의 준비이며, VM 이전 자체를 수행한 것은 아니다.

**2. 기존 daily와 restic 보관을 분리하고 실제 예약 관찰을 완료했다.**

기존 daily는 매일 13:10에 원본 저장소 전체를 검증하고 일관된 하드링크 사본을 완성한다.
별도 restic 작업은 **완료된 사본만 검증해 추가 보관**한다. 매시 05분·35분의 탐색은 새 사본을
찾는 주기이며 30분마다 새로운 데이터 복구 지점을 만드는 주기가 아니다. restic 단계만
실패하면 해당 단계의 상태를 확인해 재시도하며 기존 daily 전체를 다시 실행하지 않는다.

저장 성공·restic 저장소 전체 읽기 검사·실제 복원 검증은 각각 기록한다. 저장소 검사 실패는
저장 사실을 지우지 않고 후속 저장을 차단하며, 저장 직후 처리 기록이 유실된 경우 실제 추출·
검증 후에만 기존 snapshot을 채택한다. 종료 코드 3의 불완전 사본, manifest만 있는 후보,
상태 분실·기존 snapshot 유실도 격리 시험에서 구분했다.

snapshot의 `time`에는 검증된 manifest의 `checkpoint_finished_at`을 UTC로 반영한다.
실제 보관 시작·완료 시각은 따로 기록하므로 지연된 여러 날짜의 사본을 하루에 넣어도 원래
복구 날짜가 유지된다. 안정된 선택 범위인 `archive_scope`와 개별 backup/attempt 태그를
구분했다. 상대 경로 `.`로 백업해도 snapshot에 원본 절대 경로가 남으며, parent 지정이
향후 보관 그룹까지 정하는 것은 아니다. 정리를 도입할 때는 날짜별 입력 경로나 개별 태그마다
그룹이 쪼개지지 않도록 선택 범위와 그룹 기준을 별도로 정해야 한다. 삭제·forget/prune 경로는
구현하지 않았다.

운영 저장소는 `/mnt/backup/marketdata-restic`이다. 실행마다 필수 마운트·파일시스템 UUID·
restic 저장소 ID를 검사한다. 설치 전 유닛 구문, 실행 사용자·Python/restic 경로, 프로필·
암호 접근과 `Linger=yes`를 확인했다. 호스트별 서비스 환경도 분리했으며 수집을 중단하는
재부팅·로그아웃 시험은 수행하지 않았다.

9/28에는 저장·전체 검사가 성공했는데도 예약 집계가 진행되지 않는 문제를 발견했다.
이 호스트의 systemd가 최초 실행의 `TRIGGER_TIMER_*` 환경변수를 재사용했기 때문이다.
현재 PID·invocation·실행 중인 start Job의 `ActivationDetails`와 타이머 시각을 대조하도록
수정하고 반복 예약·수동 실행으로 검증했다. 당시 Job 증거가 없는 9/28 결과를 시각만으로
소급 집계하지 않았으며 수동 실행·처리 0개·같은 날짜의 반복도 제외했다.

| 새 checkpoint 날짜 | 실제 새 사본 저장·검사 예약 | 날짜별 관찰 |
|---|---|---|
| 9/29 | 13:35 예약, 저장·`check --read-data` 성공 | 1/3 |
| 9/30 | 14:05 예약, 저장·`check --read-data` 성공 | 2/3 |
| 10/1 | 14:05 예약, 저장·`check --read-data` 성공 | 3/3 |

복원은 관찰 시작 뒤 생성된 **9/28 운영 snapshot을 전체 ID로 명시해 수동 1회** 수행했다.
추출부터 프로그램 복원·조회·독립 재백업까지 통과했고, 35,795개 파일과 복원본 전체 무결성
438,481건을 확인했다. 원래 출처 검사를 유지했고 새 백업 폴더도 복원본 전용으로 만들었다.
이 복원 결과를 이후 날짜마다 새 시험으로 중복 계산하지 않았다.

따라서 **새 날짜의 예약 성공 3/3과 새 운영 사본 복원이라는 첫 관찰 기준은 완료**다.
9/28 사본의 저장·복원 성공과 날짜 집계 제외는 서로 다른 판정이다. 10/2 daily와 해당 사본의
restic 저장·전체 검사 성공도 10/3 점검에서 기존 기록으로 확인했지만 첫 3/3 집계와 구분한다.

daily 무결성 검사는 신규 자료뿐 아니라 과거 자료를 포함한 전체 저장소의 논리 항목을 다룬다.
10/1의 692,746건은 시장 데이터 행 수가 아니며 검증 단계는 약 25분 32초였다.
restic의 `check --read-data`도 기존 snapshot의 데이터를 포함한 저장소 전체 읽기 검사다.
처리 0개의 탐색이나 상태 조회를 새 백업·새 전체 검사 성공으로 기록하지 않는다.

**3. 미재구성 증분의 원인을 확인하고 지연 스냅샷 재시도를 보강했다.**

9/28·9/29의 미재구성 101개·102개와 범위 소진을 원문으로 조사했다. 문제 세션 3개의
106,741행·가격 수량 쌍 20,626,748개가 표준 자료와 일치했고 재생도 기존 실패 판정과 같았다.
미재구성은 저장하지 못한 증분이 아니라, 저장했지만 유효한 기준 호가장에 연결하지 못한
구간이다. 새 소켓의 첫 증분보다 REST anchor가 뒤처져 필요한 연결 증분 자체가 없었다.
기존 10초 재시도 대기는 이후 미재구성 상태가 약 10.36초 이어지는 데 영향을 줬다.

같은 소켓의 최근 증분으로 뒤처진 복구 anchor를 정렬하는 기존 보강도 실제 두 사례에서
독립 계산으로 확인했다. 이 경로는 이미 받은 증분을 활용하며, 새 소켓에서 받지 못한 연결
증분까지 만들어낼 수는 없다. 초기 연결 실패와 재시도까지의 대기를 구분해 수정했다.

새 정책은 최초 **1초**, 연속 실패 시 **2·4·8·10초**, 이후 최대 10초를 기다린다.
같은 소켓에서 증분 수신·저장을 계속하며 추가 재시도는 수집 세션의 최근 60초에 최대
8회다. epoch·연결 교체에도 rolling 예산을 유지하고, flush 후 종료·회전 시각을 다시 확인한다.
기존 429/418 대기와 ID 연결 규칙·실패 epoch·`partial` 판정은 유지한다.

9/29 19:29 소스 반영 뒤 **19:53:47 정기 프로세스 교체**로 실제 적용됐다. 호가 관련
113개 검사, 전체 383개 고유 검사 항목의 최종 통과 근거와 3분 실시간 표본을 확보했다.
전체 시험 첫 실행의 1개 환경 오류는 격리 디렉터리의 Git 정보 조회 문제였으며 해당 검사만
환경을 맞춰 재실행했다. 최초 실패와 재실행 기록을 모두 보존했다.

첫 24시간 선택 구간의 24개 세션은 모두 complete였고 증분 845,439개 수신·저장과 REST
8,407회 일치를 확인했다. 종료 직전 REST 후보 1개는 후속 증분이 없어 검증 대기로 남겼다.
집계는 보고서·카탈로그를 대조했으며, 전체 원문 검사는 선택한 2개 세션 71,154행과 대기
사례의 말미 표본에서 수행했다. 24개 세션의 모든 원문 가격·수량을 다시 계산한 것은 아니다.
이 기간에는 지연 재시도가 발생하지 않았으므로 재시도 효과까지 입증한 것으로 세지 않았다.

이후 9/30 21:31·21:46의 실제 지연 사례에서 재시도 대기는 1.068초·1.057초였고,
첫 증분부터 재동기화까지 약 1.208초·1.212초였다. 미재구성 증분은 각각 12개로 보존했다.
정책이 실제 동작한 증거지만, 이전 101·102개 사례와 시장·응답 조건이 달라 통계적인 개선율을
계산하지 않는다. 같은 후속 점검에서 가격 범위 소진 5회도 발견해 별도 개선 대상으로 남겼다.

**4. 가격 범위의 조기 갱신을 적용하고 남은 실패를 24시간 자료로 확인했다.**

실제 범위 소진 사례 중에는 정상 snapshot 채택 후 5초 전에 알려진 한쪽 호가가 모두 사라진
경우가 있었다. 같은 ID까지 정렬했어도 로컬 매도 호가가 15개뿐이라 top 20을 대조할 수 없던
사례도 확인했다. 기존 최소 5초 간격과 갱신 조건·상위 호가 부족 처리를 함께 보강했다.

- 한쪽 호가 개수가 기준 snapshot의 75% 미만이거나, 알려진 가격 경계까지의 여유가 기준
  가격 폭의 25% 미만이면 정기 검증 전에도 조회한다.
- 직전 snapshot **처리 완료 후 최소 1초**를 지킨다. 조기 요청은 한 수집의 최근 60초에
  최대 12회이며 epoch·연결 교체에도 유지한다. 정기 검증·복구 anchor·지연 재시도 계수와
  별개다. IP 전체나 여러 프로세스를 합친 공통 요청 상한은 구현하지 않았다.
- 기존 REST 후보의 동일 ID 대조가 진행 중이면 추가 검증을 요청하지 않는다. 요청 전
  flush 이후에도 종료·회전 시각과 요청 가능 여부를 다시 확인한다.
- top 20이 부족하면 부족 상태를 남기고 같은 소켓의 새 epoch에서 anchor를 받는다.
  양쪽 top의 가격·수량이 같은 ID에서 일치할 때만 snapshot을 채택한다.

전체 테스트 411개와 별도 실시간 증분 1,741개·REST 대조 16회·원문 대조가 통과했다.
과거 실패 세션 106,756행을 새 코드로 재생해 기존 partial을 유지했다. 소스는 10/2 07:20에
설치하고 **08:09:37 정기 교체**에서 실제 적용을 확인했다. 수집기를 강제로 재시작하지 않았다.

첫 적용부터 24시간 안에 시작한 24개 세션을 종료까지 확인했다. 실제 자료 범위는
**10/2 08:09:37–10/3 08:16:22**로, 정확한 24시간 경계 뒤의 마지막 세션 끝도 포함한다.

범위 부족**이 함께 있었다. 예산 소진은 당시 요청·응답 시각과 정책으로 추론한 결과이며,

snapshot의 거래 시각과 로컬 응답 시각의 차이만으로 거래소·네트워크·로컬 중 원인을 단정하지 않았다.

만들지 않았다. 미재구성 31개 역시 모든 품질 공백을 대표하는 숫자는 아니다.

미수집 호가는 계속 남고, 서로 다른 관찰 날짜의 결과를 같은 조건의 전후 성능 비교로 쓰지 않는다.

**5. 긴급용 예산 예약은 보류하고 판단 사유의 기록만 먼저 적용했다.**

12회 중 2회·4회를 긴급 갱신용으로 남기는 후보를 별도 작업 사본에서 구현했다. 기존 정책,
기록 추가·예약 0회, 예약 2회, 예약 4회를 독립적인 전체 시장 정답을 가진 11개 가상 조건에서
비교했다. 44회 수집과 후보 전체 테스트 428개를 통과했고, 유리한 사례와 악화 반례를 함께 보존했다.

반복 움직임으로 예산을 사용한 뒤 급변하는 조건에서는 예약이 도움이 됐다. 반면 일반 갱신을
막은 탓에 기존 정책은 처리한 구간에서 후보가 실패하기도 했다. 한 반례는 가상 시각 18.0초의
조회가 긴급 신호인 18.1초까지 늦어지고, REST 응답을 기다리는 사이 범위가 소진됐다.
응답 자체가 더 느려진 것이 아니라 **요청 시작을 늦추는 비용**이었다. 가상 조건의 결과를
실제 시장의 발생 확률이나 과거 장애 예방 건수로 해석하지 않는다.

예약 방식은 폐기하지 않고 후보로 보존했다. 운영에는 예약·긴급 우선순위 API를 제외한
**기록 전용 구현**을 적용했다. 기존 조회 기준·최소 간격·추가 12회 상한과 정기 검증 10초는 같다.

| 직접 기록하는 보류 사유 | 의미 |
|---|---|
| `minimum_interval` | 직전 snapshot 처리 완료 후 1초가 지나지 않음 |
| `extra_budget` | 최근 60초 추가 조회 12회를 사용함 |
| `pending_verification` | 이전 REST 후보의 동일 ID 대조를 기다림 |
| `not_synchronized` | 현재 호가장의 ID 동기화가 성립하지 않음 |
| `deadline` | 종료 또는 계획된 연결 교체 시각에 도달함 |

사유별 최초·마지막 표본과 최근 보류 8개를 유지하고, 실제 요청의 사유·여유·예산 전후를
REST 원문 메타데이터에 보존한다. 범위 실패 경계에는 당시 집계의 독립 사본을 남긴다.
평가 한 번에 겹친 사유를 모두 기록하되 대표 사유는 한 번만 센다. **보류 평가 수는 HTTP 요청
수나 장애 수가 아니며**, 조회가 필요하지 않은 평상시 평가는 보류에서 제외한다.
모든 보류를 개별 파일로 남기는 방식은 아니고 마지막 보고서 저장 이후의 집계는 강제 종료 시
남지 않을 수 있다. 지연 anchor 재시도는 별도 경로다.

기록 전용 구현은 전체 **422개 테스트**와 **11개 조건·22회 수집 비교**를 통과했다.
기존 정책과 요청 시작·완료 시각, 저장량·복구 횟수·대조·판정이 같았다. 앞선 428개는
예약 후보 전용 검사를 포함한 별도 구현의 수치이며, 운영의 422개는 기존 411개와 기록 전용
11개다. 실제 직렬화·CPU 비용도 가상 수집에서 측정했지만 운영 부하 증가율을 확정하지 않았다.

10/3 11:10:13 설치 후 **11:17:30 자연 교체로 적용**됐다. 11:18 표본의 증분 501개 저장과
REST 4회 일치, 요청 문맥 5개 저장을 확인했다. 그 요청 5개는 원문 SHA-256과 표준 snapshot의
가격 수량 쌍 10,000개도 대조했다. 두 표본의 조회 시점이 달라 요청 5개를 모두 REST 대조 완료로
센 것은 아니다. 11:23 표본까지 3,551개 증분이 저장됐고 연결 오류·동기화 손실·보류 평가는 0이었다.

새 기록의 **실제 보류 발생 표본, 첫 종료 세션 전체 검사와 24시간 운영 관찰은 아직 검증하지
않았다**. 이후에는 보류 횟수와 실제 범위 소진 여부·요청 및 처리 시간을 함께 보고 예약 방식,
갱신 기준·간격 또는 복구 흐름 중 어떤 변경이 필요한지 판단한다.

**6. 통신 공백과 자료 공개 지연을 구분하고 네트워크 관측을 추가했다.**

10/1 15:47 이후 호가·aggTrade 양쪽에 timeout·이름 해석 오류가 기록됐고 NetworkManager의
외부 연결 상태 변화도 있었다. 유선 LAN 사용을 확인했지만 확인 가능한 로그에서 carrier
단절은 찾지 못했다. 공유기·ISP·PC 중 최초 원인은 확정하지 않았다.

호가에는 약 231.790초·247.182초의 애플리케이션 수신 간격이 남았다. 이 시간 전체를 물리적
인터넷 단절 시간으로 단정하지 않고 서로 다른 연결 사이 호가 공백도 복구 완료로 표시하지 않았다.
aggTrade는 기존 자동 REST 보충으로 **4,218행**을 가져왔으며 원문·표준 대응을 확인했다.
15:40–16:30의 합친 저장 자료 51,964개 ID가 연속이고 OI REST의 15:00–17:00 라벨 24개도
완전했다. 사후 보강된 저장 자료의 연속성과 당시 실시간 무중단 수신은 구분한다.

10/2에는 별도 `marketdata-network-observer.timer`를 적용했다. 매분 20초에 유선 경로·링크,
gateway, 외부 숫자 IP, REST·스트림 이름 해석과 HTTPS 도달성을 기록한다. 호스트별 설정을
분리했고 수집기·카탈로그·DNS 설정을 바꾸거나 외부 알림을 보내지 않는다.
기록 생성 성공과 각 probe의 네트워크 정상 여부도 구분한다.

조기 갱신의 첫 24시간 범위에서 실제 네트워크 표본 1,440개는 모두 정상이었다. 이는 10/1
장애의 원인을 소급 확정하거나 1분 사이의 짧은 장애·WebSocket 수신 실패를 배제하는 결과는 아니다.

일치했고 연결 오류·미복구 공백은 0이었다. 이 구간의 체결 원문·ID 전체를 새로 감사하지는 않았다.

9/29 UTC 선물 거래봉·mark·index·OI archive가 `waiting_source`였고, 10/1 정오 자동 갱신 뒤
4종 4,608행의 실제 조회·격자·파일 체크섬을 확인했다. 이어진 9/30 UTC 자료 대기는 10/1
당시의 기록이며 이번 문서에서 현재 원격 공개 여부·수집 완료를 다시 확인하지 않았다.
오후 공개에 대응하는 추가 재탐색은 아직 구현하지 않았다.

보류 기록 적용 세션의 첫 전체 검사는 **10/3 12:25 이후** 가능한 후속 항목으로 남긴다.
새 기록의 정확한 24시간 경계는 **10/4 11:17:30**이며, 그 선택 구간에 속한 마지막 세션의
종료까지 고려해 **10/4 11:30 이후** 확인하는 것이 적절하다. 예정 시각이 지났다는 이유만으로
검증 완료로 간주하지 않고 실제 실행·종료·원문 검사 기록으로 갱신한다.

원본·revision의 기간 제한 없는 보존과 날짜별 백업 복구 지점의 보관 정책은 별개다.
1·2단계에서 기존 백업·시험 사본을 삭제하지 않았으며, 최종 보관 기간이나 모든 날짜의
영구 보존을 확정하지 않았다. restic 병행 성공을 기존 daily 대체·중복 사본 정리·전체 디스크
공간 절감 전환 완료로 해석하지 않는다. 백업은 같은 PC의 두 번째 SSD이므로 별도 장비의
사본이나 암호의 별도 복구 사본 준비는 VM 이전과 함께 다룰 후속 항목이다.

2019년 이후 확보 범위는 이전 마일스톤의 결과다. Freqtrade 대상은 기존
