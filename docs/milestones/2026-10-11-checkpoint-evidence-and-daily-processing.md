## T05 정책과 완료 근거

[최종 설계](../t05-checkpoint-clock-safety-design.md)는 기존 정리기의 잠금·승인·restic 검증을 유지하면서
현재 관측의 보수적 하한과 checkpoint 완료 상한을 연결한다.

- 유효한 관측의 총 불확실성 **U ≤ 5초**와 **하한−완료 상한 ≥ 72시간+60초**를 따로 요구한다.
  기존 수집용 100ms·500ms·100ppm 개별 차단을 T05에 그대로 적용하지 않는다.
- reference age는 원값으로 기록하며 T05의 stale/600초 차단으로 쓰지 않는다.
  조회 3초·관측 수명 15초·기존 감시/불연속/provider 확인은 유지한다.
- 실제 완료 표시를 내구성 있게 저장한 뒤 새 관측을 얻는다. 근거 확보 실패는 정상 데이터 백업 성공과 분리하며,
  원래 `completed_at`·manifest를 고치지 않고 최초 유효 사후 상한을 재사용할 수 있다.
- 기존 완료 집합과 새 생성의 선후관계를 기록한다. 확실히 후행인 검증 사본 3개를 최종 유지 목록에 남긴다.
- 필요한 기존 목록·선행 근거를 sidecar에 보존해 로컬 사본과 원래 control state가 없어도 명시적 restic 지점에서 재구성한다.

추가 60초는 더 기다리는 운영 여유다. 250ms 미만 이동의 정밀 모델은 추가하지 않았고,
U나 60초가 모든 미검출 시각 변화를 보장한다고 표현하지 않는다.
완료 근거 생성, 삭제 없는 미리보기, 한 계획의 실제 삭제, 반복 자동화 승인은 서로 다른 단계다.

[이전 후보](../../reports/baseline/t05-clock-retirement-2026-10-11/summary.md)는 108개 검사와 39개 재현을 통과했다.
11:59 시스템 접근은 통과했지만 `daily_not_today`로 후보 산정 전 보류된 결과를 그대로 보존했다.
[최종 후보](../../reports/baseline/t05-completion-evidence-2026-10-11/summary.md)는
`t05-completion-evidence-20261011-c9d413cfe11ec0e7`, 고정 소스 151개·변경 18개다.
관련 전체 실행은 214개 통과·export 환경을 가정하지 못한 구형 검사 1개 실패였고,
검사 보완 후 그 1개 통과를 연결해 215개 최종 통과로 기록한다. 별도 58개 재현은 합산하지 않는다.
시험 저장소의 오래된 사본 2개 제거·control state 분리 후 근거 복원과 구형 backup/restore 호환도 확인했다.

## T05 실제 설치와 중단·재개

[15:50 관리자 미리보기](../../reports/baseline/t05-completion-evidence-2026-10-11/operating-preview.md)는
현존 관리 사본 7개 모두 보호·후보 0개였다. 당시 새 근거가 없어서 보호한 결과이며 삭제·등록은 없었다.
첫 실행의 namespace UID 표시 차이를 기준 수집 오류로 구분하고 실제 호스트 대조로 보완했다.
후보나 보호 설정을 낮추지 않았다.

[승인한 운영 설치](../../reports/baseline/t05-evidence-deploy-2026-10-11/status.md)는 16:21에
고정 `/opt` 실행본·설정·비활성 시스템 정리 환경과 기존 7개 사본의 사후 근거 등록을 마쳤다.
첫 사용자 명령 전환은 systemd 의존성 구성원의 출력 순서를 변화로 오판해 중단·원복됐다.
구성원 비교 보완의 회귀 5개+기존 전환 11개를 통과한 뒤 17:22:52 재개, 17:24 실효 명령/보존 상태를 확인했다.
원래 실패·입력·보완 코드 해시·실제 receipt와 [현재 원복 절차](../../reports/baseline/t05-evidence-deploy-2026-10-11/recovery.md)를 함께 보존한다.

backup/restic 두 업무는 여전히 **사용자 manager**이며 고정 wrapper로 `ExecStart`만 전환했다.
사용자·시스템 자동 정리 service/timer 네 곳은 masked, manual/recurring 승인도 비활성이다.
운영 checkpoint 삭제·추가 백업 요청·시각 변경은 수행하지 않았다.
기존 7개 상한은 10/11 16:21:02.643–.730 KST다. 기간만 보아도 현재 관측 하한이
10/14 16:22:02.643–.730 이후여야 하며, 그때도 후행 사본·근거 보존·당일 완료·별도 승인 조건이 필요하다.

## T04 복원 시험 공간 정리

`t04-clock-evidence-20261010-f71c5b20490248b4b229a66f3378ab10` 부모와 그 하위 두 시험 사본만 대상으로 했다.
첫 시도는 기존 restic 잠금 때문에 삭제 0개로 중단됐다. 해당 작업의 정상 종료로 바뀐 상태 해시만 대조한 뒤 재개했다.
17:59:19에 파일 114,849개·디렉터리 92,431개를 삭제했고 journal 의도/완료 1,620쌍·미완료 0개를 대조했다.

원래 checkpoint·restic 16개 지점의 메타데이터·복구 키트·T05 registry·수집/Chrony와 검증 기록은 유지했다.
최종 목록·journal·추출 manifest/restore 기록을 Git에도 압축 보존했다. 이전 T06 삭제 승인을 재사용하지 않았다.

## T13 실제 자료 처리와 백업

[18:20 점검](../../reports/baseline/t13-operating-review-2026-10-11/summary.md)에서 UTC 날짜 전환 후
기존 예정 20개를 유지하고 새 10/10 UTC acquire/refresh 12개를 추가했으며 예정 전 요청은 없었다.
정오 12:21에 10건, 저녁 18:00에 16건을 처리했다. 시도 26개·기록된 HTTP 응답 50개는 모두 성공했다.
새 acquire 6개가 같은 대상의 refresh도 충족해 중복 요청하지 않았고, 정오 완료를 저녁 재시도로 반복하지 않았다.
원문과 Parquet 26개·24,206행, query/source/revision·해시·날짜 격자를 대조했다.
OI의 원문 역순 경고는 그대로 보존하며 표준 자료의 정렬과 구분했다.

10/11 checkpoint `9849b0ef7e523cbc79546c233f409ecd93cdcc8e1b5bc4f48fe8163229968a77`은
카탈로그 기준 14:31:51–56 KST, 완료 표시 14:38:07이며 정오 시도 10개와 10/9 UTC 보강 네 종류를 포함한다.
같은 사본의 restic `fd78b31add535359af3e2e6f77d13fede7db632308bf0bad2688d4a78b14324a`는
15:28:59 저장, 15:30:19 전체 읽기 검사를 마쳤다. 저녁 16개 시도는 이 지점에 없으며 독립 복원도 아직이다.

정오 시작의 약 67초 지연과 18:05 재평가 대기는 기존 공통 waiter의 reference_age 조건이었다.
이미 완료한 자료를 실패로 바꾸거나 scheduler 내부 waiting_source와 혼동하지 않는다.
업무별 시각 요구 분리의 후속 근거로 남기고 T13 검증 중 정책을 바꾸지 않았다.

1. **T13:** [고정 완료 계획과 ID](../../reports/baseline/t13-operating-review-2026-10-11/completion-plan.md)에 따라

   10/12 정기 백업 실제 완료 후 고정 시도 26개·근거·자료를 포함한 backup/snapshot ID·전체 검사 receipt를 연결하고
