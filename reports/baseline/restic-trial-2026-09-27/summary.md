## 실제 저장량

GB는 10억 바이트다. 파일시스템 할당량은 디렉터리·manifest를 포함한
`st_blocks * 512`이며 같은 `(device, inode)`를 한 번만 센다.
따라서 하드링크 공유분을 사본마다 중복 계산하지 않았다.

| 범위 | 현재 하드링크 사본 | restic 저장소 |
|---|---:|---:|
| 첫 복구 지점 | 8.921 GB | 6.055 GB |
| 두 번째 지점 추가분 | 2.543 GB | 1.097 GB |
| 두 복구 지점 합계 | 11.463 GB | 7.152 GB |

합계 **4,311,793,664바이트, 37.61% 감소**다. 첫 restic 저장소는 6,054,653,952바이트,
두 사본 저장 후 7,151,616,000바이트였다. 두 번째 사본 추가분은 1,096,962,048바이트다.
하드링크 방식의 동일한 추가분은 2,542,686,208바이트였다.

이는 `compression=auto`·내용 기반 중복 제거와 저장 형식에 따른 파일시스템 오버헤드 차이를
포함한 결과다. SQLite 카탈로그만의 절감률이나 압축을 제외한 중복 제거율로 해석하지 않는다.
현재 두 날짜의 결과이며 장기간
평균 증가량을 확정하지 않는다. 기존 백업을 유지하므로 시험 중 전체 디스크 사용량은 증가한다.
별도 작업 공간은 캐시 포함 **59.053 GB**다. 이 중 캐시는 20,127,744바이트이며,
나머지는 두 날짜의 추출본·복원본·새 독립 백업 6개다. 로컬 실행 보고서는 16,093,184바이트다.
작업 공간은 위 저장소 비교 표에 포함하지 않았다. 서로 독립적인 복원·재백업을 검증한 뒤
증거와 사본을 남겼으므로 실제 디스크에서 4.31 GB가 비워졌다는 뜻은 아니다.

| restic 단계 | 벽시계 시간 | 최대 RSS |

| 9/27 추출·검증 | 25.83초 | 212,132 KiB |

위 시간은 **완료된 checkpoint에서 실행한 restic 명령 자체**다. 기존 daily 작업의
전체 데이터 검증과 일관된 checkpoint 생성, 이 시험 스크립트의 입력 사전 검사는 제외한다.
daily 전체 소요 시간과 비교해 수백 배 빨라졌다고 주장할 수 없다. RSS도 해당 restic
자식 프로세스 값이며 Python 검증 작업 전체의 최대 메모리가 아니다.

9/26은 프로그램 복원 117.96초, 조회 대조 38.35초, 전체 무결성 검사 555.97초,
새 독립 백업 생성 98.85초, 새 사본 검증 37.10초였다. restic 추출부터 마지막 inode 확인까지
15분 15초가량 걸렸다. 첫 복원 검증은 UTC 06:45:03에 끝났고, 두 번째 추출은
UTC 07:23:45에 시작하여 두 실제 복원 구간은 겹치지 않았다.
9/27은 프로그램 복원 139.51초, 조회 대조 43.77초, 전체 무결성 검사 782.26초,
새 독립 백업 생성 118.83초, 새 사본 검증 50.69초였다. 마지막 inode 확인까지
UTC 07:44:04에 완료하여 추출 시작부터 약 20분 19초 걸렸다.

실행 우선순위는 `nice +10`, `ionice` best-effort 7이다. restic의 Go 실행 스레드와
읽기 동시성은 2이며 강제 CPU·I/O 상한은 아니다. 실행 단계 중 약 10초 간격으로
운영 SQLite의 WAL까지 읽어 aggTrade·호가 수신 시각과 오류를 관측한다.
입력 사전 검사와 단계 사이 시간은 관측에서 빠지므로 전체 경과 시간과 관측 시간을 혼동하지 않는다.

UTC 06:13:26–07:43:56 사이 실행 단계에서 **222개 표본**을 기록했다. 샘플링 오류와
수집 오류 기록은 없었고, aggTrade의 미복구 누락·순서 역전, 호가의 동기화 손실·미복원
메시지·뒤처진 스냅샷 카운터는 관측 표본에서 모두 0이었다. 최대 마지막 수신 경과 시간은
aggTrade 20.43초, 호가 16.72초로, 완료된 세션에서 다음 세션으로 넘어가는 대기 표본을 포함한다.
`running` 표본만으로 무중단을 주장하지 않는다.

호가 신규 세션 초기 보고서에 `state`·`last_received_at`이 없던 표본 1개는 `unreported`로
그대로 보존했다. 이어진 표본에서는 수신·동기화 상태가 정상으로 기록됐다. 집계가 이
미보고 값을 정렬하다 실패하지 않도록 처리했고 실제 restic 통합 검사에도 이 경우를 추가했다.
종료 시점의 운영 카탈로그에서 이 기간과 겹친 6개 세션의 보고서를 별도로 보존했다.
이 관측은 전 시간대의 모든 체결 ID·호가 재생을 감사한 결과는 아니다.

## 안전 검사와 이전 준비

관련 테스트 **41개 통과, 건너뜀 0개**. 실제 restic을 사용하는 작은 사본 두 개의
전체 복원·재백업 테스트도 포함한다. 경로 겹침·심볼릭 링크·필수 마운트 누락·
위험한 암호 경로는 쓰기 전에 거부한다. 하드링크 할당량 중복 계산 방지도 검사한다.

다른 source root의 자동 백업 폴더는 **당일 사본과 전날 사본 양쪽에서 거부**했다.
복원본에 새 전용 폴더를 지정하면 첫 독립 백업이 정상적으로 생성된다. 이 부정 검사는
격리된 fixture에서만 수행했다. 기존 운영 source-root 검사를 바꾸거나 약화하지 않았다.
원래 저장소와 사본 폴더를 다른 이름으로 옮긴 뒤에도 추출 사본에서 복원·조회할 수 있음을
작은 실제 restic 통합 검사로 확인했다.

호스트 설정은 `~/.config/marketdata/backup-host.toml`, 암호 파일은
`~/.config/marketdata/secrets/restic-password`에 `0600` 권한으로 분리했다.
Git에는 [예시 설정](../../../configs/backup-host.example.toml)만 넣는다. 실제 암호 값은
출력·보고서·Git에 넣지 않았다. 운영 전환이나 VM 이전 전에는 암호의 별도 복구 사본도 준비한다.

restic 0.19.1은 `.cache/restic/0.19.1/restic`에 설치했다. 공식 HTTPS 릴리스와 고정 SHA-256,
공식 체크섬 파일을 확인했으며 GPG 서명 검증은 수행하지 않았다.
[설치 도구](../../../scripts/install_restic.py), [시험 도구](../../../scripts/restic_trial.py),
[집계 도구](../../../scripts/summarize_restic_trial.py), [절차·VM 이전 안내](../../../docs/restic-trial.md).

이 시험은 운영 교체의 근거다. 매일 restic을 실행하는 예약·보관 기간·정리 기능을 적용한 것은
아니며, 같은 PC의 두 번째 SSD라는 장애 범위도 유지된다. 다음 단계는 일관된 checkpoint
준비 비용까지 포함한 운영 연결과 실패 처리·마운트 의존성을 검토하는 것이다.
