# 호가 보류 기록의 첫 종료 세션 검증

2026-10-03 **11:17:30–12:17:32 KST**의 첫 운영 세션을 고정해 재생·원문 대조를 마쳤다.
저장된 호가와 운영 당시 판정이 일치했고, 실제 보류 1회의 사유와 해소 과정도 확인했다.
검사는 **13:12:41 KST**에 끝났다. 새 기록의 24시간 품질 판정은 아직 하지 않았다.

대상은 [적용 기록](../depth-decisions-2026-10-03/activation.json)의 첫 collection
`6d39cd17a2604b97a53e2932ac829e19`다. 다른 정상 세션으로 대체하지 않았다.
운영 코드·요청 정책·서비스 설정은 바꾸지 않았고, 새로운 거래소 요청이나 수집 재시작도
하지 않았다. 카탈로그는 live WAL을 반영하는 `mode=ro`로 열고 기존 파일 읽기 잠금을 사용했다.

물리 연결은 4개였고, 연결 내부의 연속 증분 ID 연결 35,225개가 모두 맞았다. 3번의 정기 연결
교체 전후 수신 간격은 각각 2.243559·2.244381·2.244678초다. 연결 사이 호가를 복원하지
않으므로 재생 결과의 `continuous`는 **false**로 유지한다. 전체 증분 수신 간격의 최댓값은
5.409975초이며, 애플리케이션의 수신 처리 시각이므로 물리적인 통신 단절 시간으로 해석하지 않는다.

**실제 보류 1회는 이전 REST 대조 대기와 최소 간격에 함께 걸린 경우였다.**

보류 평가는 12:16:02.007353 KST, epoch 3의 sequence 34712 직후에 기록됐다.
당시 매도 측에 알려진 가격 단계가 728개여서 조기 갱신 기준 750개보다 적었지만,
상위 20호가는 유지되고 있었다. 재생한 호가 여유가 기록과 정확히 일치했다.

다음 증분의 수신 기록은 보류 평가보다 약 **41.4ms 뒤**다. 이는 수신 기록 사이의 차이이며
실제 대조 처리 완료 시각을 별도로 계측한 값은 아니다. 보류 1회에 두 사유가 함께 적용됐으므로
두 장애나 두 HTTP 실패로 집계하지 않는다. 이 사례에서 보류는 미재구성 증분이나 범위 소진으로
이어지지 않았다.

[보류·요청 검산](decision-audit.json)에는 전후 행과 ID·호가 여유를 남겼다.
[전체 요청 문맥](request-contexts.json)의 351개 요청에 대해서도 요청 전 호가 상태,
대조 대기 부재, 기록된 간격·사유·예산을 검산했다. 추가 요청의 저장된 시각으로 재계산한
60초 내 횟수가 모두 일치했으며, 가장 가까운 만료 경계도 1.148336초 떨어져 있었다.
다만 별도의 monotonic 처리 완료 시각을 저장하지 않으므로 기록된 경과 시간을 동일한 정밀도로
독립 재현한 검사는 아니다. 이번 한 사례만으로 긴급 예산 예약의 효과나 필요성을 결정하지 않는다.

**동시에 진행된 정기 작업의 재시도도 별도로 기록했다.**

13:10 daily 첫 시도는 파일 묶음 생성 뒤 배타적인 파일 배치 잠금을 얻는 단계에서
`WriterBusy`로 **13:10:45에 실패**했다. 원문 감사가 실행 중인 시간과 겹친다.
파일 읽기·백업 잠금과의 경합은 오류에 명시돼 있지만, 당시 잠금 보유 프로세스의 신원까지
기록된 것은 아니므로 이번 감사만을 유일한 원인으로 확정하지 않는다.

기존 서비스의 `Restart=on-failure`, `RestartSec=120s`에 따라 **13:12:45에 새 시도**가
시작됐고, 13:14:57 표본에서 `running`, `phase=validate`였다. 서비스를 수동으로 재시작하거나
잠금 조건을 완화하지 않았다. 이는 자동 재시도가 시작된 근거이며 오늘 daily·restic 완료
판정은 아니다. 첫 실패를 후속 정상 진행으로 덮어쓰지 않고
[첫 시도](daily-first-attempt.json), [재시도 표본](daily-retry-sample.json),
[관측 시각과 출처](maintenance-observation.json)를 함께 보존한다.

13:13:30의 [현재 상태 표본](current-status.json)에서는 후속 depth·aggTrade가 수신·저장 중이고,
보고서의 연결 오류·미재구성 또는 미복구 공백은 0이었다. 네트워크의 가장 최근 표본도
정상이었다. 이 순간 표본을 전체 기간의 무중단 증거로 사용하지 않는다.

**남은 점검과 실행 순서**는 다음과 같다.

- 오늘 **10/3 14:15 이후** daily 재시도의 최종 결과와 그 새 사본의 restic 저장·검사를 확인한다.
  예정 시각이 지나도 실행이 끝나지 않았다면 완료로 집계하지 않는다.
- 새 기록의 24시간 경계는 **10/4 11:17:30 KST**다. 선택한 마지막 세션의 종료까지 포함해
  **11:30 이후** 보고서 집계가 가능하다. 대량 원문 검사는 13:10 daily와 겹치지 않도록
  정기 작업 완료를 확인한 뒤 수행한다. 긴급 예산 예약은 실제 보류·실패 관계를 더 관찰한 뒤 판단한다.
- 운영 정책과 기존 백업 병행 방식은 유지한다. 이 점검에서는 보관 정책 변경이나 백업 사본 정리를 하지 않았다.

검사 자체는 [check_capture.py](check_capture.py)에 남겼다. 재실행할 때에는 기존 증거를
덮어쓰지 않는 새 폴더를 명시한다. 고정 세션 검증용이며 최신 세션을 임의로 선택하지 않는다.

```bash
.venv/bin/python reports/baseline/depth-decisions-followup-2026-10-03/check_capture.py --output /tmp/depth-decisions-followup-recheck
```

운영 코드와 보호 대상 설정의 해시는 설치 기록과 검사 전후 모두 일치했다.
검사 스크립트의 Ruff 검사·포맷 검사도 통과했다. 운영 코드를 변경하지 않아 기존 단위 테스트를
다시 실행하지 않았으며, 실제 저장 자료의 재생·전수 원문 대조를 검증 근거로 사용했다.
