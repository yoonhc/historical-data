# T13 운영 검증의 고정 완료 범위

2026-10-11 합의. [이미 확인한 운영 결과](summary.md)는 유지하고, 아래 날짜 경계와 한 후속 복구 지점의 대조로 T13 운영 검증을 마무리한다.
현재는 **확인 대상 고정 완료·다음 주기/백업/복원 대기**다. 미래 backup ID·snapshot ID나 성공 결과를 미리 지정하지 않는다.

## 확인 대상

[completion-targets.json](completion-targets.json)에 기존 원장 기록으로부터 작업·시도·저장 근거를 고정했다.

- Target ID: `300941a16686697c683a16f39e325cd34b52a5d2fcf77addef7ed8e5eb584ef0`
- 정오 run: `6a1cf0c8d15848f8b7a0a6ba336dec1a` — 실제 시도 **10개**.
- 저녁 run: `0d70176a798241e8887418a1d65fee1c` — 실제 시도 **16개**.
- 직접 처리 작업 26개와 같은 acquisition 성공을 공유한 refresh 6개, 합계 **관련 작업 ID 32개**.
  공유한 6개는 추가 요청이나 새로운 검증 범위가 아니라 이미 확인한 중복 방지 결과다.
- 다음 주기 비교용으로 현재 완료 acquisition **162개**의 ID·대상·완료 근거 해시도 보존한다.

각 시도의 ID, 대상 자료/UTC 날짜/목적/확인 주기, 원장 기록 해시, query/source/revision ID,
파일 해시와 입력 artifact ID를 포함한다. 원본 [압축 원장](ledger-records.json.gz)·[저장 대조](inspection.json)·[검증 요약](verification.json)의 해시도 연결했다.
Target ID는 `target_id` 필드를 제외하고 키 정렬·공백 없는 UTF-8 JSON을 직렬화한 SHA-256이다.
이 목록은 그대로 보존하고, 실제 후속 확인 결과와 backup/snapshot 선택은 별도 결과 파일에 기록한다.

## 1. 다음 확인 주기와 UTC 날짜 경계

| 경계 | 확인할 구분 |
|---|---|
| 10/12 00:00 KST 이후 첫 실제 runner | 새 KST 주기의 refresh/metadata와 기존 완료 acquisition을 구분한다. |
| 10/12 09:00 KST 이후 첫 실제 runner | UTC 날짜 변경에 따른 **10/11 UTC** 신규 자료 작업과 이전 날짜의 완료 작업을 구분한다. |

예약 시각이 지났다는 사실 대신 실제 runner·작업 ID·주기·상태·시도 기록으로 판단한다.
새 작업도 최초 실행 가능 시각을 지키는지 확인하고, 기존 완료 acquisition을 실패 재시도 명목으로 다시 요청하지 않는지 대조한다.
정당한 새 refresh는 acquisition 재시도와 구분한다.

새 예정 작업 때문에 `data_complete=false`가 되는 것은 허용되는 결과다.
기존 완료가 취소됐다고 표현하지 않으며, 이전 ID의 상태·완료 근거와 새 작업을 각각 확인한다.
**전체 작업 수 188개 유지는 요구하지 않는다.** 188은 10/11 관찰 당시 수치일 뿐이다.
10/12 저녁 자료의 실제 완료는 이번 검증에 추가하지 않는다.

## 2. 10/12 정기 백업의 실제 완료 후 복구 지점 선택

13:10은 예약 시각이며 완료 보장이 아니다. 기존 정기 작업이 실제 완료된 뒤 다음을 한 결과에 연결한다.

1. 정확한 checkpoint 경로·backup ID·manifest 해시·카탈로그 기준 시각·완료 기록.
2. 그 지점에 고정한 **정오 10개·저녁 16개 시도, 관련 완료 근거와 자료**가 포함됐는지 확인.
3. 같은 backup ID의 정확한 restic snapshot ID와 저장 성공 기록.
4. **그 snapshot을 포함한 성공한 전체 읽기 검사**의 receipt·완료 시각. 이미 완료된 정기 검사를 재사용한다.

10/11 snapshot `fd78b31add535359af3e2e6f77d13fede7db632308bf0bad2688d4a78b14324a`는 정오까지만 포함하므로 이 최종 지점을 대신할 수 없다.
후속 checkpoint에 10/12 작업이 추가되거나 아직 예정/대기 상태여도 고정한 10/11 검증 대상이 충족되면 된다.
10/12 저녁까지 범위를 확장하거나 조건을 앞당기려고 추가 백업을 실행하지 않는다.

## 3. 한 번의 독립 복원·종합 대조

선택한 **명시적 snapshot ID**에서 운영 경로와 분리한 시험 경로로 복원한다.
실행 전에 필요한 카탈로그·자료/pack·근거와 예상 공간을 확인해 한 번의 복원으로 묶고 불필요한 대규모 복원을 반복하지 않는다.

- 원장의 daily 작업·run·시도·냉각·재개·공개 관측 기록을 **선택한 checkpoint 시점**의 ID별 내용과 대조한다.
  이후 달라진 운영 DB의 전체 행 수나 현재 상태를 기준으로 삼지 않는다. 실제 없는 기록은 0개로 확인한다.
- 고정한 시도 26개·관련 작업 32개의 완료 근거를 query/source/revision·원문 및 표준 파일에 연결하고,
  복원한 실제 자료의 해시·내용을 대조한다. 파일 존재나 완료 플래그만으로 통과시키지 않는다.
- 새 작업 추가는 허용하되 고정 대상의 누락·변경·복원 불일치는 정확한 ID와 사유로 남긴다.
  과거 완료 기록이나 카탈로그를 덮어써서 맞추지 않는다.

같은 snapshot에 T05 근거가 **실제로 포함됐다면** 복원 작업을 공유할 수 있다.
T13 원장/자료 대조와 T05 완료 상한/순서/연결 대조는 각각 판정한다.
T05 근거 누락·설치·후행 사본 3개 축적·72시간 보호 조건은 T13을 기다리게 하는 선행 조건이 아니다.

## 4. 분리한 후속과 완료 처리

[10/11 공통 waiter의 reference_age 대기](summary.md#기존-strict-gate의-대기는-별도)는 완료 자료 상태와 별도로 보존한다.
이는 TODO의 **진단·백업 등 업무별 시각 요구 분리** 후속 근거이며, T13을 마무리하기 위해 현재 시각 정책을 변경하지 않는다.
실행 전 waiter가 지연되면 실제 관찰/백업이 대기 중이라는 사실을 남기되, 이미 완료한 자료를 실패로 바꾸지 않는다.

위 1–3의 실제 결과가 통과하면 **이번 T13 운영 검증 완료**로 기록한다.
자연 발생하지 않은 오류는 기존 213개 격리 검증 근거를 유지하고 운영 장애를 주입하거나 발생을 기다리지 않는다.
공개 관측기는 비활성, 사용자·시스템 자동 정리 service/timer는 masked로 유지한다.
완료 보고서에서 후속 위치를 연결한 뒤 활성 T13 항목과 진행 중 상세 계약 메모를 TODO에서 정리한다.
보고서·고정 대상·검증 원본과 별도 후속은 보존한다.
