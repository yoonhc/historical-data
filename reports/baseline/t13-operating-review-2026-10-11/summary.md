# T13 실제 예약 처리·UTC 날짜 경계·정오 백업 확인

**2026-10-11 18:20 KST 확인: 정오·저녁 자료 처리와 첫 UTC 날짜 경계는 통과했다.**
현재 원장 188개 작업은 모두 `complete`이며 `data_complete=true`, `review_required=false`다.
실제 자료 요청을 수행한 실행은 정오 10건·저녁 16건이다. 기존 자료 연결과 같은 요청의 acquire/refresh 공유까지 포함한
원장 188개를 신규 다운로드 188건으로 해석하지 않는다.

오늘 정기 checkpoint에는 정오 처리·새 원장 및 전날 보강한 10/9 UTC 자료가 들어 있고,
같은 backup ID의 restic 저장·전체 읽기 검사가 완료됐다. **저녁 자료의 후속 백업과 독립 복원 조회는 아직 남아 있다.**
후보 개발·배포·전체 검사 반복, 수동 daily 재실행, 외부 자료 재요청, 추가 백업/복원은 하지 않았다.

## 실제 일정과 저장

시각은 KST이며, 자료 날짜는 별도로 표시한 UTC 날짜다.

| 관찰 | 실제 결과 |
|---|---|
| UTC 날짜 전환 전 08:50:10 | 완료 156개·예정 전 20개, 요청 없음 |
| 전환 후 첫 실행 09:07:04 | 기존 예정 작업 20개 유지, 10/10 UTC acquire 6개·refresh 6개 추가, 요청 없음 |
| 정오 12:21:06.869–12:21:10.609 | 10건 처리, runner 약 3.740초, 완료 168개·저녁 예정 20개 |
| 저녁 18:00:06.258–18:00:14.338 | 16건 처리, runner 약 8.079초, 완료 188개·미완료 0개 |

09:00 예약 시각 자체가 아니라 실제 09:07 실행에서 날짜 전환을 확인했다. 모든 실제 시도는 해당 작업의
`first_eligible_at` 이후다. 날짜 전환 전 만들었던 10/7 refresh도 범위 밖이라고 사라지지 않았다.
따라서 이번 첫 주기에는 10/7–10/9의 기존 수정 확인과 10/10 신규 확보가 함께 처리됐다.
이를 매 실행마다 모든 과거 자료를 재수집하는 정책이나 최근 3일 범위의 영구 확장으로 해석하지 않는다.

| 신규 자료/관측 | 대상 | 검증한 표준 행 |
|---|---|---:|
| 현물 1분봉 | 10/10 UTC | 1,440 |
| 확정 펀딩 | 10/10 UTC | 3 |
| 현물·선물 instrument metadata | 10/11 12:21 실제 관측 | 각각 1 |
| 선물 거래봉·마크봉·지수봉 | 10/10 UTC | 각각 1,440 |
| OI 아카이브 | 10/10 UTC | 288 |

정오에는 신규 현물/펀딩 2건·metadata 2건·기존 날짜 refresh 6건, 저녁에는 신규 선물 아카이브 4건·refresh 12건을 처리했다.
새 acquire 6건의 저장 근거가 같은 대상의 due refresh 6건도 충족했으며 추가 요청하지 않았다.
정오 완료 대상을 저녁 재시도 명목으로 다시 처리한 기록은 없다.

현재 읽은 **143개 runner 기록 중 141개는 처리 0건**, 자료 처리는 위 2개 실행뿐이다.
26개 시도는 각각 한 번 성공했고 기록된 HTTP 응답은 **50개 모두 200**이다.
미공개·통신 실패·429 냉각·needs_review·수동 재개 기록은 없고 공개 HEAD 관측기도 계속 비활성이다.
실패 이월·냉각 복구·프로세스 중단 경로를 운영에서 새로 재현한 결과는 아니며 기존 격리 근거를 유지한다.

## 완료 플래그와 실제 파일 대조

운영 DB를 `mode=ro`·`query_only`로 읽고 기존 layout 잠금을 읽기 전용으로 공유했다.
Scheduler/Store를 생성하거나 쓰기가 있는 `plan()`을 호출하지 않았다. DB 전체 사본도 만들지 않았다.
원장 원문은 [압축 기록](ledger-records.json.gz), 실제 대조 결과는 [inspection.json](inspection.json)에 보존했다.

- 실제 시도 26건의 query ID·source ID·revision ID·파일 해시를 대조했다.
- 해당 원문 해시·크기와 **Parquet 26개·24,206행**을 읽어 확인했다. 신규 자료뿐 아니라 이번 refresh 결과도 포함한다.
- 봉·OI는 날짜 전체의 정확한 1분/5분 timestamp 배열을 확인했다. 해결되지 않은 blocking issue는 없었다.
- 10/10 OI에는 원문의 인접 역순 22건 경고가 남아 있다. 표준 파일은 288개 timestamp의 정확한 오름차순 범위를 충족한다.
  기존 원문과 경고를 수정하지 않았고, 완료를 “원문 경고가 전혀 없음”으로 확대하지 않는다.
- metadata는 실제 관측한 응답이며 과거 정오 상태나 날짜 전체 상태를 복원했다는 의미가 아니다.

[고정 실행본·설정·검증 요약](verification.json): 배포 소스 149개와 설치 모듈 4개, daily 설정·유닛·root guard 해시가
기존 적용 기록과 일치한다. 시스템/사용자 자동 정리 service·timer 4개 mask와 수집·Chrony 실행을 유지했다.

## 기존 strict gate의 대기는 별도

정오의 최초 허용 시각은 12:20이지만, 기존 공통 waiter가 `reference_age` 때문에 대기하다
12:21:06에 해제되어 daily가 시작됐다. 약 66.9초 늦게 시작했으며 runner 자체 소요 시간 3.740초와 구분한다.
공통 waiter의 총 대기 170.5초는 12:18부터의 기록으로, 이를 모두 정오 daily의 지연으로 세지 않는다.

**18:17 호스트 관찰**에서는 18:00 실행이 성공 종료했고 timer는 enabled/active였다.
18:05 재평가 start job은 공통 waiter의 `reference_age` 조건에서 대기 중이었다.
이는 scheduler 내부의 waiting_source/재시도 상태가 아니며 오늘 작업 188개는 이미 완료됐다.
다른 예약 업무의 시각 정책은 이번 T13 범위에서 바꾸지 않았다.
[실효 유닛·대기 job](host.json), [원본 journal](journal.jsonl.gz).

| Restic 저장 완료 | 15:28:59.243 KST |
| 기존 전체 읽기 검사 완료 | 15:30:19.733 KST, 성공·동일 snapshot 포함 |

로컬 checkpoint의 원장은 **작업 188개(완료 168·예정 20), run 131개, 시도 10개**다.
냉각·재개·공개 관측 기록은 당시 0개다. 정오 시도 10개와 해당 완료 task의 전체 JSON이 운영의 같은 기록과 일치하며,
그 query/source/revision·실제 원문/Parquet 해시도 checkpoint에서 대조했다.
전날 18:52 보강한 **10/9 UTC 선물 네 종류**도 원래 revision/source ID와 해시로 이 checkpoint에서 확인했다.

manifest 해시는 restic 상태 원장의 같은 backup ID와 일치하고, 지정 snapshot을 실제 저장소에서 조회해 태그·식별자를 대조했다.
기존 `check --read-data` 완료 receipt를 연결했으며 전체 검사를 다시 실행하지 않았다.
**18시 시도 16개는 이 checkpoint에 없고 원장은 예정 상태다.** 현재 운영의 완료 상태를 과거 checkpoint에 덧씌우지 않는다.

`backup.json`의 기존 `catalog_counts`에는 daily 테이블이 열거되지 않지만, 실제 checkpoint의 SQLite에는 위 여섯 daily 테이블과
원문 기록이 들어 있음을 직접 조회했다. 이 필드의 열거 누락을 원장 백업 누락으로 오인하지 않는다.
이번에는 restic에서 DB를 꺼내 독립 복원하는 단계까지 수행한 것은 아니다.

## 남은 완료 조건

10/11 합의로 [최종 완료 범위](completion-plan.md)와 [작업·시도 ID 및 완료 근거](completion-targets.json)를 고정했다.

1. 다음 KST 확인 주기의 새 refresh/metadata, UTC 날짜 변경의 신규 자료 작업, 기존 완료 acquire를 구분한다.
   새 작업으로 `data_complete=false`가 되는 것과 과거 완료 취소를 혼동하지 않는다.
2. **10/12 정기 작업이 실제 완료된 뒤**, 정오 10개·저녁 16개 시도와 완료 근거·자료가 들어 있는
   정확한 backup ID·snapshot ID 및 그 snapshot의 전체 읽기 검사 완료 근거를 연결한다.
3. 지정 snapshot에서 별도 경로로 한 번 복원하여 **고정 대상 ID와 해당 checkpoint 시점의 원장·자료**를 대조한다.
   전체 작업 수 188개를 고정하지 않고, 10/12 저녁 자료까지 기다리며 범위를 늘리지 않는다.

T13은 이 실제 검증이 끝날 때까지 활성 항목으로 유지한다. 공통 waiter 대기는 업무별 시각 요구 분리의 후속 근거로 남긴다.
같은 snapshot에 T05 근거가 실제 포함되면 복원을 공유할 수 있지만 두 완료 기준은 별도이며 T05 때문에 T13을 미루지 않는다.
운영 장애 주입·추가 대규모 복원·현재 시각 정책 변경은 하지 않고 공개 관측기 비활성·자동 정리 mask를 유지한다.
