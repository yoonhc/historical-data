# 다음 후보의 범위 — 아직 구현·운영 적용 전

대상은 depth·aggTrade 사용자 서비스 두 개의 **수집 프로세스 시작 직전**이다. 현재 사용자
관리자에서 존재하지 않는 `network-online.target`을 기다리는 설정을 실제 준비 상태 확인으로
대체한다. 기존 수집기의 세션·복구·저장·품질 판정과 다른 예약 작업은 유지한다.

## 기동 조건

| 조건 | 제안하는 판정 |
|---|---|
| 현재 부팅의 초기 시각 동기화 | 현재 프로필의 timesyncd가 동작하고 `/run/systemd/timesync/synchronized`가 존재하며 시스템의 동기화 상태도 확인됨 |
| 초기 네트워크 | 사용할 경로·인터페이스가 준비되고 스트림/REST 호스트 이름을 제한 시간 안에 해석 가능 |
| 실패·대기 | 사유·boot ID·monotonic 시각을 별도 운영 로그에 남기고 아직 수집 프로세스를 시작하지 않음 |

시각 제공자와 경로·대상 호스트는 호스트 프로필로 분리한다. 현재 Linux의 timesyncd 조건을
다른 NTP 제공자나 미래 VM에 묵시적으로 적용하지 않는다. `/var/lib/systemd/timesync/clock`의
존재·최근 수정 시각, NTP 데몬의 active 상태만으로 동기화 완료를 대신 판정하지 않는다.
동기화 표시는 부팅 이후의 초기 준비 근거이며, 운영 중 모든 시각 보정까지 방지하는 장치는 아니다.

NetworkManager의 초기 완료 여부만으로 외부 도달성을 보장하지 않는다. 준비 확인 뒤의
연결 실패·상태 변경은 기존 스트림 복구 절차가 계속 처리한다. 기동 검사에 거래소 depth REST
요청을 추가하거나 매번 별도 NTP 질의를 보내는 방식은 필요하지 않다. DNS 검사 자체는
실제 구현 시 네트워크 질의를 발생시킬 수 있으므로 호출·타임아웃을 제한한다.

## 서비스 연결과 대기 한도

공통 검사기를 각 서비스의 `ExecStartPre`에서 호출하는 방안을 우선 검증한다. 준비될 때까지
잠깐씩 재평가하되 monotonic 기준의 유한한 한도를 둔다. 초기 후보 값은 한 시도 최대 180초,
각 외부 명령은 짧은 별도 타임아웃, 서비스의 전체 시작 한도는 이보다 여유 있게 둔다.
조건이 충족되지 않으면 실패 사유를 남기고 종료하며 기존 `Restart=always`, `RestartSec=15s`의
다음 시도가 다시 평가하게 한다. 시간 경과만으로 준비됐다고 처리하지 않는다.

`ExecStartPre`의 실패는 본 실행을 막는 반면 `ExecCondition`의 일반적인 불충족 종료는
서비스 실패로 취급되지 않는다. 원하는 자동 재시도 의미를 격리 유닛에서 확인해야 한다.
[systemd v255 서비스 설명](https://raw.githubusercontent.com/systemd/systemd/v255/man/systemd.service.xml)

수집 대기 상태는 실제 collection의 정상·실패 판정을 덮어쓰지 않는 별도 기록으로 남긴다.
시작하지 못한 수집을 정상 수집으로 집계하지 않으며, 준비 대기 중 생기는 수집 공백도
숨기지 않는다. 해당 프로필·검사기 오류와 일시적인 준비 대기를 구분한다.

## 격리 검증 후 적용

- 경로 없음, DNS 오류, NTP 데몬만 active, 동기화 표시 없음이면 본 수집 명령이 실행되지 않음.
- 같은 boot의 준비 조건을 만족하면 본 실행으로 넘어가며, NTP로 벽시계가 바뀌어도 대기 한도가 안정적임.
- 타임아웃 후 재시도, 대기 중 명시적 중지, 손상된 설정과 명령 실패의 로그·종료 코드가 구분됨.
- 과거 부팅·잘못된 제공자의 표시를 채택하지 않으며, 이미 동기화된 상태에서는 불필요한 긴 대기가 없음.
- 실제 수집기 대신 표식만 쓰는 명령으로 유닛의 시작·재시도 동작을 시험함. 운영 시간·네트워크를 조작하지 않음.
- 두 기존 서비스의 로그·종료 동작 및 원래 collection 보고서를 유지함.

이 후보의 구현·검증 결과를 먼저 고정하고 운영 반영 범위를 정한다. 설치 시에는 중복 수집을
만들지 않으며 검증된 파일·설정만 적용한다. 현재 수집 프로세스를 멈추지 않고 준비할 수 있는
작업은 모두 먼저 완료한다. 강제 재부팅·로그아웃·네트워크 차단 시험은 필요하지 않다.

RTC의 약 41초 오차는 별도 호스트 설정 항목으로 처리한다. 다른 OS가 RTC를 공유하는지
확인한 뒤 UTC 전환·시스템 시각에서 RTC로의 반영을 검토한다. RTC 보정만으로 네트워크 준비
대기가 생기지는 않으며, 기동 검사만으로 RTC의 빠른 상태가 교정되는 것도 아니다.
NTP 제공자 교체·서버 변경이나 모든 사용자 서비스의 기동 지연으로 범위를 넓히지 않는다.
