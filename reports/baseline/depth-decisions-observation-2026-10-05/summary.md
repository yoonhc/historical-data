# 보류 기록 적용 후 45개 종료 세션과 호가 범위 손실의 관계

2026-10-05 오전 점검. **이번 두 범위 손실은 추가 조회 예산 소진으로 갱신을 못 한 사례가
아니었다.** 한 건은 사전 보류 없이 정상 범위가 한 증분에서 소진됐다. 다른 한 건은 직전의
대조 대기가 해소되고 새 범위가 채택된 뒤, 다음 증분에서 상위 20호가가 부족해졌다.
둘 다 같은 연결에서 수집을 이어가며 복구했지만 원래 `partial` 판정은 유지한다.

운영 요청 정책·코드·서비스 설정을 변경하지 않았고, 수집 재시작이나 새 거래소 요청도 하지 않았다.
[분석 종합](analysis.json), [실패 전수 원문 검사](failures-verification.json),
[남아 있는 보류 문맥 검산](decisions-verification.json)에 근거를 남겼다.

## 고정한 관찰 범위

새 기록이 실제 적용된 **10/3 11:17:30.060370 KST부터 10/5 08:30:13.870845 KST까지**의
종료 세션 45개를 고정했다. 약 45시간 13분의 구간이며 연결·프로세스 교체 공백도 포함한다.
08:30:29에 시작해 점검 당시 실행 중이던 세션은 [별도 표본](running-excluded.json)으로 제외했다.
검사 중 새로 종료되는 세션을 이 집계에 임의로 추가하지 않았다.

첫 24시간의 시작 기준 경계는 **10/4 11:17:30**이며, 그 안에 시작한 마지막 세션은
**11:24:09**까지 포함했다. 이로써 새 기록의 첫 24시간 운영 관찰도 완료했다.
종료 보고서·카탈로그 집계는 [audit.json](audit.json), [세션 목록](book_depth-index.json),
[고정 보고서](book_depth-reports.json)에 있다. 표의 전체 REST 집계는 운영 보고서의 기록이며,
아래 독립 재생·원문 대조 범위와 구분한다.

105회는 보류 **평가** 횟수다. HTTP 실패나 독립된 장애 105건이라는 뜻이 아니다.
63회에는 `pending_verification`과 `minimum_interval`이 함께 적용됐으므로, 전체 blocker 집계는
최소 간격 105회·대조 대기 63회다. 사유를 더해 장애 168건으로 계산하지 않는다.

## 두 범위 손실의 실제 순서

| KST 시각 | 실패 직전과 원문 증분 | 보류와의 관계 | 같은 연결의 다음 정상 증분까지 수신 시각 차이 |
|---|---|---|---:|
| 10/4 06:05:18.166642 | 알려진 매수 997개가 한 증분에서 0개가 되는 변경; 범위 소진 | 해당 epoch에는 보류 없음. 직전 상태의 여유도 정상이고 대조 대기도 없었음 | 0.143604초 |
| 10/5 07:16:19.112482 | 새 범위를 채택한 뒤 알려진 매도 981개가 다음 증분에서 8개로 감소; top 20 부족 | 직전 보류는 이미 해소됐고 대조·범위 갱신도 성공한 뒤 발생 | 0.147036초 |

이 차이는 애플리케이션 수신 기록의 차이다. 정확한 장애 지속시간이나 REST 응답시간으로
해석하지 않는다. 미재구성 카운터 0도 순간 범위 손실·연결 공백이 없다는 뜻은 아니다.

**첫 사례**의 collection은 `c595e79851ef4ced8e4194f22cf58b84`다.
해당 세션에 보류 12회가 있지만, 실패 전 4회는 이전 물리 연결의 다른 epoch에 있었고 나머지
8회는 복구 후 epoch에 있었다. 실패 epoch 2에는 보류가 없다. 마지막 보류는 실패 약 13분
51초 전이었다. 즉 같은 세션에 보류와 실패가 함께 있다는 집계만으로 선후 인과를 만들 수 없다.

실패 직전 sequence 25273에서 매수 997·매도 989개, 여유 정상, pending 없음이었다.
25274의 원문 절대 수량 변경을 독립 적용하면 알려진 범위 안의 매수 단계가 0개가 된다.
실패한 적용은 기존 정상 Book을 교체하지 않으므로 재생 trace의 저장 Book에는 이전 997개가
남는다. 이 상태 보존과 독립 계산한 0개를 혼동하지 않았다. 마지막 갱신 REST 응답 이후
수신 시각 차이는 2.144503초였다. [전수 원문·재생 결과](c595e79851ef4ced8e4194f22cf58b84.json)와
[보류·직전 trace](c595e79851ef4ced8e4194f22cf58b84-decisions.json)를 보존했다.

**두 번째 사례**의 collection은 `54d28ea721ed41fab80928c064514159`다.
실패 직전의 순서는 다음과 같다.

| sequence | 실제 저장 순서와 재생 결과 |
|---|---|
| 27514 | REST snapshot 수신. 현재 호가보다 ID가 앞서 대조 대기 |
| 27515 | 기존 범위의 매도 670개. 대조 대기·최소 간격으로 보류; 추가 예산은 0/12 사용 |
| 27516 | REST와 같은 ID에서 top 20 일치. 새 범위 채택, 매도 981개·매수 1,014개, 여유 정상·pending 해소 |
| 27517 | 다음 증분에서 매도 8개로 감소. top 20 부족을 사실대로 기록하고 새 epoch로 이동 |
| 27518~27519 | 같은 소켓의 새 anchor와 후속 증분으로 동기화·충분한 top 회복 |

27516과 27517의 수신 시각 차이는 약 **44.8ms**이며, 마지막 갱신 REST 응답에서 실패 증분
수신까지는 약 **165.7ms**다. 보류가 기록됐다는 이유로 아직 갱신을 못 한 상태라고 해석하면
실제 순서를 놓친다. [전수 원문·재생 결과](54d28ea721ed41fab80928c064514159.json)와
[요청 문맥·직전 trace](54d28ea721ed41fab80928c064514159-decisions.json)에서 ID 연결과
갱신 성공을 함께 대조했다.

두 세션의 **71,187행·가격 수량 쌍 9,219,929개**를 원문과 전수 비교했고 모든 epoch의 최종
재생 상태가 운영 보고서와 같았다. 원래 두 `partial`을 정상으로 바꾸거나 범위 밖 호가를 추측하지 않았다.

## 정상적으로 해소된 보류와 비교

보류가 있는 세션은 16개다. 전체 105회 중 개별 문맥이 남은 **67개**를 중복 없이 모았다.
최초·마지막·최근 8개와 실패 직전 복사본을 합친 결과이며, 나머지 **38회의 개별 문맥은
저장 구조상 남아 있지 않다**. 집계 카운터와 개별 사례 전수 보존은 다른 범위다.

67개를 포함한 24개 epoch를 재생해 당시 호가 여유·pending 상태·최소 간격 조건과 추가 예산
사용량을 검산했다. 같은 epoch의 실제 REST 요청 문맥 1,964개도 재생 상태와 일치했다.
주변 342행의 원문 가격 수량 쌍 305,615개 대조가 통과했다. 두 실패 세션의 전수 검사와
일부 겹치는 범위이므로 별개의 고유 자료 수로 합산하지 않는다.

- 67개 모두 뒤따르는 행에서 조기 갱신 필요 조건이 해소됐다. 평가 시각에서 해당 행의
  수신 시각까지 최대 0.774782초였다.
- 대조 대기가 있는 41개 표본은 모두 해당 snapshot의 동일 ID 대조 일치로 해소됐다.
  다음 해소 행의 수신 기록까지 최대 0.063685초였다.
- 정상 세션 `94e0f5c39acd43b1baa026d2dac364ff`의 최소 간격 보류는 이전 처리 후 0.929초에
  발생했고, 후속 행에서 여유가 회복됐다. 수신 기록 차이는 약 0.223초였다.
- 정상 세션 `701614f313b044328ffb14dedc579a68`에는 보류 25회가 기록됐지만 범위 손실은 0회다.
  남아 있는 9개 문맥도 재생과 일치했다. 보류가 곧 실패라는 분류는 성립하지 않는다.

위 시간은 서로 다른 기록 지점의 차이며 실제 대조 처리 완료를 별도 계측한 값이 아니다.
저장하지 않은 monotonic 완료 시각을 독립 재현했다고 주장하지 않는다.

## 저장 품질·검증 대기·통신 관찰

[전체 표준 파일 검사](receipt-continuity.json)는 47,955개 segment의 해시와 1,601,273행의
순서를 확인했다. 증분 1,585,267개가 보고서 수신·저장 집계와 같고, 같은 소켓의 ID 연결
1,585,087개에서 오류 0, 수신 시각 역전 0이었다. 전체 가격 수량 원문 대조를 45개 모두에
수행한 것은 아니다.

10초 초과 수신 간격 44개는 모두 시간제 프로세스 교체 경계였다. 최대 17.85초이며,
물리 소켓 교체 경계의 최대는 2.35초, 같은 epoch 안의 최대는 8.82초였다. 수신 시각은
애플리케이션의 recv 반환 기록이므로 이를 그대로 네트워크 단절 시간으로 판단하지 않는다.
연결 사이를 이어 무중단·완전 연속 자료로 선언하지 않았다.

검증 대기 1개는 `18b0e59ea9844b66b7d56010828ad1d0`의 마지막 REST snapshot이다.
10/4 09:23:33 KST에 마지막 증분보다 앞선 ID를 받아 둔 채 duration 종료했다. 뒤따르는 행이
없음을 확인했고 [전체 재생·마지막 원문 대조](pending-boundary.json)도 같은 결과다.
일치나 복구 실패로 다시 분류하지 않고 **미검증 1개**로 유지한다.

분 단위 네트워크 표본 2,712개 중 2,711개가 정상이다. 10/3 23:16:20 KST의 한 표본에서
REST HTTPS TLS 연결이 2초 제한으로 timeout 됐지만, 같은 표본의 유선 링크·게이트웨이·
외부 TCP·두 DNS·스트림 HTTPS는 정상이다. 두 범위 손실과 시각이 다르며, 각각 전후 2분
표본도 정상이다. [원래 표본과 해시 대조](network-context.json)를 남겼다.
분 단위 표본으로 짧은 장애나 WebSocket 전달 상태까지 배제할 수는 없다.

## 검사 중 정기 정리와 후속 판단

이번 대량 읽기와 겹친 09:15 정기 파일 정리는 09:15:54에 pack 단계의 배타 파일 배치 잠금
획득이 `WriterBusy`로 실패했다. [첫 시도](maintenance-first-attempt.json)를 보존했다.
잠금 소유 PID는 당시 기록되지 않았으므로 이 감사만을 유일한 원인으로 확정하지 않는다.
[journal](maintenance-journal.jsonl)의 자동 재시도 기록과 [후속 결과](maintenance-retry.json)에서
09:17:54 재시작 → **09:18:58 정상 완료**를 확인했다. 수집기를 수동 재시작하거나 잠금을 완화하지 않았다.
후속 대량 읽기 검사는 정기 파일 정리 직후에 시작하도록 시간대를 조정할 근거다.

두 실패 모두 추가 예산을 따로 남겨두는 정책이 직접 해결할 유형이라는 근거는 없다.
최소 간격을 줄이거나 더 자주 요청했다면 어떤 REST 응답을 받았을지는 관측하지 못했다.
따라서 **현재 요청 정책을 유지하고, 이번 두 급격한 범위 변화를 후속 격리 실험의 실제 사례로
사용하는 것**이 적절하다. 설정 변경의 효과를 이번 관측만으로 확정하지 않는다.

검사 후 종료 보고서 45개와 운영 코드가 그대로임을 확인했다. [현재 수집 표본](current-streams.json)은
호가·aggTrade가 계속 running임을 보여 주며, 이 순간 표본을 전체 기간의 무중단 증거로 쓰지 않는다.
기존 단위 테스트 전체를 재실행하지 않았고 실제 자료 검산·재생, report 스크립트 검사와 근거 해시로 검증했다.
새 checkpoint 정리 이후 첫 daily → 예약 restic 저장·검사는 별개로 오늘 14:15 이후 확인할 항목이다.
