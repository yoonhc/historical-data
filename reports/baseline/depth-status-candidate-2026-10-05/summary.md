# 호가 실패 상태 선행 공개 후보 구현·격리 검증

2026년 10월 5일 검증. **대량 이벤트 저장에 들어가기 전에 실패 상태를 DB에 커밋하는
후보를 구현했고, 호가 관련 회귀 테스트 163건이 통과했다. 운영에는 적용하지 않았다.**
한쪽 0개와 top 20 중 8개만 남는 경우 모두, 이벤트 저장을 멈춘 동안 별도 읽기 연결과
실제 `depth-status` CLI가 `healthy=false`를 반환했다.

이 결과는 [두 실제 사건의 독립 계산](../depth-independent-2026-10-05/summary.md)을
이어받은 상태 전달 보완이다. 원문·Book 계산·범위 채택·요청 예산·최소 간격·재생 판정은
유지했다. 실제 서비스의 적용·재시작이나 운영 부하에서의 후속 관찰은 이번 범위에 포함하지 않았다.

## 후보 격리와 변경 범위

운영 Python 환경은 작업 저장소의 소스를 직접 읽는 editable 설치다. 따라서 운영 경로에서
파일을 교체하지 않고 `/tmp/marketdata-depth-status-20261005`에 후보를 만들었다.
기준 commit은 `c2d02e784b0456560ec734b9ef88f4d960dc6b78`이며, 앞선 독립 계산 보고서와
아직 커밋하지 않은 `tests/test_depth_independent_cases.py`도 복사했다. 테스트의
`PYTHONPATH`를 후보에 명시하고 실제 모듈 경로까지 확인했다.

[후보 패치](candidate.patch)는 실행 코드 2개 파일과 테스트 3개 파일의 변경을 보존한다.
기존 독립 계산 테스트 2건은 그대로 두고, 공개 지연을 재현하던 소비 경로 4건의 기대값을
후보에서만 바꿨다. 운영 저장소의 해당 테스트와 이전 보고서는 수정하지 않았다.
이 패치는 현재 작업 저장소의 미커밋 독립 계산 테스트를 전제로 하며, 기준 commit만
복원한 디렉터리에 단독 적용하는 패치는 아니다.

[변경 검토](change-review.json)에서 운영 소스·서비스 파일·기존 독립 검증 자료 등
66개 파일의 해시가 착수 당시와 같은 것을 확인했다. AST 대조 결과 `depth.py`의 기존
Book, History, Session, `save_collection`, `status`, `replay` 등은 모두 같고,
`depth_stream.py`에서는 `capture`만 변경됐다. `depth_refresh.py`도 바이트 단위로 같다.
`git apply --check`만 통과시켰으며 실제 적용은 하지 않았다.

## 저장 순서와 데이터의 의미

후보의 순서는 다음과 같다.

```text
범위 소진 또는 top 부족 감지
  → 마지막 DB 보고서의 복사본에 실패 관측만 반영
  → 별도 트랜잭션 커밋
  → depth-latest.json 갱신
  → 기존 이벤트 저장
  → 상세 epoch·수집 보고서 저장과 복구 진행
```

새 `publish_failure()`는 메모리의 전체 보고서를 조기에 저장하지 않는다. DB에 마지막으로
저장한 보고서를 읽고 `synchronized=false`, `complete=false`, 누적 손실 수와
`failure_notice`를 추가한다. 저장한 이벤트·snapshot 건수, 마지막 ID·수신 시각, 기존
epoch 보고서는 그대로 둔다. 반환하는 것도 실패 관측뿐이므로 수집기의 미저장 버퍼와
상세 보고서를 이전 보고서로 덮어쓰지 않는다.

| 필드 | 의미 |
|---|---|
| 기존 `messages`, `persisted_messages`, `snapshots`, `last_update_id`, `epochs` | 마지막 상세 보고서가 확정한 저장 범위; 선행 공개로 앞당기지 않음 |
| 기존 `last_received_at` | 마지막 저장 보고서의 실제 수신 시각; 상태 갱신 시각으로 바꾸지 않음 |
| `failure_notice.observed_at` | 수집기가 실패를 감지한 시각 |
| `failure_notice.observed_received_at`, `observed_update_id`, `sequence`, `epoch` | 실패 입력의 진단 정보; 저장 완료 범위를 뜻하지 않음 |
| `failure_notice.recorded_at` | writer 잠금 안에서 최초 실패 기록을 준비한 시각; 정확한 COMMIT 완료 시각을 계측한 값은 아님 |
| `updated_at` | 보고서 갱신 시각; 시장 데이터 수신 시각과 별개 |

진행 중인 DB 트랜잭션 안에서 호출하면 거부한다. 정상 반환은 커밋 뒤에 이루어지며,
JSON 쓰기는 그다음이다. 재시도는 손실 수를 다시 더하지 않고 절대 누적값의 최댓값을
사용한다. 같은 sequence의 재시도는 최초 `recorded_at`을 유지하고, 내용이 다른 재시도와
더 오래된 실패로 최신 관측을 바꾸려는 시도는 거부한다. 종료된 실패·partial 수집을
재시도 때문에 `running`으로 되돌리지 않는다.

## 실패 처리에서 추가로 보완한 부분

선행 공개가 성공한 뒤 이벤트 저장이 계속 실패하면, 종료 처리도 마지막 DB 보고서에
실패 정보만 덧붙인다. 메모리에만 있는 이벤트·ID·건수를 완료된 저장 범위로 올리지 않는다.
반면 이벤트가 실제로 저장된 후 전체 보고서의 JSON 쓰기만 실패한 경우에는 DB에 이미
확정한 저장 범위를 보존한다.

오류 주입 중 파일 저장의 `OSError`가 기존 소켓 오류 처리에 잡혀 재연결로 이어지는
상황도 드러났다. 후보에서는 `flush()`의 이벤트·보고서 저장 `OSError`와 선행 공개 오류를
원인 예외가 연결된 `DataError`로 전달한다. 저장 오류가 네트워크 재연결로 처리되어
성공처럼 진행되지 않게 한 변경이다. 네트워크 요청 정책은 바꾸지 않았다.

DB 단계와 JSON 단계의 오류 문구를 구분한다. DB 단계는 커밋을 확인하지 못했다고
보고하고, DB 커밋 뒤 JSON 실패는 커밋 성공과 mirror 실패를 함께 알린다. JSON 쓰기가
계속 실패하면 DB와 JSON이 서로 다른 상태로 남을 수 있다. DB를 읽는 CLI의 실패 판정과
오래된 JSON의 내용을 같은 것으로 보고하지 않는다.

## 격리 시험 결과

시험은 실제 collector, SQLite, 원문·표준 이벤트 저장, 상태 조회, 재생을 사용했다.
거래소 I/O는 합성 입력이며 새 Binance 요청은 없었다. 수집 시간 제한을 위한 시계만
대역으로 바꾸고 수신 시각은 실제 시계를 사용해, 별도 CLI가 신선도 검사를 그대로 수행했다.

합성 정상 기준은 저장 증분 2개·마지막 ID 102다. 실패 증분 ID 103에서 알려진 매수
100개를 모두 제거하거나 매도 100개 중 92개를 제거한다. 이 숫자와 ID는 실제 두 사건의
값이 아니다. 실제 사건은 기존에 고정한 원문을 사용하는 별도 독립 계산 테스트로 확인했다.

| 시험 | 확인한 결과 |
|---|---|
| 0개·8개, 이벤트 저장 함수 진입 뒤 정지 | 별도 프로세스의 CLI 종료 코드 2, `healthy=false`; 새 SQLite 읽기 연결·JSON도 실패 상태 |
| 위 정지 지점의 저장 범위 | 저장 증분 2개·ID 102·기존 epoch·수신 시각 유지; 실패 ID 103은 `failure_notice`에만 존재 |
| 저장 재개·같은 소켓 복구 | 현재 Book의 top 충족, 손실 1회 유지, 최종 `partial`, 재생 일치 및 `valid=false` |
| DB 커밋 후 JSON 1회 실패 | 재시도로 동일 관측 유지, 원문 저장 후에도 최종 `failed`; 손실 중복 없음 |
| DB 커밋 후 JSON 지속 실패 | DB는 거부 상태, JSON은 이전 정상 보고서일 수 있음; 저장 범위 2개 유지 |
| 이벤트 저장 성공 후 상세 보고서 JSON 1회 실패 | DB에 확정한 증분 3개 보존, 최종 `failed`; 정상으로 되돌아가지 않음 |
| 선행 공개 후 원문 저장 1회 실패 | 종료 처리의 재시도에서 저장, 실제 증분 3개와 보고서 일치, 최종 `failed` |
| 선행 공개 후 원문 저장 지속 실패 | 실제 저장 증분 2개·기존 epoch·ID 유지, 실패·flush 오류 보존 |
| DB UPDATE 또는 COMMIT 1회 실패 | 재시도에서 실패 커밋 후 이벤트 저장; 손실 1회·최종 `failed` |
| DB UPDATE 또는 COMMIT 지속 실패 | 선행 공개 불가, 이벤트 저장 진입 없음; 이전 정상 보고서가 남는 한계를 확인 |
| 선행 공개 후 강제 종료 | 시험 자식 프로세스의 예외 처리 없이 종료해도 실패 관측·저장 범위 유지 |
| 강제 종료 뒤 동일 관측 2회 재시도·새 시험 수집 | 카운터·최초 기록 시각 유지; 기존 수집은 `interrupted`, 새 수집과 분리 |
| 같은 수집에서 실패 2회 | 누적 손실 1→2, `partial` 유지; 오래된 관측으로 역행하는 재시도 거부 |
| 중첩 트랜잭션·같은 sequence의 다른 관측 | 거부, 기존 상태·손실 수 유지 |

정지 시험은 저장을 일정 시간 늦춘 뒤 확인하는 방식이 아니다. 자식 수집기가 대량
저장 직전의 장벽에서 대기하고, 부모가 새 CLI 프로세스와 읽기 연결로 실패 상태를 확인한
뒤에만 재개시킨다. 따라서 장비 속도에 기대지 않고 커밋 순서를 확인했다.
강제 종료와 재시작은 모두 임시 시험 저장소·프로세스에 한정했다.

새 오류·공개 시험은 25건이다. 이 중 오류 주입은 9가지 조건 × 0개·8개 경로로 18건이며,
나머지는 별도 CLI 정지 시험 2건, 반복 실패 2건, 강제 종료 2건, 트랜잭션·충돌 1건이다.
DB COMMIT 주입은 실제 SQLite 트랜잭션을 rollback한 뒤 예외를 내는 조건이다. 원문 저장
오류는 해당 저장 호출의 쓰기 전 실패를 주입했다. 모든 디스크 장애 위치를 망라한 검증은 아니다.

호가 관련 최종 검사 **163건 통과, 실패·오류·건너뛰기 0건**, 약 12.35초다.
[최종 JUnit 결과](tests.xml)의 시작은 2026-10-05 12:12:04 KST다. 여기에는 앞선 두 실제
사건 독립 계산과 소비 경로 4건, 기존 bootstrap·history·재시도·REST 대조·갱신·보류 기록
검사도 포함한다. 프로젝트 전체 테스트를 모두 실행했다는 뜻은 아니다.

최초 오류 시험은 [17건 중 14건 실패](first-fault-tests.xml)했다. 시험의 가변 수신 경과시간
비교와 segment 종류 대신 실제 행 종류를 세어야 하는 집계 오류를 고쳤고, 앞서 설명한
저장 `OSError`의 소켓 오류 처리 진입도 수정했다. 이후 [17건 통과](fault-tests-v2.xml),
COMMIT·반복 실패 등을 추가한 [25건 통과](fault-tests-v3.xml) 순서로 검증했다.
전체 163건 통과 뒤 기록 시각 이름을 `published_at`에서 `recorded_at`으로 명확히 했으며,
최종 코드로 163건을 다시 통과시켰다. 이전 결과는 [변경 전 기록](tests-before-timestamp-naming.xml)에 남겼다.

## 재현과 산출물

격리 후보가 남아 있는 동안의 재현 명령은 다음과 같다. Python 실행 파일은 운영 환경의
의존성만 이용하고, import는 명시한 후보 경로에서 한다.

```bash
cd /tmp/marketdata-depth-status-20261005
env PYTHONPATH=/tmp/marketdata-depth-status-20261005/packages/marketdata/src:/tmp/marketdata-depth-status-20261005/packages/marketdata_freqtrade/src:/tmp/marketdata-depth-status-20261005 \
  /home/yoonhc/projects/algoTrade/historical_data/.venv/bin/python -m pytest -q tests/test_depth*.py
```

임시 디렉터리는 장기 보관을 보장하지 않는다. 후보 코드와 테스트는 이 보고서 옆 패치에
남겼으며, 입력·기준은 [격리 기록](isolation.json)과 기존 독립 계산 보고서로 특정한다.
[패키징 검사기](package_candidate.py)는 변경 파일·보호 해시·AST·모듈 경로·패치 적용
가능 여부만 검사하고 운영에 패치를 적용하지 않는다. Ruff·형식·문서 링크·최종 보호
해시 검사는 [최종 검증 기록](validation.json)에 남긴다.

## 남은 한계와 후속 결정

보장한 것은 **실패 상태 기록이 성공한 경우, 대량 이벤트 저장이 이전 정상 표시를
유지시키지 않는 순서**다. 선행 기록 자체의 writer 잠금 대기·DB 오류·디스크 장애까지
즉시성을 보장하지 않는다. DB 기록이 계속 실패하면 현재의 수신 신선도 제한에 걸리기
전까지 이전 정상 표시가 남을 수 있으며, 이번 시험도 그 결과를 숨기지 않는다.

새 연결·새 조회에서는 커밋된 상태를 확인했다. 이미 시작한 오래된 읽기 트랜잭션이나
독자적인 캐시까지 강제로 갱신하는 변경은 아니다. SQLite의 연결·트랜잭션 가시성은
[공식 격리 문서](https://www.sqlite.org/isolation.html)의 구분을 따른다.
`depth-status` 하나가 모든 순간의 최신 호가를 보증한다는 의미로 확대하지 않는다.

실제 두 사건의 공개 지연 시간을 새로 측정하거나 실제 거래 피해를 확인한 것은 아니다.
요청 정책·범위 정책의 추가 실험도 하지 않았다. 다음 결정은 이 후보의 운영 반영 여부와
적용 방법이며, 현재 운영 파일·서비스·과거 partial과 원문은 유지했다.
checkpoint 정리 후 새 daily → 예약 restic 저장·검사 확인은 별개의 후속 항목이다.
