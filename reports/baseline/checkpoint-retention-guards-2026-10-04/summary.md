# checkpoint 정리 계획의 코드 고정과 공간 관측 보강

2026-10-04 00:21 KST 기준. [10/3 구현·검증](../checkpoint-retention-2026-10-03/summary.md)에
이어 계획의 코드 식별자, 사본별 판정 시각·경과시간, snapshot 연결 재대조와 적용 전후 공간
관측을 추가했다. **운영 삭제 0건, 적용 비활성화 유지**다. 정리 타이머·restic forget/prune은
추가하지 않았고, 기존 수집·daily·restic 서비스와 원본·백업·시험 사본·복구 키트는 유지했다.

## 보완한 동작

- 계획 schema 2는 Git commit과 관련 소스·의존성 선언의 SHA-256, 실행 경로·Python 버전을
  묶은 `code_id`를 포함한다. 적용 때 정책·프로필과 함께 대조하며, 계획 후 코드·commit이
  바뀌면 거부한다. import 이후 디스크 소스가 바뀐 기존 Python 프로세스도 새로 시작해야 한다.
- 코드 식별자가 없는 기존 schema 1 계획은 과거 증거 조회만 허용한다. 10/3의
  `bb871d25…`는 새 코드의 적용 계획으로 사용할 수 없다. `apply_enabled` 변경도 정책 해시를
  바꾸므로, 최종 적용 정책으로 만든 **새 전체 계획 ID와 정확한 대상 목록**을 승인받아야 한다.
- `assessed_at`을 공통 UTC 판정 시각으로 기록하고 완료 시각부터의 `age_seconds`를 표시한다.
  최근 3개와 완료 후 72시간 미만의 합집합을 계속 보호한다. 유지 사본에도 보호 사유와
  snapshot ID를 명시하고, 유지·후보 모두 backup/snapshot 연결이 바뀌면 적용을 거부한다.
- 적용 시도마다 같은 UUID·장치의 공간을 전후 측정한다. 예상 회수량과 사용 가능 공간의 관측
  변화량을 분리하고 다른 쓰기의 영향을 포함하므로 정확한 회수량은 `null`로 기록한다.
  사후 측정 실패는 삭제 결과를 덮지 않는다. 강제 종료로 없는 표본은 추정하지 않고 재개 시도를
  별도로 기록한다.

[운영 절차](../../../docs/restic-transition-and-retention.md)에 첫 적용 전 새 정기 사본의
생성·검증·보관·검사 연결, 오래된 reader 확인, 최종 정책·코드 고정 후 특정 계획 승인 순서를
명시했다. 다른 프로세스의 import나 외부 복사가 공통 잠금을 지킨다는 것을 코드 해시로
증명할 수는 없다. 해당 점검은 첫 실제 적용 직전에 수행해야 한다.

## 검증과 반영

[관련 테스트 14개](retention-guards-tests.txt)가 **전부 통과**했다(208.78초).
[JUnit 결과](retention-guards-tests.xml), [검증 범위](validation.json)를 보존한다.

- 새 9개: 실행 소스·의존성 변경과 import 이후 파일 변경, 정책·코드·옛 계획 거부,
  유지/후보의 snapshot 연결 변경 거부, 음수 공간 변화와 사후 측정 실패.
- 기존 정리 통합 5개: 72시간 경계, 실제 정리 후 다음 daily·restic 연결과 중복 방지,
  강제 종료 5개 지점의 재개, 예상 밖 파일 보존과 보호 조건 거부, snapshot 소실 등을 재확인.
  이 격리 실행에 새 코드·시각·공간 기록 검사를 함께 추가했다.
- `packages scripts tests` Ruff, 변경한 Python 4개 파일의 포맷 검사와 코드·문서·이번 증거의 diff 공백 검사 통과.
  이전 전체 434개 시험의 기록은 유지하며, 이번에 전체 suite를 다시 실행했다고 주장하지 않는다.
  함께 커밋하는 10/3 pytest 실패 원문 6개(txt/XML)의 후행 공백 경고는 원문 그대로 보존했다.

Git 이력이 있는 별도 `/tmp` 개발 사본에서 시험했다. [반영 기록](source-install.json)의
00:21:08 KST에 동일한 바이트를 운영 작업 저장소에 옮겼으며, 서비스 재시작은 하지 않았다.
[반영 직후 status](installed-retention-status.json)는 `apply_enabled=false`, `journals=[]`다.
이 status의 Git 식별자는 커밋 전 상태이며, 이후 최종 계획은 커밋된 코드로 새로 생성해야 한다.

## 실제 예약 상태와 미완료 항목

[운영 기록](operations.json)은 00:21:48 KST의 로컬 상태와 실제 예약 receipt를 읽은 결과다.
새 restic 저장소 전체 검사나 복구 시험을 실행한 것은 아니다.

| 항목 | 확인 결과 |
|---|---|
| 최신 정기 daily | 10/3 13:50:28 완료, 최종 소스 반영 전 사본 |
| 최종 10/3 소스 반영 후 restic 예약 | 10/4 00:05~00:05:11 성공, `processed=0` |
| 미보관·미해결 사본 오류·검사 미포함 지점 | 모두 0, active operation 없음 |
| 마지막 전체 데이터 읽기 검사 | 10/3 14:09:04 성공, 운영 지점 7개 포함 |
| 새 코드로 새 정기 daily 생성 → 같은 ID의 예약 보관·검사 | **미완료** |
| 첫 삭제 직전 오래된 reader·외부 복사 점검 | **미완료** |
| 최종 적용 정책의 계획 생성·특정 계획 승인·운영 정리 | **미완료**, 삭제 0건 |

[사용자 systemd 조회](systemd.txt)에서도 두 타이머는 enabled/active waiting, 두 oneshot 서비스의 마지막
결과는 success였다. 다음 daily는 **10/4 13:10 KST**, 조회 당시 다음 restic은 **00:35 KST**다.
첫 후속 점검은 **10/4 14:15 이후**가 적절하다. 완료 시각을 보장하는 뜻은 아니며, 그때 새 사본의
실제 daily·예약 보관·검사 기록과 ID 연결을 확인한다. 처리 0개인 이번 탐색은 새 사본의 전체
운영 흐름을 증명하지 않으며 기존 날짜별 관찰 3/3에 추가하지 않는다.

최종 적용 시에는 기존 독립 복구 증거의 유효성, 현재 저장소 대조와 남길 사본 무결성 검사를
다시 수행한다. 54분의 전체 복구 절차를 매번 반복하거나 과거 미리보기 목록으로 바로 삭제하지 않는다.
