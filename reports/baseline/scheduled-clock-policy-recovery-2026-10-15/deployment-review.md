# T16 수정 후보의 적용 전 검토

대상은 `scheduled-clock-policy-20261015-5b02fc74867e5bab`이며 [manifest](manifest.json)의 파일과 해시로 한정한다.
**후보·격리 검증까지만 완료**했다. 실제 root 인계 실행기나 운영 승인이 준비됐다는 문서가 아니다.
[첫 후보의 적용 계약](../scheduled-clock-policy-2026-10-15/deployment-review.md)의 운영 경계를 유지하고 아래 보완을 연결한다.

## 고정한 변경 범위

8개 system 서비스의 실행 명령과 업무 전용 waiter, topology·bootstrap guard·binding 연결을 바꾸는 검토안이다.
새 wrapper는 감시/기록 장애를 시간 대기로 보내지 않으며, 실제 업무 결과로 요청을 종결한다.
8개 timer의 내용·예약·Persistent/OnActive, 일반 계정 UID, 데이터·기존 잠금·재시도·완료 의미는 유지한다.
첫 후보보다 runtime 파일 18개를 수정하고 `request_contract.py` 1개를 추가했다. [변경 목록](source-review.json).

collector/bootstrap의 strict 정책, Chrony·RTC·polling·시간원, T05 시각/삭제 정책은 변경하지 않는다.
기존 boot ID·closed·보정 이력·baseline·완료 상한·생성 순서·과거 실패 기록도 보존한다.
T15의 승인이나 첫 T16 후보의 해시를 이번 적용 승인으로 사용하지 않는다.

## 실제 관리자 환경에서 보충할 접점

1. 고정된 세 실행본과 wrapper를 시험용 root 경로에 설치하고 UID 1000·최종 보호 옵션에서 import/설정·저장·공통 잠금 접근을 확인한다. 가상환경 경로 이동과 파일 권한은 실제 설치 경로에서 확인한다.
2. 시험 유닛에서 명시적 시각 보류와 기록/감시 오류의 종료를 구분한다. 실제 systemd의 종료 제한 안에서 monitor 종료와 최종 request 저장이 수행되는지 확인한다. 운영 시간을 바꾸거나 8개 업무에 장애를 주입하지 않는다.
3. 해당 요청의 pins, 입력 digest, 결과 참조, 시도 기록을 보존한 상태에서 다음 invocation을 시작해 복구를 확인한다. 기존 형식 또는 다른 설정의 pending 요청은 자동 삭제/재등록 없이 거부해야 한다.
4. 그 결과와 실제 현재 boot·유닛·소유권·해시·대기 job을 고정해 새 인계 실행기/계획을 검증한다. handoff 잠금은 전체 인계, coordinator 배타 잠금은 짧은 구성 전환에 사용한다. 실행 중 backup의 완료 후처리와 종료 대기가 서로 막히면 안 된다.
5. 새 waiter·8개 유닛·topology/profile/binding·ledger의 불완전한 조합에서는 새 시작을 보류하고, 중단·재개·원복을 시험한다. 기존 collector supervisor는 중지하지 않는다.

현재 17개 유닛 검사는 실행 경로를 시험 후보로 치환한 native 구문·순서 검증이다. 위의 실제 system 실행·권한·종료 시험을 대신하지 않는다.

## 요청과 원복

이번 요청 형식은 `scheduled-request-v2`다. 종료 코드와 실제 자료 완료를 분리하며, `finalization_failed`는 업무 저장이 실패했다는 단정이 아니다. 같은 설정과 결과 해시를 대조해 이미 저장된 결과만 종결할 수 있다. 자료·보고서·원장·T05 근거를 되돌리거나 지우지 않는다.

구버전 실행기는 새 요청 이력을 자동 해석하지 않는다. 원복 전에 다음을 대조해 필요한 요청만 정확히 인계한다.

- 저장된 결과가 검증 가능하면 해당 backup ID·원장/보고서와 요청 종결을 연결한다.
- 업무가 실제 실행 중 또는 대기 중이면 중복 발행하지 않는다.
- 미완료인 고정 날짜/범위는 새 날짜로 바꾸지 않고 보존한다. 구버전으로 안전하게 처리할 구체적인 명령 또는 명시적 보류 사유를 남긴다.
- 기록 실패로 결과가 불명확하면 자동 반복이나 추정 완료 대신 남아 있는 업무 근거를 점검한다.

원복 시험은 새 request/attempt·system receipt·원장·T05 근거가 남은 상태에서 수행해야 한다.
부팅 보정 권한을 재개방하거나 T05 목록을 다시 등록하지 않는다. 구버전으로 돌아가면 reference age 600초의 strict 대기도 돌아온다.

## 적용 후에만 확인할 사항

별도 승인 후 실제 기동·중복 방지, 업무별 첫 처리/보류와 회복, 다음 정기 backup/T05/system restic 연결, 같은 supervisor의 자연스러운 child 경계를 확인한다.
시작 요청 성공을 실제 자료 완료로 표시하지 않는다. 정상적으로 발생하지 않은 실패를 운영에서 만들거나 기존 전체 복원 검증을 반복하지 않는다.

보조 요청·관측 이력 전체의 백업/회전, 현재 시각 미확인 진단, 나머지 600초 의존성 및 polling 복원은 후속이다.
T05 삭제 계획·수동 적용·반복 자동화 승인은 포함하지 않으며 네 자동 정리 mask를 유지한다.
