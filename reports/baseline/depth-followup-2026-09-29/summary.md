# 2026-09-29 호가 품질 후속 분석

9/28·9/29 점검에서 남긴 미재구성 **101개·102개**와 새 가격 범위 소진 2건을 조사했다.
3개 완료 세션을 9/29 daily 사본에서 읽기 전용으로 재생하고 원문과 대조했다.
주 분석은 **9/29 18:44:02~18:48:49 KST**에 수행했다.

**수신 원문·표준 파일의 누락이나 값 불일치는 확인되지 않았다.** 101개·102개는 저장된
증분을 유효한 기준 호가장에 연결하지 못한 구간이다. 두 초기 연결 실패는 실제로 필요한
연결 증분이 없었으며, 이후 약 10초의 미복원 구간에는 현재 재시도 대기 정책이 영향을 줬다.
별도의 범위 소진 2건은 정상 갱신 후 5초가 되기 전에 발생했다.

기존 최근 이벤트 버퍼가 실제 복구에 사용된 두 사례를 독립 계산으로 확인했다.
따라서 기존 복구 보강이 실패 판정을 숨긴다는 근거는 없지만, **초기 동기화 재시도와 급변 시
범위 갱신 주기는 추가 개선 대상**이다. 이번 작업에서 운영 복원 코드·설정은 변경하지 않았다.

## 101개·102개의 발생 원인

둘 다 **15분 계획 회전 후 새 소켓**에서 발생했다. 첫 메시지를 먼저 받고 REST를 요청하는
초기 버퍼 절차는 실제 원문·요청 시각으로 확인됐다. bootstrap 원문의 첫 메시지 바이트와
증분 journal의 첫 메시지도 동일하다. 반환된 anchor의 ID가 그 첫 증분보다 뒤처져 있었다.

| 항목 | 9/28 12:29 KST | 9/29 02:03 KST |
|---|---:|---:|
| 이전 소켓 마지막 `u` | 11675541626712 | 11681741036339 |
| 새 snapshot `lastUpdateId` | 11675542716168 | 11681741470964 |
| 새 소켓 첫 `pu` | 11675542721465 | 11681741471631 |
| 새 소켓 첫 `U` | 11675542721528 | 11681741471761 |
| 첫 증분 T − snapshot T | 113ms | 103ms |
| REST 요청→응답 | 64.24ms | 62.92ms |
| 미재구성 증분 수 | 101 | 102 |
| 첫 수신→다시 동기화한 증분 수신 | 10.365초 | 10.364초 |

두 경우 모두 **이전 소켓 마지막 u < snapshot ID < 새 소켓 첫 U**다. 해당 세션에 수집된
이벤트로 snapshot을 연결할 수 없으며, 버퍼가 이미 받은 이벤트를 잘못 버린 경우가 아니다.
서로 다른 소켓의 이력을 이어도 이 빠진 연결 증분이 생기지는 않는다.

처음 연결할 때는 `U <= lastUpdateId <= u`가 필요하고, 이후에는 `pu == 직전 u`가 필요하다.
이 조건을 완화하지 않은 것은 [공식 USD-M 호가장 절차](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/websocket-market-streams/How-to-manage-a-local-order-book-correctly)에 맞다.
두 T 값의 차이는 거래소 자료끼리의 비교다. REST 요청 시간이 10초 걸렸던 것이 아니며,
내부 스냅샷 생성·전달 경로의 어느 부분에서 지연됐는지는 이 자료로 단정하지 않는다.

첫 실패 뒤 수집기는 같은 소켓의 원문을 계속 저장하고 **10초 후 새 anchor를 요청**한다.
그래서 약 10.16초 동안 수신한 101개·102개 증분이 미재구성으로 남았다. 새 anchor를 받은 뒤
다시 ID가 연결됐지만 이전 구간의 품질은 소급 변경하지 않았다. 해당 저장 자료만으로는
이 구간의 완전한 과거 호가장을 확정할 수 없다.

**초기 실패와 긴 대기 시간은 구분해야 한다.** 첫 anchor가 뒤처지는 것은 원천·연결 경계의
문제이며, 최초 재시도까지 10초 기다리는 것은 수집기의 정책이다. 짧은 최초 재시도로 공백을
줄일 여지가 있지만, 그 시각의 REST 응답을 당시 수집하지 않았으므로 개선 후 복구 시간이나
예방 건수를 이번 원문만으로 확정할 수는 없다.

## 새 가격 범위 소진 두 건

두 경우 모두 직전 REST 대조가 정상이며 가격 범위 갱신도 성공했다. 그 뒤 급격한 변화로
알려진 범위 안의 매도 호가가 모두 없어졌다. 실패 이벤트의 원문 절대 수량을 별도로 적용해도
매도 측이 비어, 실제 범위 소진 판정과 일치했다.

| 항목 | 9/29 01:16:44 KST | 9/29 02:11:29 KST |
|---|---:|---:|
| 마지막 정상 갱신 응답→실패 증분 수신 | 4.583초 | 4.825초 |
| 실패 직전 알려진 매도 호가 수 | 74 | 27 |
| 실패 직전 매도 가격 범위 여유 | 14.1 USDT | 5.3 USDT |
| 실패 이벤트 적용 후 알려진 매도 호가 수 | 0 | 0 |
| 500개 미만을 처음 관측한 시점→실패 수신 | 2.721초 | 3.661초 |

현재 선제 갱신은 한쪽 호가 수가 임계값 아래로 내려가도 마지막 요청 처리 후 **최소 5초**를
기다린다. 이 두 사례는 그보다 먼저 소진됐고 미완료 검증 스냅샷이 갱신을 막고 있지도 않았다.
따라서 호가 수 임계값만 조정하는 것으로는 이 5초 제한이 해소되지 않는다.

스냅샷은 양쪽 최대 1,000호가이고 이 크기의 요청 weight는 20이다.
[공식 REST 한도](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/market-data#order-book)
범위 바깥에서 일부 가격 변경을 받았다는 사실만으로 그 바깥의 전체 호가가 알려진 것은 아니다.
갱신 정책은 정확한 알려진 범위를 유지하면서 요청 한도와 남은 호가·가격 여유를 함께 고려해야 한다.

표의 간격은 애플리케이션 수신 시각 기준이다. 큐 대기·처리 지연을 포함하므로 네트워크 지연으로
해석하지 않는다. 더 이른 REST 요청이 두 실패를 모두 예방했을 것이라는 주장은 하지 않는다.
실패 직전 추이는 두 `*-trace.csv`와 각 수집의 결과 JSON에 보존했다.

## 기존 버퍼 복구가 실제로 한 일

범위 소진 직후 받은 새 anchor도 이미 수신한 증분보다 뒤처져 있었다. 기존 최근 이벤트 버퍼가
이때 실제로 사용됐다.

| 사례 | 새 anchor를 연결한 실제 sequence | 독립 계산 결과 |
|---|---|---|
| `884a…`, epoch 1→2 | 16839, **16840** | 알려진 범위 전체의 가격·수량·최종 ID 일치 |
| `d915…`, epoch 2→3 | 13547, 13548, 13549, **13550** | 알려진 범위 전체의 가격·수량·최종 ID 일치 |

굵게 표시한 것은 범위 소진을 유발한 증분이다. 실제 보존 한도와 같은 소켓 범위를 재현해
`anchor_history`와 대조하고, `Book.apply`를 호출하지 않는 별도 원문 계산으로 전체 알려진
호가를 확인했다. 사용한 증분은 모두 새 anchor 전에 이미 수신한 것이다.
**9/26 복구 보강이 해결하려던 경로는 이번 실제 사례에서도 동작했다.** 초기 연결 두 건은
이와 달리 필요한 증분 자체를 그 소켓에서 받은 적이 없어 동일한 방법으로 해결할 수 없다.

기존 실패 자료·품질 판정과 restic의 날짜별 병행 관찰은 그대로 유지한다.
