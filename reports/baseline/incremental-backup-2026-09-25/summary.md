# 증분 저장·두 번째 SSD 백업 전환 — 2026-09-25

원문·표준 데이터·과거 revision·스냅샷·백업을 무기한 보존하면서, 반복되는 전체 파일 복사를
백업 사본끼리의 하드링크 재사용으로 줄였다. 원본과 복원본은 백업과 파일을 공유하지 않는다.
사용자가 지정한 두 번째 SSD를 실제 목적지로 연결했으며 기존 로컬 백업도 그대로 보존했다.

## 실제 저장·복원 검증

목적지는 `/mnt/backup/marketdata-historical/automatic/2026-09-25/`다.
`/mnt/backup`은 ext4인 `/dev/nvme1n1p1`이며 원본의 `/dev/nvme0n1p7`과 다른 SSD다.
기존 `/etc/fstab`의 UUID 마운트 설정을 확인했고 변경하지 않았다.

| 항목 | 첫 사본 `initial` | 두 번째 사본 `linked` |
|---|---:|---:|
| 카탈로그 기준 시각 UTC | 00:20:42 | 00:22:37 |
| 파일 수 | 30,453 | 30,572 |
| 전체 파일 내용 바이트 | 6,071,500,012 | 6,074,077,087 |
| 새로 저장한 내용 바이트 | 6,071,500,012 | 290,861,747 |
| 이전 사본 재사용 바이트 | 0 | 5,783,215,340 |
| 재사용 파일 수 | 0 | 30,452 |
| writer 잠금 시간 | 0.623초 | 0.765초 |

두 번째 사본은 전체 복사 대비 추가 파일 내용 저장량을 **95.21%** 줄였다. 약 2분 간격의
검증 사본 비교이며 매일 같은 절약률을 보장하지 않는다. SQLite 카탈로그는 매번 독립 복사하고
새 시장 데이터도 추가 저장한다. 두 사본을 합친 고유 inode의 할당 바이트는 **6,447,296,512**다.
이 수치는 manifest를 포함하고 디렉터리 블록은 제외하며, 파일 내용 바이트와 기준이 다르다.

- 첫 백업 ID: `e6d4a8f8936990f158cb5a8cc91f419a933eb0f19610e5c4ad30c71a877a2240`
- 두 번째 ID: `a3f90efe758c2bc584d7e57e5ec1b5e98b8384637e65e5e547591699d5b9636c`
- 두 번째 사본을 `restore-checks/incremental-2026-09-25/`에 독립 복사로 복원했다.
  UTC 00:26:17에 모든 파일의 해시, SQLite 무결성·참조, ZIP 묶음·멤버 검증을 통과했다.
- 파일 **30,572개**의 inode를 대조했다. 재사용한 **30,452개**만 백업끼리 공유하고,
  카탈로그·원본·복원본은 독립적이다.
- 스냅샷 **20개**, 각 데이터셋의 처음 최대 24시간인 **107개 구간·109,497행**을 원본과
  복원본에서 조회해 모든 열이 일치했다. 전체 기간을 다시 조회한 검사는 아니다.
- aggTrade·depth의 처음·마지막 표본 세그먼트 **4개·1,060행**, 원본 파일 표본 **10개**도
  일치했다. 기존 호가의 partial 상태나 과거 결측을 정상으로 바꾸지는 않았다.
- 복원 시 수집 서비스는 시작하지 않았다. 운영 aggTrade·depth는 계속 수신했고 점검 시 healthy였다.

## 자동 운영과 실패 처리

`marketdata-backup.service`의 실제 `ExecStart`를 다음과 같이 전환하고 daemon-reload했다.

```text
marketdata --root . maintenance --mode daily --min-free-gib 10 --incremental \
  --backup-dir /mnt/backup/marketdata-historical/automatic --backup-mount /mnt/backup
```

기존 매일 UTC 04:10 / 한국 시각 13:10 예약을 유지한다. 당일 완료 사본은 전체 검증 후
재사용하며, 다음 날짜부터 이전 날짜의 완료 사본을 이용해 새 복구 지점을 만든다.
목적지 디렉터리·마운트가 없거나 공간이 부족하면 실패하고 로컬 경로로 대체하지 않는다.
서비스와 상태 명령 모두 원본·백업 목적지의 공간을 확인한다. 외부 메시지 알림은 설정하지 않았다.

실제 systemd 서비스를 수동으로 시작해 daily 경로 전체를 실행했다. UTC 00:24:46~00:31:27에
원본의 **170,715개 항목 전체 검증**을 통과하고 당일 첫 사본 `initial`을 재검증·재사용했다.
자동 실행 설정은 증분 모드지만 이번 당일 재시도는 새 사본을 추가하지 않는 경로를 검증한 것이다.
증분 사본의 실제 생성·복원은 위의 `linked` 검사로 확인했다. 종료 시 두 번째 SSD의 여유는
**949,076,668,416바이트(약 883.9GiB)**였다.

UTC 00:29:46의 hourly 작업은 진행 중인 daily의 유지보수 잠금 때문에 실패 기록을 남겼다.
기존 120초 재시도로 00:31:46~00:31:54에 정상 완료했고 최종 `maintenance-status`는 healthy였다.
이 일시적 잠금 충돌은 수집 중단이나 데이터 오류가 아니다. 전체 6개 타이머와 스트림 서비스의
활성 상태를 확인했고 다음 백업 예약은 한국 시각 2026-09-25 13:10이었다.

## 코드 검증과 한계

전체 테스트 **225개 통과**, Ruff 검사·형식 검사·diff 검사·systemd 유닛 검증 통과.
추가 테스트는 원본/이전 사본 손상, 하드링크 실패·중단, 용량 산정, 이전 경로 제거 후 복원,
format 1/2 호환, 목적지 누락·마운트 누락, 다른 저장소 사본의 오인 재사용 거부를 확인했다.
고장·연결 단절은 임시 저장소와 모의 조건으로 시험했으며 운영 SSD를 분리하거나 손상시키지 않았다.

하드링크로 공유한 파일이 손상되면 관련 복구 지점들이 함께 영향을 받는다. 전체 해시 검증으로
이를 검출하지만 복구용 독립 사본을 추가로 만드는 기능은 아니다. 두 번째 SSD는 첫 SSD의
장치 고장에 대비하며, 같은 PC의 고장·사고와 분리된 원격 또는 별도 장비 사본은 아직 없다.
보존 기간과 자동 삭제 정책은 바꾸지 않았다. 파일 일부의 중복 제거와 검증 읽기량 감소도 범위 밖이다.

## 근거

- `initial.json`, `linked.json`: 실데이터 생성 결과와 저장량·카탈로그 행 수.
- `restore.json`, `readback.json`, `readback.py`: 독립 복원 결과, inode·조회 대조와 재현 스크립트.
- `maintenance-daily.json`, `maintenance-hourly.json`, `maintenance-retry.txt`,
  `maintenance-status.json`, `service-status.txt`, `timers.txt`:
  실제 daily 실행 완료와 적용된 서비스·예약 상태.
- `aggtrade-status.json`, `depth-status.json`, `storage.json`: 수집과 로컬 저장 용량 점검.
- `validation.json`, `tests.xml`: 코드·유닛·전체 manifest 해시와 테스트 기록.

여기의 `initial.json`과 `linked.json`은 결과 요약이다. 전체 파일 목록은 SSD의 각 백업
`backup.json`에 있으며 Git 보고서가 시장 데이터 백업을 대신하지 않는다.
[운영 절차와 백업 범위](../../../docs/backup-and-storage.md)를 함께 참고한다.
