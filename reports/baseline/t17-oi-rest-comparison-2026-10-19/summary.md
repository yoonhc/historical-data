# T17 · 같은 날짜의 REST 원문과 archive 비교

**10/15 UTC 자료는 REST에서도 품질 문제가 확인됐다.** 기존 `quarantined_zero_oi` issue 25가 가리키는 query manifest와 실제 REST 응답을 읽었다. 그 응답에는 **금액이 0인 행 6개**가 있고, 기존 비교 가설인 `REST label = archive label + 5분`으로 문제 구간을 대응시키면 archive의 수량·금액과 모두 일치한다. archive에서 수량·금액이 모두 0인 다른 8개 label에 대응하는 행은 **해당 REST 응답에 없다.** 정상 REST 자료로 바로 대체할 근거는 확인되지 않았다.

이번 확인은 저장된 한 REST 응답·그 격리 기록·현재 active revision·기존 정기 품질 보고서에 한정한다. API를 새로 호출하거나 모든 과거 REST 응답을 전수 조사하지 않았다. 운영 원장·자료·설정·정책·서비스 변경은 없다.

## 현재 비교 기능

설치된 `oi_quality.parity_report()`는 두 series의 정상 게시 자료에서 **수량과 금액의 정확한 수치 일치**를 각각 비교한다. archive의 각 label에 대해 REST label의 **−5분·동시각·+5분** 세 경우를 계산하며, 기본 검토 가설은 +5분이다. 저장 시각 자체는 이동하지 않고 단위·시간 의미가 동일하다고 인증하지 않는다.

비교는 누락, 수치 불일치, blocking issue를 구분한다. blocking issue가 있으면 같은 숫자가 보여도 정상 일치로 세지 않는다. 별도의 관측 부분에서는 REST 응답의 값 변경·등장/소멸·관측 공백도 점검한다. 현행 정기 실행은 KST 12:40에 완료된 최근 7 UTC일을 대상으로 한다.

10/19 12:40의 기존 보고서 `reports/oi-quality/20261019T034000-ecbc1b3053c3/report.json`에서 10/15는 세 시각 가설 모두 **expected 288 / comparable 0 / blocked 288**이다. 따라서 정식 품질 결과는 이 날짜를 두 자료의 정상 일치나 288건 불일치로 판정한 것이 아니라 **품질 문제로 비교 보류**한 것이다. 이번 원문 대조로 그 결과를 덮어쓰지 않았다.

## 실제 저장 근거

| 근거 | 값 |
|---|---|
| REST issue | 25 / `quarantined_zero_oi` / `blocking=1` / `resolved=0` |
| query manifest | `f94c97c2a5e53997294be6163ce33da543d759bf19170db37bada478e053e9f3` |
| 실제 REST 원문 | `7d0cca001b0e1fd9a108919edb6d5e2390656437fc811829571fb631855b3920` |
| fetch | 1078289 / HTTP 200 / `2026-10-15T16:59:10.124418+00:00` 수신 |
| 요청 | `openInterestHist`, BTCUSDT, period 5m, 13:45–16:59:10 UTC 범위 |
| 응답 | 5,047바이트·30행 / 수량 0인 행 없음 / 금액 0인 행 6개 |
| 현재 정상 게시 REST | revision `3353a60b8ff95a8fbb751da4a754fbfb17a3f2c61dd831888bb6203baf36fa5f` |
| 정상 게시 범위 | UTC 00:00–13:40, 165행 / 하루 격자 288행 중 일부 |
| 정상 게시 파일 SHA-256 | `a43f29220ba852b39c8b85c7f546a606b1ed9861001f6b11e8f7e959c713a0a1` |

manifest는 원문 응답 자체가 아니라 요청 범위와 source ID를 연결한 기록이다. [manifest 사본](rest-query-manifest.json)에서 [실제 REST 응답](rest-response.json)으로 연결한 뒤 각각 카탈로그 해시와 대조했다. 설치된 `normalize_rest()`로 이 응답을 해석한 6개 `zero_oi`가 저장 issue의 세부 내용과 정확히 같다. 정상 게시 Parquet도 파일 해시와 165행을 읽어 확인했다.

기존에 게시된 앞부분 165행은 유지되고, 문제가 있는 후속 batch는 격리됐다. 원문 수신과 날짜 전체의 정상 게시 완료는 서로 다르다. 165행이 보인다는 이유로 이 날짜의 REST 전체를 정상이라고 판단하지 않는다.

## 문제 구간의 원문 대응

다음은 **+5분 비교 가설 아래** 저장 원문을 대응시킨 결과다. 실제 시각 의미를 확정하거나 시계열을 이동한 것이 아니다.

| archive UTC label | 대응 REST UTC label | archive 상태 | 저장 REST 응답 |
|---|---|---|---|
| 13:40 | 13:45 | 수량·금액 0 | 해당 행 없음 |
| 13:45 | 13:50 | 금액 0 | 수량·금액 동일 |
| 13:50 | 13:55 | 금액 0 | 수량·금액 동일 |
| 13:55 | 14:00 | 수량·금액 0 | 해당 행 없음 |
| 14:00 | 14:05 | 금액 0 | 수량·금액 동일 |
| 14:05 | 14:10 | 수량·금액 0 | 해당 행 없음 |
| 14:10 | 14:15 | 수량·금액 0 | 해당 행 없음 |
| 14:15 | 14:20 | 금액 0 | 수량·금액 동일 |
| 14:20 | 14:25 | 수량·금액 0 | 해당 행 없음 |
| 14:25 | 14:30 | 수량·금액 0 | 해당 행 없음 |
| 14:30 | 14:35 | 금액 0 | 수량·금액 동일 |
| 14:35 | 14:40 | 수량·금액 0 | 해당 행 없음 |
| 14:40 | 14:45 | 수량·금액 0 | 해당 행 없음 |
| 14:45 | 14:50 | 금액 0 | 수량·금액 동일 |

예를 들어 archive 13:45의 `91641.4350000000000000 / 0E-16`은 REST 13:50의 `91641.43500000 / 0.00000000`과 Decimal 값이 같다. 요청 범위 전체에는 이 문제 구간 밖의 **14:55 label도 빠져 있으므로**, 전체 응답 누락 수는 8개가 아닌 9개다. 여기서는 문제 구간에 해당하는 8개와 구분한다.

이 응답에 행이 없다는 사실만으로 다른 시점의 모든 응답에도 영원히 없었다거나, 거래소가 특정 이유로 행을 제거했다고 추정하지 않는다. 두 경로의 실제 시장 값·단위·시간 의미를 인증한 결과도 아니다.

## T17에 미치는 의미

T17에서 먼저 특정한 acquisition은 archive이지만, **같은 날짜의 REST 역시 정상 대체 자료로 확보된 상태가 아니다.** 두 경로에 0값/누락이 있는 관측을 함께 기록한다. 현재 원본 수정 확인 대기와 기존 품질 조건을 유지하며, 두 series 합치기·보간·0값 허용·강제 완료는 수행하지 않는다.

정확한 값·원본/보고서 해시·fetch·issue·설치 함수와 검증 결과는 [대조 JSON](comparison.json), 파일 목록은 [artifact 목록](artifacts.json)에 있다. DB는 `mode=ro`·`query_only`로 읽었고 연결별 변경 수는 0이다.
