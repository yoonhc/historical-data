## 예약 판별 오류와 수정

이 호스트에서 systemd가 첫 타이머 실행의 `TRIGGER_TIMER_*` 환경변수를 다음 실행에도
재사용했다. 기존 코드가 이 값을 현재 타이머 시각과 대조하면서 `unconfirmed_service`로
분류했다. 보관은 성공했지만 날짜 집계와 첫 자동 복원 선택이 진행되지 않았다.
초기 설치 시험에서 첫 타이머 실행까지만 확인하여 반복 실행의 이 차이를 놓쳤다.

수정 후에는 현재 PID·invocation ID·oneshot 유형을 확인하고, **현재 start Job**의
`ActivationDetails`에서 타이머와 두 trigger 시각을 읽는다. 해당 Job의 서비스·실행 상태와
타이머의 realtime/monotonic 시각을 대조하고 원래 응답을 영수증에 보존한다. 환경변수는 진단
용도로 남긴다. 증거 누락·불일치와 수동 실행은 계속 집계에서 제외한다.

근거는 [v255 Unit의 이전 activation details 유지](https://github.com/systemd/systemd/blob/v255/src/core/unit.c#L1820),
[현재 Job에 타이머 시각을 전달하는 코드](https://github.com/systemd/systemd/blob/v255/src/core/timer.c#L561),
[Job의 D-Bus 속성](https://github.com/systemd/systemd/blob/v255/src/core/dbus-job.c#L126)와
이 호스트의 실제 재현 결과다.

- 관련 테스트 **38개 통과**, 실패·오류·skip 0. [테스트 XML](tests.xml)
- 별도 시험 타이머에서 예약 2회와 수동 1회 정확히 분류. 오래된 환경변수의 재사용도 재현했다.
  [시험 결과](isolated-systemd-probe/result.json), [시험 코드](probe.py)
- 운영 **15:35·16:05 예약 실행 모두 `verified_timer`**, 종료 코드 0.
  두 실행 모두 새 처리 0건이므로 날짜 집계에 포함하지 않았다.
  [15:35 증거](corrected-scheduled-receipt.json), [16:05 증거](latest-scheduled-receipt.json)
- 16:05 실행은 최종 수정 소스 해시와 일치하며, 이미 끝난 복원 시험을 다시 만들지 않았다.

13:35의 현재 Job 증거는 당시 저장되지 않았고 완료된 Job은 조회할 수 없다. 원래 영수증을
수정하거나 예약 시각과 일치한다는 이유로 소급 집계하지 않았다. 관찰 초기화나 시작 시각 변경도
하지 않았다. 오늘의 사본은 저장·검사·복원 가능한 사본으로 남으며, **예약 성공 3개 날짜의
집계에는 포함하지 않는다**.

## 명시적 ID의 수동 복원 시험

관찰 시작 후 새로 만들어져 저장·전체 검사된 위 ID를 명시적으로 선택했다. 수동 선택과 시도를
관찰 상태에 먼저 기록하는 `restic_schedule restore-check --snapshot-id` 경로를 추가했다.
이 경로는 날짜 집계를 올리지 않으며 이전 사본·짧은 ID·미검사 스냅샷·기존 선택 변경·통과한
시험 반복을 거부한다. 실패 시 증거를 남기고, 자동으로 대용량 복원을 반복하지 않는다.

실행은 **15:37:55 ~ 16:04:39 KST**, 수동 1회·자동 0회다.

| 단계 | 확인 결과 |
|---|---|
| restic 추출 `--verify` | 통과, 원래 manifest SHA-256 일치 |
| 프로그램 백업 검증·다른 경로 복원 | 35,795개 파일과 카탈로그·pack 검증 통과 |
| 조회 대조 | 스냅샷 manifest 20개, 조회 107개, 이벤트 조각 4개, 원문 10개 일치 |
| 체결·호가 표본 | 10분 체결 6,397건과 닫힌 호가 세션 35,585행 재생 일치 |

원본 daily 검증과 복원본 전체 검증의 건수는 다르다. daily 검증 중에도 수집이 계속되므로
검사와 checkpoint의 관측 시점이 다르다. 복원본 검사는 고정된 checkpoint의 전체 항목을 확인했다.

새 시험 작업 경로는
`/mnt/backup/marketdata-restic-restore/0cc942c867b34ba1b561fc4f7e6d1dca/`이며,
그 아래 `extracted`, `store`, `new-backup`을 각각 만들었다. 새 독립 백업 ID는
`1c2e5a8912b004e9d7ee781c703e29c4bca53c34c4809b49e98823541ac8b61e`다.

원래 manifest의 source root는 기존 프로젝트 경로 그대로이고, **새 백업**의 source root만
실제로 복원한 `.../store`다. 출처 검사·manifest를 고쳐 통과시키지 않았다.
복원 저장소에서 수집 서비스를 시작하지 않았다.

호가 동기화 상실 및 상태 조회 오류는 0이다. 정기 세션 교체는 있었다.
마지막 수신 시각 이후 경과의 최댓값은 체결 16.77초, 호가 11.08초다. 이 값에는 카탈로그

[관측 원문](monitor.jsonl)

별도로, 관찰 시작 이후 세션 보고서를 15:41 KST에 읽었을 때 체결 17개 세션에 오류 기록은
없었고, 호가 17개 중 **3개가 partial**이었다.

- 09:21:01·14:38:51 KST: 알려진 호가 가격 범위 소진, 같은 소켓에서 새 epoch로 재동기화.
- 12:29:51 KST: 지연된 초기 스냅샷의 연결 증분이 없어 101개 메시지를 재구성하지 못한 뒤
  같은 소켓에서 재동기화. 해당 세션의 보고서상 수신 35,223개 모두 원문에 저장되어 있다.
- 3건 모두 `partial`과 과거 오류를 보존했다. 오늘 백업에 들어 있는 앞의 2개 문제 세션을
  추출본에서 재생해 당시 결과와 일치함을 확인했다. 재생 결과도 `valid=false`,
  `continuous=false`이며 품질 실패를 정상으로 바꾸지 않았다.
