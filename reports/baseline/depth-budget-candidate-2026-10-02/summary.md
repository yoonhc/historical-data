# 호가 조회 보류 기록과 긴급 예산 후보 비교

2026-10-02에 **격리 구현과 검증을 완료했고 운영에는 적용하지 않았다**.
추가 조회 12회 중 2회 또는 4회를 긴급 상황에 남기면 유리한 경우가 있었지만,
일반 조회를 늦춰 기존 방식보다 나빠지는 반례도 확인했다. 따라서 예약 숫자는 확정하지
않으며, 기존 정책의 24시간 점검 후 **보류 사유 기록을 먼저 적용할지** 판단하는 것을 권한다.

배경은 [이전 운영 감사](../depth-refresh-2026-10-01/summary.md)의 추가 조회 예산 사용 중
범위 소진 사례다. 별도로 기록된 지연 snapshot과 미재구성 증분 12개는 이번 후보로
복구하거나 해결한 항목이 아니다.

기준 소스는 `c8535803df065248bee39dc73587b9b734cdf855`다. 운영 디렉터리가 아닌
`/tmp/marketdata-depth-budget-20261002`에서 구현했다. 검토와 재현에 필요한 변경 전체는
[candidate.patch](candidate.patch)에 보존했고, 운영에 적용하지 않는 `git apply --check`를 통과했다.
원본·과거 판정·daily·기존 백업·시험 사본은 유지했다.

## 구현한 기록과 예산 규칙

조회 필요가 생겼지만 요청을 보류할 때 다음 원인을 직접 구분한다.

| 기록 | 의미 |
|---|---|
| `minimum_interval` | 마지막 snapshot 처리 완료부터 최소 1초가 지나지 않음 |
| `extra_budget` | 해당 수집의 최근 60초 추가 요청 12회를 사용함 |
| `critical_reserve` | 일반 조기 조회 몫은 사용했고 남은 몫을 긴급 상황에 보존함 |
| `pending_verification` | 이전 REST 후보의 동일 ID 대조를 기다리는 중 |
| `not_synchronized` | 현재 호가장의 ID 동기화가 아직 성립하지 않음 |
| `deadline` | 수집 종료 또는 연결 교체 시각에 도달함 |

하나의 평가에 여러 조건이 겹치면 모두 남기되 대표 사유는 하나만 센다. 아직 조회가
필요하지 않은 평상시 평가는 보류로 세지 않는다. flush 전후 재평가도 최종 판단 한 번으로
기록한다. **보류 평가 횟수는 HTTP 요청 수나 서로 다른 장애 횟수가 아니다.**

메모리 크기를 제한하기 위해 누적 카운터, 사유별 최초·마지막 표본, 최근 보류 8개를
수집 보고서에 보존한다. 실제 요청에는 판단 시각·epoch·순번·남은 범위·예산 전후 상태를
REST 성공 또는 오류 원문 메타데이터에 남긴다. 범위 소진 복구 경계에는 당시 보고서의
독립 사본을 고정한다. 모든 보류 평가를 개별 파일로 영구 기록하는 방식은 아니며,
프로세스가 갑자기 죽으면 마지막 보고서 저장 이후의 메모리 집계는 남지 않을 수 있다.

예약 후보는 일반 조기 조회를 최근 60초에 최대 10회 또는 8회로 제한한다. 긴급 조회는
남아 있는 총량을 사용할 수 있으나 **일반·긴급 합계 12회 상한은 유지**한다. 긴급 기준은
한쪽 잔여 호가 개수가 초기 개수의 50% 또는 top의 두 배 중 큰 기준보다 적거나,
알고 있는 가격 여유가 초기 폭의 25% 미만인 경우다. 개수 기준은 초기 개수보다 커지지 않는다.

최소 간격·pending·종료 조건·기존 REST cooldown은 긴급 조회도 우회하지 않는다.
예산은 같은 capture의 epoch·연결 교체에 걸쳐 유지되고 새 프로세스에서는 초기화된다.
정기 검증·복구 anchor는 기존처럼 별도 계수이며 IP 전체의 공통 예산을 추가한 것은 아니다.
후보의 Python API 기본 예약은 **0회**이고 CLI·운영 설정에는 새 옵션을 연결하지 않았다.

## 격리 비교 결과

실제 capture → REST 처리 → 원문 저장 → 표준화 → 재생 경로를 사용했다.
각 가상 시장은 수학적으로 정해진 전체 호가장을 가지며, REST·flush 지연 중에도 증분이
계속 쌓이도록 했다. 동기화된 top 20을 그 update ID의 전체 시장 정답과 비교했다.
현재 정책, 기록 보강과 예약 0회, 예약 2회, 예약 4회를 **11개 시나리오에서 각각 실행했다**.

아래 숫자는 해당 시나리오 전체의 범위 소진·top 부족 재동기화 횟수다.
0회인 실행은 모두 complete이고 1회 이상은 모두 partial이었다.

| 가상 조건 | 길이 | 기존 및 기록 보강 0회 | 2회 예약 | 4회 예약 |
|---|---:|---:|---:|---:|
| 작은 가격 변화 | 35초 | 0 | 0 | 0 |
| 초당 80단계 이동 | 70초 | 0 | 0 | 0 |
| 초당 200단계 이동 | 50초 | 6 | 6 | 5 |
| 반복 왕복 | 35초 | 0 | 0 | 0 |
| 왕복으로 예산 사용 후 급변 | 30초 | 1 | 0 | 0 |
| 일반 조회를 늦추면 불리한 급변 | 25초 | 0 | 1 | 1 |
| 왕복 후 급변과 REST 지연 700ms | 30초 | 1 | 1 | 1 |
| 왕복 후 급변과 flush 지연 150ms | 30초 | 1 | 0 | 0 |
| 예고 없는 1,200단계 점프 | 15초 | 1 | 1 | 1 |
| 2초마다 600단계 이동 | 45초 | 5 | 5 | 5 |
| 반복 왕복 중 10초마다 연결 교체 | 45초 | 0 | 0 | 0 |

불리한 반례에서는 일반 조기 요청을 이미 10회 사용한 뒤, 가상 시각 18.0초에 새 신호가
발생했다. 기존 방식은 즉시 조회했지만 2회 예약 후보는 18.1초의 긴급 신호까지 기다렸다.
REST 지연 250ms 사이에 시장이 더 움직였고, 후보 대조가 끝나기 전에 기존 범위가 소진됐다.
4회 예약도 같은 실패를 보였다. **예산을 남기는 이점과 더 오래된 호가 범위를 유지하는
비용이 함께 존재한다.** 이 반례를 제외하거나 partial을 정상으로 바꾸지 않았다.

반면 충분히 빠른 REST 응답을 받는 왕복 후 급변 사례에서는 예약이 불필요한 조기 요청을
줄여 뒤의 긴급 요청을 가능하게 했다. 이는 의도적으로 구성한 공학적 시험이며 발생 확률이나
실거래소 개선율을 추정하는 표본이 아니다. 과거 운영 장애에 존재하지 않았던 REST 응답을
만들어 넣거나 그 장애를 복구했다고 판단하지 않았다.

## 검증 근거와 한계

- [전체 테스트](tests.xml): **428개 통과, 실패·건너뜀 0개**, 약 285초.
  새 17개 검사는 예산·중복 보류 집계·영속 요청 기록·flush 중 시각 만료·429 오류·
  복구 경계 기록을 다룬다. 기존 restic 실제 임시 저장소 검사도 포함했다.

  시각, 저장 증분 수, 연결·복구·REST 대조와 판정이 같았다. 실제 CPU·디스크 기록 비용이나
  실시간 네트워크 상황의 동등성까지 입증한 것은 아니다.
- 수신·저장 증분 **16,400개**, 원문 대조 **16,955행·가격 수량 쌍 1,595,600개**가 일치했다.
  전체 시장 top 대조는 16,750회이며 모든 실행의 재생은 당시 상태와 일치했다.
- REST 대조는 **432회 일치**, 값 불일치·대조 불가 0회다. 실패 시나리오의 **검증 대기 6개는
  그대로 남았다**. 비교할 REST 검증 자체가 없는 단발 점프 시험도 있으므로 모든 검증이
  완료됐다는 뜻은 아니다.
- 후보의 실제 원문 메타데이터로 최근 60초 총 추가 조회 ≤12, 일반 조회 ≤12−예약을 확인했다.
  70초 실행에서는 전체 요청 수가 12회를 넘을 수 있다. 연결 교체·복구 후에도 같은 rolling
  예산을 적용했다. 가상 수신 큐의 최대 길이는 12개로 설정 상한 128개 이내였다.
- `ruff check`와 `ruff format --check`의 `packages scripts tests` 대상은 통과했다.
  더 넓은 디렉터리 검사에서 확인한 과거 baseline 스크립트의 기존 스타일 문제는 수정하지 않았다.

각 프로세스에 해당 디렉터리의 두 packages 경로와 루트를 PYTHONPATH로 지정해야 한다.
공유 `.venv`의 editable 설치만 사용하면 운영 소스를 잘못 시험할 수 있다.
