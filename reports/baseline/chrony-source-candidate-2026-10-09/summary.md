# Chrony 시간원 후보와 명시적 설정 전환 검증

> **2026-10-09 후속 판단:** T10 시간원 교체를 활성 작업 목록에서 제외했다.
> 시간원 교체를 완료하거나 응답 격차를 해결했다는 뜻은 아니다. 아래는 당시 조사·후보 검증 기록이며,
> 현재의 판단과 재검토 조건은 문서 끝의 「T10 활성 목록 제외」를 따른다.

**설정 전환 도구는 구현·격리 검증·배포본 고정을 완료했다. 시간원 교체 구성은 운영 적용을 권고할 상태에 도달하지 못했다.**
공개 시간원 실측에서 응답이 적은 후보가 많았고, 실제 Chrony 4.5 장애 시험에서도 다른 정상 시간원으로
600초 안에 전환한다는 보장은 확인하지 못했다. 이 한계를 기준 완화나 강제 재선택으로 숨기지 않았다.

운영 설정·Chrony·수집 서비스를 이번 작업으로 변경하거나 재시작하지 않았다.
시각 step·RTC 쓰기·ledger 삭제·재등록·자동 정리 재개도 수행하지 않았다.

## 완료한 후보

최종 도구는 **`clock-config-20261009-c365499dab14a4b1`**이다.
[배포본·재현 결과](release-final.json), [최종 코드](release-final/clock_config_transition.py),
[정확한 적용 범위와 되돌리기](deployment-review.md)에 근거를 남겼다.

- 시간원 행과 연결된 두 프로필 해시만 변경하도록 범위를 제한했다.
- 기존 boot ID·closed·보정 횟수/결과·관측을 보존하며 이전/새 파일·계획·승인·receipt를 연결했다.
- 전환 중에는 버전이 있는 pending ledger를 먼저 fsync한다. 기존 gate가 거부하는 상태에서 파일을 바꾼다.
- 실제 daemon의 새 설정 활성화를 확인한 뒤 설정 전환을 확정한다. 현재 시각 준비 통과는 별도로 판정한다.
- 같은 부팅에서 적용 재개·되돌리기를 지원한다. 다른 부팅에서는 적용 재개를 거부하고,
  bootstrap 정지·비활성화와 기존 보호 파일 유지가 확인된 경우만 이전 설정으로 원복한다.
  원복이 새 부팅 준비 완료나 새 step 권한을 생성하지 않는다.
- 새 helper가 서비스 제어나 시각 변경을 직접 수행하지 않는다. 기존 수집 배포본·gate·runtime은 그대로다.

**최종 관련 회귀 48건, 깨끗한 압축 해제 경로에서 같은 48건을 통과**했다.
파일별 교체·receipt/ledger 경계의 실제 SIGKILL, 재실행과 rollback, 잠금 경합,
승인·코드·파일·증거 불일치, boot ID 변경, 현재 시각 미준비를 시험했다.
이 검사는 일반 계정의 격리 파일과 서비스/provider 대역을 사용했다. 새 helper의 실제 root 쓰기·운영 재시작을 검증했다고 주장하지 않는다.
[검사 결과](transition-tests-final.xml), [clean 결과](clean-transition-tests-final.xml).

실제 운영 파일을 읽는 **삭제·변경 없는 계획**도 생성했다.
계획 ID는 `c36acd75fb6363817da0792ebe61d2a3546c6d427d9d955d1c34f96a09aec057`이다.
[계획](review-plan-final.json), [승인되지 않은 양식](approval.template.json).
현재 설정 입력은 첫 실측 조합을 고정한 검토용이며, 시간원 선정이 바뀌면 이 계획을 재사용하지 않는다.

## 시간원과 장애 시험 결과

[시간원 운영 주체·주소·윤초 정책·응답 실측](source-review.md),
[Chrony 4.5 장애 검증](fault-validation.md), [원문 기반 집계](observation-analysis.json)를 분리했다.

첫 30분 실측에서 Cloudflare는 30/30 응답했지만 NICT·Netnod·PTB는 각각 6/21, 5/19, 3/17이었다.
다른 묶음에서는 국내 Pool 한 주소가 24/24 응답해도 최종 reference age가 1,018.612초까지 늘었다.
국내 Pool 주소는 실제 운영 주체가 미확인이며, 두 국내 주소는 같은 origin ASN이다.
정상 응답·선택 진행·reference 갱신·현재 준비 통과를 서로 같은 결과로 취급하지 않았다.

| 실제 4.5 격리 시험 | 관측 결과 |
|---|---|
| 선택 시간원 완전 무응답 | 장애 후 30분 동안 다른 시간원 선택·새 reference 갱신·준비 회복을 관측하지 못함. 마지막 age 1,796.569초 |
| 선택 시간원 간헐 응답 | 다른 시간원으로 바뀌지 않음. 같은 시간원의 새 응답으로 회복했으나 최대 age 648.354초, 종료 무렵 거부 재발 |

둘 다 다른 세 서버는 계속 응답했다. 600초 이내 자동 전환은 미충족으로 남겼다.
실제 바이너리의 `-x` 관측과 수정하지 않은 품질 계산을 사용했으며, 호스트 시각을 보정하거나
전체 운영 provider gate를 통과한 시험이 아니다. 공개 시간원 실측은 묶음당 30분으로 장기 안정성 근거도 아니다.

Cloudflare의 non-smear는 공식 문서로 확인했다. 나머지 일부 후보는 공식 UTC 서비스·과거 윤초 설명까지 확인했지만
현재 endpoint의 세부 윤초 정책을 명시적으로 확인하지 못했다. 따라서 모두 non-smear라고 단정하지 않는다.
네 DNS 이름·네 주소·서로 다른 ASN만으로 실제 경로와 기준 시계까지 독립적이라고 판단하지 않는다.

## 2026-10-09 후속 판단 — T10 활성 목록 제외

T04·T11은 [19:33:46 KST 실제 운영 반영](../clock-runtime-deploy-2026-10-09/summary.md)을 완료했다.
같은 supervisor의 연속 감시와 다른 조건이 유효할 때 reference age 600초 초과만으로 다음 수집을
차단하지 않는 정책을 적용했으며, 첫 child 전환과 새 시각 근거의 운영 백업·복원 관찰은 아직 남아 있다.

[Chrony 공식 FAQ 3.7](https://chrony-project.org/faq.html)은 선택 시간원이 응답하지 않아도 기존 측정의
추정 오차가 다른 시간원보다 작고 비교 가능한 측정 구간이 남아 있으면 기존 기준을 유지할 수 있으며,
전환까지 수 시간이 걸릴 수도 있다고 설명한다. 따라서 이 문서의 600초 내 전환 미관측 결과를
Chrony 결함이나 시간원 교체의 필수 근거로 취급하지 않는다. 600초는 프로젝트의 신선도 기준이다.

[당시 조사](../chrony-reference-age-2026-10-09/summary.md)의 TX 142 / RX 45 / good RX 45는
특정 시간원의 응답 수신이 다른 세 시간원보다 적었다는 근거다. 정확한 패킷 유실 위치나 서버 고장을
확정하지 않으며, 받은 표본을 Chrony가 거부한 결과와도 구분한다.
[공식 카운터 정의](https://chrony-project.org/doc/4.5/chronyc.html)에 따라 이 관측은 보존한다.
응답이 항상 올 필요는 없지만, 해당 격차가 모든 환경에서 무해하다고 증명된 것도 아니다.
당시 다른 오차 조건은 한계 이내였으므로, 응답 격차만으로 즉시 시간원을 교체해야 한다는 결론은 내리지 않는다.

T10의 상태는 **필수 후속에서 제외·근거 보존**이다. 후보 시간원 구성은 운영에 적용하지 않았으며,
고정 전환 도구·검토용 설정·실측·장애 시험·승인되지 않은 계획을 그대로 보존한다.
T04·T11 전환 후 현재 프로필·ledger 기준이 달라졌으므로 당시 계획을 그대로 적용할 수 없다.
향후 동기화 상실, 현재 추정 오차 한계 초과, 가용 시간원 부족이 반복될 때 시간원 개선의 필요성을 다시 판단한다.
reference age 초과나 응답 누락 자체를 새로운 필수 교체 작업으로 만들지 않는다.

기존 8개 예약 업무와 supervisor 최초 시작의 엄격한 gate는 여전히 별도 범위다.
그 정책으로 생기는 대기를 시간원 교체로 반드시 해결해야 한다고 가정하지 않는다.
이번 정리는 TODO와 판단 기록만 갱신하며 운영 설정·서비스·시각·과거 품질 이력·자동 정리 mask를 변경하지 않는다.
