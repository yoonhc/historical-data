# T13 합의 계약 보존

2026-10-12 고정 범위 운영 검증 완료에 따라 TODO에서 옮긴 **10/11 당시의 계약 메모**다.
링크 경로는 새 위치에 맞췄다. 아래의 미완료/대기 표현은 당시 상태이며, 최종 실제 결과와 범위는 [완료 보고서](summary.md)를 따른다.

아래 상세 메모는 T13 진행 중에는 유지한다. **T13 전체 완료 시 합의사항·결과·분리한 후속의 기록 위치를 확인한 뒤, 활성 T13 항목과 아래 메모를 TODO에서 함께 삭제한다.** 보고서·운영 문서와 별도 후속 항목은 보존한다.

10/10 T13 daily 예약·재시도의 합의 계약은 아래와 같다. **10/11 보완 213개 검증·운영 적용·초기 실행에 이어 첫 UTC 경계·정오/저녁 실제 처리·정오 원장/자료의 checkpoint/restic 편입까지 확인했다. 다음 확인 주기·UTC 경계와 고정한 10/11 시도 26개/완료 근거/자료의 후속 백업·독립 복원은 미완료다.** 활성 T13과 [최종 검증 보고서](../../../reports/baseline/t13-daily-review-2026-10-10/summary.md), [실제 적용·현재 원복](../../../reports/baseline/t13-daily-deploy-2026-10-11/summary.md), [10/11 운영 점검](../../../reports/baseline/t13-operating-review-2026-10-11/summary.md), [범위를 늘리지 않는 최종 완료 계획](../../../reports/baseline/t13-operating-review-2026-10-11/completion-plan.md)을 함께 따른다.
현물 봉·펀딩 및 현물/선물 metadata는 정오 관측을 유지하고, 선물 봉·마크·지수·OI 아카이브는
18시 최초 실행 후 미완료 대상만 20시·22시에 재확인하는 초기안을 운영에 적용했다. 시각은 KST이며 공개 보장 시각이 아니다.
HTTP 계층의 기존 짧은 재시도와 미공개 재탐색을 분리하고, 429 냉각·요청 오류·검증 실패·잠금/시각 준비 보류도 구분한다.
자료 종류·시장·종목·주기·series·UTC 날짜/범위로 대상을 고정하고, 상태·마지막 사유·다음 실행 시각·공개 확인 횟수·통신 시도·저장 근거를 실행 간 보존한다.
미확보 작업은 최근 3일 범위를 벗어나도 소멸하지 않으며, 장기 대기는 낮은 빈도의 재확인과 점검 대상으로 남긴다. 기한 경과를 완료로 바꾸지 않는다.
완료 대상의 당일 재탐색과 최근 3일 수정 확인은 별도 목적이다. 수정 확인도 확인 주기를 식별해 서비스 재실행마다 반복하지 않으며, 수정 확인 실패가 기존 정상 revision을 훼손하거나 새 확인 성공으로 표시되지 않도록 한다.
현행 `operations.plan_tasks`도 정책 시작일 이후의 오래된 누락을 후보로 유지한다. 새 실행기는 그 동작을 보존하고, 재부팅 후 놓친 예약을 연속 재생하는 대신 현재 실행 가능한 작업만 한 번씩 선택한다.
metadata는 날짜 전체의 규칙 복원이 아닌 실제 관측 시각의 성공으로 판정한다. 기동 시 따라잡기도 자료별 최초 실행 시각을 지킨다.
검증된 예상 경로의 404만 미공개 대기로 분류하고, REST/API와 ZIP 호스트의 제한 계약을 구분한다. 동일 ZIP·CHECKSUM의 반복 검증 실패는 증거를 보존한 점검 대상으로 남긴다.
HTTP의 제한 재시도, 작업 관리자의 다음 실행 예약, systemd의 프로세스 복구를 구분하며 중첩 즉시 재시도로 예산을 초기화하지 않는다.
완료 표시는 해당 작업의 카탈로그·검증 저장 근거와 연결한다. 다운로드만 완료한 중단과 저장 커밋 후 상태 기록 전 중단을 나눠 시험하고, 후자는 기존 근거로 복구해 중복 등록하지 않는다.
미공개 재시도와 수정 확인이 같은 대상에 겹치거나 두 실행기가 동시에 기동돼도 기존 잠금을 유지하고, 한 번의 성공 근거를 연결해 불필요한 중복 처리를 막는다.
예정 전·공개 대기·통신 재시도·잠금/시각 보류·검증 완료·점검 필요와 실행기 자체의 종료 결과를 구분한다. 정오 묶음 완료를 전체 daily 완료로 표시하지 않는다.
ZIP/CHECKSUM의 마지막 404→최초 200 관측은 기간을 제한한 별도 조사로 유지하고 수집 재시도 횟수와 혼동하지 않는다.
404의 캐시 가능성을 고려해 관측자에게 보인 구간으로 표현하며, 두 URL의 200만으로 수집 완료를 판정하지 않는다.
당일 미완료는 다음 실행으로 이월하며, 저녁 신규 편입분은 13:10 checkpoint 생성 이후이므로 실제 후속 checkpoint/restic 편입을 별도 확인한다.
`marketdata-backup`의 `maintenance --mode daily`는 갱신용 daily 완료가 아니라 보유 자료의 무결성을 검사하는 현행 구조를 유지한다. 미공개·예정 전 자료 때문에 기존 자료의 백업을 차단하거나 자료별 완료마다 추가 전체 백업을 실행하지 않는다.
