# Daily 재시도와 restic 보관 완료 확인

2026-10-03 **16:16 KST**에 실제 실행 기록을 대조한 결과, 오늘 daily 재시도와 그 사본의
restic 저장·전체 읽기 검사가 모두 정상 완료됐다. 앞선
[호가 원문 감사](../depth-decisions-followup-2026-10-03/summary.md)에서 미완료로 남겼던
백업 점검을 마무리한 기록이다. 이번에는 기존 결과·manifest·journal을 읽었으며,
원본 무결성 검사나 restic 전체 검사·복원 시험을 다시 실행하지 않았다.

|---|---|
| daily 첫 시도 | 13:10:00 시작, 13:10:45 파일 배치 잠금의 `WriterBusy`로 실패 |

첫 시도와 재시도의 journal에 자동 재시작 횟수 1이 기록돼 있다. 최종 daily 보고서가 journal의
완료 메시지와 일치하고, 서비스 결과도 `success`다. 첫 실패를 지우거나 수동으로 작업을
재실행하지 않았다. 원문 감사와 잠금 경합 시각이 겹쳤으나 잠금 보유 프로세스의 신원까지
확정된 것은 아니다. 대량 원문 검사를 13:10 정기 작업과 겹치지 않도록 하는 후속 순서는 유지한다.

완료 사본의 backup ID는 다음과 같다.

```text
e971e8b4b008fd5144f0ee6e8125ace882d2bdf1c6bf9f1fba23f0f5a1ac2e30
```

같은 사본의 restic snapshot 전체 ID는 다음과 같다.

```text
d27a0a557e1795a4651132016491f1b2c6735e8181b71303f3adccd414f0f8ad
```

프로그램의 기존 checkpoint 판독 경로로 원래 `source_root`, backup ID, manifest 해시를
확인했다. snapshot 기준 시각은 **13:47:03.758567 KST**의 checkpoint 시각이며,
실제 restic 저장 완료 시각 14:08:31과 구분된다. 저장 명령의 결과 snapshot ID가 일치하고,
이 ID가 그 직후 성공한 `check --read-data`의 대상 목록에 포함돼 있다.
검사는 새 데이터에 한정하지 않고 기존 사본이 있는 restic 저장소 전체를 읽었다.

**예약 실행과 기존 관찰 완료 상태도 확인했다.**

13:05–16:05의 예약 7회 모두 실행 결과·PID·invocation·현재 start Job·job 완료 메시지가
대응했다. 새 사본을 처리한 실행은 14:05의 1회이고 나머지 6회는 처리 0개 탐색이다.
최근 16:05 탐색도 정상 종료했으며 새 복구 지점이나 새로운 전체 검사로 세지 않는다.
예약 판별은 저장된 환경변수만 믿지 않고 실제 start Job의 ActivationDetails를 사용한
`verified_timer` 기록과 대조했다.

초기 운영 관찰은 이미 9/29·9/30·10/1의 **3/3**으로 완료됐고 그 기록은 유지됐다.
오늘 실행은 신규 사본의 예약 저장·검사 조건을 별도로 재계산해 통과했지만, 이미 완료된
초기 관찰을 4/3 또는 5/3으로 바꾸지 않았다. 기존 운영 snapshot의 복원 검증 1건도 그대로며
오늘 새 복원을 한 것으로 집계하지 않았다.

상태 조회에서 마운트·파일시스템 UUID 확인을 통과했고, 보관 대기 사본과 검사되지 않은 snapshot은
0개다. 보관 상태는 healthy다. 이 상태 조회가 restic 저장소를 다시 전수 검사했다는 뜻은 아니다.
사용자 타이머는 active/waiting이며, 조회 당시 다음 restic 탐색은 **오늘 16:35**,
다음 daily는 **10/4 13:10**이었다. depth·aggTrade 서비스는 실행 중이었다.
