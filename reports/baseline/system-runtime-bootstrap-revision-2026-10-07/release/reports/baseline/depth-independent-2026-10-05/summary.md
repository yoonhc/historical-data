# 두 호가 범위 손실의 독립 계산과 상태 전달 검증

2026년 10월 5일 검증. **두 사건 모두 마지막 REST 범위 교체를 생략해도 부족한 쪽의
가격 단계는 0개가 된다.** 특히 10월 5일 사건은 같은 ID에서 기존 매도 651개와 새
candidate의 공통 범위가 완전히 일치했고, 실제 다음 증분을 적용하면 기존 범위는 0개,
새 범위는 8개가 남았다. 새 매도 범위 축소나 공통 범위 불일치로 이 사건을 설명할 근거는 없다.

별도 격리 시험에서는 **실패 감지 후 보고서 저장 전까지 `depth-status`가 이전 정상
보고서의 `healthy=true`를 반환할 수 있음**을 확인했다. 저장 뒤에는 두 실패 모두 정상적으로
거부되고, 복구 후에도 해당 수집의 `partial`과 재생 `valid=false`가 유지된다. 실제 두 사건의
상태 공개 지연 시간을 측정한 것은 아니다. 운영 코드·요청 정책·서비스는 변경하지 않았다.

별도 취급했다. 두 구간의 증분 ID 연결 8,136개에서 위반은 없었다.

## 실패 증분을 적용한 독립 결과

계산기는 빈 결과도 보존한다. 따라서 예외 후 객체에 남은 이전 Book을 실패 증분의
계산 결과로 오인하지 않는다. 아래 기존 범위 유지 계산은 마지막 채택만 생략하고 실제로
기록된 같은 후속 증분을 적용한 결과다. 더 이른 모든 범위 교체를 생략한 실험은 아니다.

| 사건 | 부족한 쪽 적용 전 | 기존 가격 중 0 수량으로 제거 | 새 양수 가격 추가 | 적용 후 | 마지막 교체를 생략했을 때 |
|---|---:|---:|---:|---:|---:|
| 10월 4일 06:05, 매수 | 997 | 997 | 0 | 0 | 0 |
| 10월 5일 07:16, 매도 | 981 | 975 | 2 | 8 | 0 |

두 번째 사건은 `981 - 975 + 2 = 8`이다. 기존에 남은 6개는 양수 수량이 변경됐다.
공통 범위 일치와 매도 영역 포함 조건이 성립하며, 동일 27517 증분 후에도 기존 결과가
candidate 결과의 부분집합이다. 기존 Book을 유지했어도 top 20을 확보할 수 없었다.

실패 증분 원문에는 첫 사건의 매수 범위 밖 양수 가격 1,597개, 두 번째 사건의 매도 범위 밖
양수 가격 530개도 있었다. 이는 **원문에서 관측한 범위 밖 가격**이며, 그 바깥의 모든 호가가
완전하게 알려졌다는 뜻은 아니다. 이 값을 신뢰 가능한 top 구성에 임의 편입하지 않았다.

첫 사건에서 계산한 매수 0개와 기존 보고서가 보존한 매수 997개는 다른 상태다. 운영은 빈
호가 검증에서 예외가 나므로 이전 호가·ID를 유지한다. 독립 계산 7,374회에는 이 실패 증분의
계산 1회가 포함되며, 운영의 성공 적용 7,373회와 구분한다. 두 번째 사건은 새 8개 Book과
ID가 반영되고 호출부에서 top 부족으로 처리된다. 두 사건 모두 보고서에 실제로 남은
최종 ID·경계·단계 수·top 가격·수량이 독립 결과와 일치했다. 독립 계산의 전체 가격·수량
맵을 기존 형식으로 직렬화한 SHA-256도 두 운영 보고서의 `book_sha256`과 일치했다.

이 결과는 기록된 입력에 대한 범위 소진 경로를 설명한다. 체결·취소 등 거래소 내부 원인,
미관측 범위의 완전한 호가, 더 자주 요청했을 때의 REST 응답까지 규명하지는 않는다.

## 실패 상태가 조회에 전달되는 시점

[격리 재현기](consumer_probe.py)는 실제 collector, Store, `depth.status`, CLI,
`depth.replay`를 사용한다. 거래소 I/O와 시계만 대역으로 바꾸고 저장 전후 관찰 함수를 넣었다.
한쪽 0개와 매도 8개를 분리하고, 정상 보고서가 먼저 저장된 것을 전제로 시험했다.

[소비 경로 결과](consumer-results.json)의 정상 baseline ID는 102, 실패 증분 ID는 103이다.
이는 합성 ID이며 실제 사건의 ID가 아니다. 두 경로 모두 아래 결과를 보였다.

| 관찰 위치 | 수집기 메모리 | 외부 status와 CLI |
|---|---|---|
| 실패 전 정상 보고서 저장 뒤 | 정상 | `healthy=true`, 종료 코드 0 |
| 실패 감지 후 이벤트 저장·보고서 commit 전 | `sync_losses=1`, `synchronized=false` | 이전 저장 보고서의 `sync_losses=0`, `healthy=true`, 종료 코드 0 |
| 실패 보고서 commit 뒤, 복구 REST 전에 | 실패 상태 | `healthy=false`, 종료 코드 2 |
| 같은 소켓 복구 후 | 현재 Book은 동기화·top 충분 | 누적 손실 유지, 상태 거부; 최종 `partial`, replay `valid=false`, 종료 코드 2 |

0개 경로의 실패 보고서에는 이전 정상 Book·ID 102·`top_complete=true`와 Session 오류가
함께 남는다. 8개 경로에는 새 ID 103·`top_complete=false`가 남으며 Session 오류는 없다.
보고서 저장 뒤에는 상위 품질 표시와 CLI가 두 경우를 모두 거부한다.

**최초 차이는 실패를 인지한 메모리 상태와 아직 갱신하지 않은 저장 보고서 사이에 있다.**
`depth_stream.py`의 `renew_coverage()`가 메모리 상태를 먼저 바꾸지만, `flush()`는
`persist_messages()`를 마친 뒤 `save_collection()`을 호출한다. `depth-status`는 저장된
보고서를 읽으므로 그 사이에는 이전 정상 상태가 보인다. `state/depth-latest.json`도 같은
이전 보고서이며 이번 관찰에서 status/CLI/파일의 내용은 일치했다.

회귀 시험은 저장 지연 0초·합성 2초 각각에서 이 경계를 확인했다. **2초는 시험에서 삽입한
값이며 실제 두 사건의 상태 공개 지연 시간이 아니다.** 지연 0초도 저장 전 관찰 지점에서는
이전 보고서를 읽는다. 코드에 저장 순서 차이가 존재한다는 증거이지, 모든 이용자가 그
순간 잘못된 데이터를 받았다는 증거는 아니다.

초기 [bootstrap 관찰](consumer-bootstrap-observation.json)은 정상 보고서가 먼저 저장되지
않아 상태 지연을 판정할 수 없었다. 이를 성공 근거로 쓰지 않고, 정상 baseline을 요구하는
위 시나리오로 보완했다. 기존의 세션 종료 후 품질 검사만으로 이 전파 시점까지 검증됐다고
확대하지 않는다.

현재 `publish()`는 스냅샷·증분 이벤트를 저장하며 정상 top 호가를 제공하는 함수가 아니다.
Freqtrade 어댑터의 시계열 Key 목록에는 `book_depth`가 없어 호가를 연구 특성으로 내보내는
경로도 없다. 따라서 이 발견은 **운영 상태 조회의 공개 지연**이며, 잘못된 최신 top이
Freqtrade에 이미 전달됐다는 증거는 아니다. `replay.valid`와 `verification_complete`도
별도 의미를 유지한다.

## 최소 보완안과 미적용 범위

후속 수정 후보는 범위 복구나 요청 횟수 변경이 아니라 **실패 상태의 선행 공개**다.
범위 실패를 인지하면 대량 이벤트 저장에 앞서 외부 조회가 거부 상태를 볼 수 있게 하고,
그 뒤 원문 저장과 기존 epoch 보고서 완성을 계속하는 방식이다.

구체적으로는 마지막으로 저장된 보고서를 기반으로 `synchronized=false`와 누적 손실 등
운영 유효성 정보를 먼저 기록하는 좁은 경로를 검토할 수 있다. 이때 아직 저장되지 않은
이벤트를 저장 완료로 표시하거나 새 Book·ID를 정상으로 공개하면 안 된다. 원문 저장 또는
선행 상태 기록 실패 시에도 정상 표시로 돌아가지 않아야 하며, 같은 수집의 과거 손실을
복구 후 지우지 않아야 한다. 이 변경의 검증 목표는 즉시성의 절대 보장이 아니라, 대량
저장 지연이 이전 정상 표시를 유지시키지 않도록 하는 것이다.

이번에는 위 수정안을 운영 코드나 별도 후보 코드에 적용하지 않았다. 현재 상태 조회는
마지막 저장 보고서의 관측값이므로, 미래의 실시간 거래용 호가 제공 경로에서 이것 하나만을
현재 시점의 데이터 유효성 보증으로 사용해서는 안 된다.

전환 작업은 하지 않았다. checkpoint 정리 후 새 daily → 예약 restic 저장·검사 확인은 이
호가 검증과 별개의 후속 항목이다.
