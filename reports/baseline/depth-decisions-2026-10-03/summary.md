# 호가 조회 보류 사유의 운영 기록

2026-10-03에 격리 검증을 마친 **보류 기록 전용 구현을 11:10:13 KST에 설치**했다.
설치 당시 실행 중인 수집 프로세스는 유지했고 **11:17:30 KST의 자연스러운 시간제 교체로
실제 적용**됐다. 첫 서비스 표본과 아직 끝나지 않은 전체 세션·24시간 관찰은 구분한다.

기준은 `234be12`의 운영 코드이며, 구현은 문서 전용 커밋 직전 `e1da07d`에서 추출한
`/tmp/marketdata-depth-decisions-20261003`에서 검증했다. 두 커밋의 운영 코드는 같다.
[이전 후보](../depth-budget-candidate-2026-10-02/summary.md)에서 예산 예약·긴급 우선순위와
관련 API 인자를 제외했다. 기존 60초당 추가 12회, 처리 완료 후 최소 1초, 서비스의 정기
검증 10초, 여유 기준 75%·25%를 유지했다. `headroom()`과 정책 메타데이터는 이전 코드와
AST까지 같다. Book·Session·재생, 서비스 설정, 기존 백업 설정은 변경하지 않았다.

## 기록의 의미

`refresh_decisions.policy=coverage_decisions_v1`을 새 수집 보고서에 기록한다.
조회가 필요할 때 `minimum_interval`, `extra_budget`, `pending_verification`,
`not_synchronized`, `deadline`을 구분한다. 조건이 겹치면 모든 사유를 남기되 대표 사유는
하나로 집계한다. 조회가 아직 필요하지 않으면 보류로 세지 않는다.

집계는 `check_coverage` 호출의 최종 평가당 한 번이며 flush 전후를 중복 집계하지 않는다.
**평가 횟수는 HTTP 요청 횟수나 장애 횟수가 아니다.** 지연 anchor의 재시도·미재구성 증분
보존은 별도 경로이므로 모든 수신 이벤트마다 이 평가가 생기는 것도 아니다.

사유별 최초·마지막 표본과 최근 보류 8개를 유지한다. 실제 검증 REST 요청의 성공·
`SourceError` 원문 메타데이터에는 `refresh_context`로 사유·순번·여유·예산 전후를 남긴다.
범위 소진·상위 호가 부족의 종료 epoch에는 당시 집계의 독립 사본을 보존한다.
모든 보류를 개별 파일로 보존하지는 않으며 강제 종료 시 마지막 보고서 저장 이후 집계는
사라질 수 있다. 과거 실패·pending·미재구성 원문과 기존 품질 판정은 유지한다.

필드 설명은 [운영 문서](../../../docs/orderbook-depth.md)에 추가했다.

  기존 411개와 기록 전용 11개다. 예산 유지, 겹친 보류의 집계, pending, 저장 중 종료 시각
  도달, 429 원문·cooldown, 복구 경계 기록의 독립성을 확인했다.
- [가상 시장 비교](matrix.json): **11개 조건·22회 수집**에서 기존과 기록 전용 구현의
  REST 요청 시작·완료 시각, 수신·저장량, 연결, 복구 횟수, top 상태와 대조 결과가 같다.
  REST 및 저장 지연 중에도 증분이 쌓이며, 독립적인 전체 시장 정답과 top을 비교한다.
  이전 예약 후보에서 유리했던 조건과 불리했던 반례도 모두 포함했다.
- 원문·표준 대조 **8,492행·가격 수량 쌍 826,800개** 통과, 증분 8,200개 수신·저장 일치.
  REST 대조 230회 일치, 검증 대기 2개는 그대로 남았다. 모든 재생이 실제 수집 판정과 같다.
  추가 요청의 rolling 60초 최대는 12회, 가상 수신 큐 최대는 10개였다.
- `ruff check`와 `ruff format --check`의 packages·scripts·tests 및 새 기록 보조 도구가 통과했다.
  비교 도구의 출력 사전 표현을 포맷터로 정리한 것 외에는 시험한 바이트와 설치본이 같다.

[비용 표본](comparison-summary.json)의 실제 capture CPU 합계는 기존 9.120초,
기록 전용 9.195초였다. 0.075초 차이는 공유 호스트에서 한 번씩 순서대로 실행한 표본이며
운영 부하 증가율을 확정하는 측정은 아니다. 최종 보고서 크기는 조용한 조건 6,438→8,268바이트,
반복 실패 조건 29,769→91,738바이트였다. 보고서를 저장할 때의 실제 직렬화 비용은 시험에
포함됐지만, 가상의 시간·시장·REST 지연을 사용했으므로 운영의 처리 지연은 별도 관찰한다.

[validation.json](validation.json)에 시험·설치 파일 해시와 결과를 남겼다. 가상 저장소·원문은
Git 제외 경로 `reports/depth-decisions-20261003/matrix/`에 유지했다. 실제 거래소에 추가 시험
요청을 보내지는 않았다. 재현 시 baseline과 후보의 packages 경로·루트를 각 프로세스의
PYTHONPATH에 넣는다. 공유 가상환경의 editable 설치만 사용하면 코드가 섞일 수 있다.

## 설치와 실제 적용

[release.json](release.json)에 설치 전후 파일 해시와 당시 수집 ID를 남겼다.
검증한 파일을 준비한 뒤 호환되는 helper, stream 순서로 원자 교체했다. 수집기에는
재시작·중지 신호를 보내지 않았고, 설치 전후 수집 ID는
`af36f40790f64b4ea7071c152a8ca873`로 같다. 원문·기존 백업·시험 사본을 삭제하지 않았다.
Book 모듈·프로필·설치 유닛·서비스 템플릿 57개 파일의 해시를 유지했다.

11:13 KST 표본에서 기존 PID 1006599가 계속 실행 중이었으며 새 기록은 아직 없었다.
기존 세션은 `complete`·`end_reason=duration`으로 종료했고, 새 PID 1018051에서
`6d39cd17a2604b97a53e2932ac829e19` 수집이 **11:17:30.060370 KST**에 시작됐다.

일회성 읽기 전용 관찰 작업 `marketdata-depth-decisions-observe-20261003-v2.service`가
새 capture의 기록 정책·동일 요청 정책·실제 REST 문맥·정상 수신을 확인하고 종료했다.
반복 타이머는 만들지 않았다. 원본 관찰 결과는
`reports/depth-decisions-20261003/activation-v2/`에, 확정 사본은
[activation.json](activation.json)과 [표본](samples.jsonl)에 보존했다.
최초 관찰기의 segment 종류 조건을 실제 스키마의 `journal` 구조에 맞춰 수정했고,
해당 관찰기만 중지·교체했다. 최초 대기 표본도 `activation/`에 보존했다.

11:18:25 KST의 [첫 서비스 표본](activated-capture-sample.json)에서 증분 **501개 수신·저장**,
REST 동일 ID 대조 **4회 일치**, 연결 오류·동기화 손실 0을 확인했다. 20초 이상 정상 표본을
연속 확인했으며 [REST 요청 문맥](request-contexts.json) 5개를 카탈로그에서 읽었다.
보고서와 요청 이력은 실행 중 각각 읽은 표본이므로 다섯 번째 요청까지 모두 검증됐다는 뜻은 아니다.
기록의 조회 평가 500회 중 보류는 0회였고, 조회가 불필요한 평가를 보류로 세지 않았다.
별도 [저장 검증](operating-request-verification.json)에서는 고정한 요청 5개의 메타데이터가
카탈로그와 같고, REST 원문 SHA-256 및 표준 snapshot의 가격 수량 쌍 **10,000개**가
일치함을 확인했다. 이는 요청 기록·원문 대응 검사이며 전체 세션 재생 검사를 대신하지 않는다.

**실제 보류 사유의 발생 표본, 첫 종료 수집의 원문·재생 검사, 새 기록의 24시간 운영 관찰은
아직 미완료**다. 당시 확인한 것은 초기 적용·수신·요청 문맥이며 미래 실행을 완료로 집계하지 않는다.

## 후속 확인과 되돌리기

첫 새 수집의 종료 예정은 12:17:30 KST다. **10/3 12:25 KST 이후**에 수신·저장 일치,
REST 동일 ID 대조, 원문 대응·재생, 보류 사유·보고서 크기와 기존 실패 판정 유지를 확인한다.
24시간 경계는 **10/4 11:17:30 KST**이며, 그 시작 구간에 포함된 마지막 세션의 종료도 기다린다.
시간제 교체의 대기 시간을 고려하면 **10/4 11:30 KST 이후** 점검이 적절하며 실제 종료 기록으로 집계한다.
이 결과는 긴급 예산 예약의 채택이나 급격한 범위 소진 문제 해결을 의미하지 않는다.

문제가 발견되면 검토 후 아래 두 파일만 기준 코드로 되돌릴 수 있다. 실행 중인 프로세스에는
신호를 보내지 않고 다음 자연 교체부터 사용한다. helper를 먼저 제거하면 새 stream의 import가
실패할 수 있으므로 아래 순서를 유지한다. 데이터와 보류 기록을 삭제하는 절차가 아니다.

```bash
git restore --source=234be12 -- packages/marketdata/src/marketdata/depth_stream.py
git restore --source=234be12 -- packages/marketdata/src/marketdata/depth_refresh.py
```

관찰 작업만 조기에 종료할 때는 아래 명령을 사용한다. 수집 서비스는 계속 실행된다.

```bash
systemctl --user stop marketdata-depth-decisions-observe-20261003-v2.service
```
