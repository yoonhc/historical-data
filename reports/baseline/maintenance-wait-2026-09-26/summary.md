# 백업·파일 정리의 잠금 대기 개선 — 2026-09-26

KST **13:51:27**에 검증한 변경을 적용했다. 시간별 파일 정리와 일별 백업이 겹치면
후발 작업은 같은 프로세스에서 잠금을 기다린 뒤 실제 작업을 수행한다.
정상적인 잠금 경합으로 systemd의 실패 재시도 한도를 소모하던 원인을 수정했다.

## 원인과 변경

[당일 자동 백업 관측](../daily-backup-2026-09-26/summary.md)에서 13:15 파일 정리가
백업의 유지보수 잠금과 경합했다. 기존 코드는 `WriterBusy`로 종료했고, 120초 간격으로
네 번 실패한 뒤 시작 제한에 걸렸다. 백업이 13:21:57에 끝난 뒤에도 13:23 재개가 막혔다.

- CLI에 `maintenance --wait-for-lock`을 추가하고 pack·backup 서비스 모두에 적용했다.
- 충돌 시 `waiting_for_maintenance_lock`을 출력한 뒤 OS의 배타적 `flock`을 기다린다.
  반복 프로세스 시작이나 자체 polling 없이 같은 프로세스가 실제 작업까지 수행한다.
- 대기 중에는 기존 최신·실행 이력 보고서를 덮어쓰지 않고, writer·파일 배치 잠금과
  DB 트랜잭션을 보유하지 않는다. 대기는 journal과 systemd `activating` 상태로 확인한다.
- 획득 후 보고서에 요청 시각·작업 시작 시각·실제 잠금 대기 시간을 기록한다.
- `SIGINT`로 대기를 중단할 수 있다. 서비스의 기존 6시간 제한은 대기와 작업의 합계에
  적용된다. 검증·디스크 오류·시간 초과는 실패로 유지하며 기존 실패 재시도 정책을 따른다.
- 옵션 없는 수동 CLI의 즉시 충돌 오류, 타이머 시각, 재시도 간격·시작 횟수 제한,
  데이터·백업의 무기한 보관 정책은 유지했다.

CLI 단독 `--wait-for-lock`에는 자체 시간 제한이 없다. 자동 운영에서는 systemd가 제한한다.
잠금 대기 중의 이전 성공 보고서는 새 요청의 완료를 뜻하지 않는다.

## 검증

운영 디렉터리를 바로 편집하지 않고 `/tmp/marketdata-maintenance-wait-20260926`에서
수정·시험했다. 전체 테스트 **295개 통과, 실패·건너뜀 0개**다. 신규 6개 검사는 실제 CLI
프로세스를 띄워 hourly/daily 대기, 수집 쓰기 병행, 보고서 보존, 잠금 해제 후 실제 묶음 생성·
백업, SIGINT 취소, 대기 후 검증 실패와 내부 writer 오류 보존을 확인했다.

패키지·테스트·이번 검증 스크립트의 Ruff 검사 및 변경 Python 형식 검사를 통과했다.
호스트의 `systemd-analyze --user verify`도 통과했다. 전체 트리 Ruff에는 기존
`observation-2026-09-25/{audit,collect_evidence}.py`의 import 정렬 경고 두 건이 남아 있으며,
과거 보존 기록은 수정하지 않았다. [소스 해시와 검증 정보](release.json)

실제 사용자 systemd에서 가짜 데이터와 고유 이름의 임시 유닛으로 다음을 시험했다.
빠른 재현을 위해 시험에만 재시도 간격 100ms·시작 제한 30초/4회를 사용했다.
운영값은 120초·1시간/4회다.

| 시험 | 결과 |
|---|---|
| 기존 즉시 실패 방식 | 잠금 충돌 네 번, `NRestarts=4`, journal의 시작 제한 오류 재현 |
| 수정된 hourly | 약 2.051초 대기, 동일 PID·재시작 0회, 8개 파일 묶음·검증·중복 사본 정리 완료 |
| 수정된 daily | 약 2.051초 대기, 동일 PID·재시작 0회, 묶음·전체 검증·신규 백업 완료 |
| 대기 중 시간 초과 | 시험용 3초 제한으로 `Result=timeout`, 종료 코드 130, 기존 보고서 보존 |

수정된 두 정상 작업은 대기 중 추가 시작 요청에도 프로세스가 하나였고 수집 쓰기가 가능했다.
검증 중 발견한 systemd 255의 동작도 검사에 반영했다. `systemd-run --wait`는 첫 실패 때
반환할 수 있고, 시작 제한에 걸려도 서비스 `Result`가 마지막 `exit-code`로 남을 수 있다.
초기 시험 스크립트의 이 두 가정을 보정한 뒤 네 시험을 모두 통과했다.
최종 판정은 실제 재시작 수·종료 상태·journal·완료 보고서를 함께 확인했다.
[실제 systemd 결과](pilot.json), [시험 스크립트](pilot.py)

## 운영 적용과 확인

배포 전후 파일 해시와 기존 서비스 링크를 확인했다. 유지보수 잠금을 확보한 상태에서
하위 호환되는 `maintenance.py`를 먼저, 새 CLI를 다음에 설치했다. 두 서비스 파일은 기존
사용자 systemd 링크를 유지한 채 변경하고 `daemon-reload`로 반영했다. 복사·설정 검증 실패 시
이전 파일을 복원하도록 준비했다. [적용 스크립트](deploy.py), [적용 결과](deployment.json)

적용 후 실제 pack 서비스를 한 번 실행했다. KST **13:51:27.769~13:51:41.026**, 약
**13.256초** 동안 **508개 파일을 묶음 1개로 보존**하고 검증된 개별 중복 사본 508개를
정리했다. `ok=true`, `wait_for_lock=true`, 논리 파일 삭제 0개다.
이 실행은 경합이 없었으며 운영에서의 긴 잠금 대기를 관측한 사례는 아니다.
[운영 파일 정리 결과](hourly-result.json)

호가·체결 수집기에 stop/restart를 보내지 않았고 적용 전후 두 PID가 같았다.
수집·유지보수 상태 명령 세 개가 모두 종료 코드 0·healthy였으며 두 타이머의 다음 실행 시각도
같았다. 오늘의 완료된 전체 백업을 다시 만들지는 않았다.
