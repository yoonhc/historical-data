# 원본 경로 없이 복구·재백업 확인과 보관 정책 검토

2026-10-03 KST. **독립 복구 검증 통과**, 기존 병행 운영 유지.
사용자가 두 번째 SSD의 복구용 암호 사본 준비와 작업용 최근 3개·날짜별 보관 검토를 선택했다.
삭제·`forget`·`prune`·기존 백업 대체는 수행하지 않았다. PC 외부 암호 보관과 실제 새 VM 시험은 후속이다.

원래 `backup.json` 바이트와 `source_root`는 보존했다. 새 백업의 source root는 프로그램이
실제로 복원한 격리 환경의 경로로 생성했으며 수동으로 고치지 않았다. 원문·revision·이벤트의
파일 목록/해시/크기와 모든 카탈로그 테이블 건수도 새 백업과 대조했다.
`artifacts=432,343`, `revisions=18,445`, `event_segments=414,831`, `snapshots=20`이다.
앞선 daily 검사의 864,023건과 다른 것은 daily 검사 후에도 수집이 이어져 checkpoint의 항목 수가
달라지기 때문이다. 이번 기준은 명시한 checkpoint의 카탈로그다.

조회는 연구 snapshot manifest 20개와 각 key의 첫 최대 24시간 조회 107개가 일치했다.
원문 표본 10개·이벤트 세그먼트 4개·마지막 10분 aggTrade 1,702행·종료 호가 세션 35,583행도 일치했다.
호가는 `valid=true`, `replay_matches_live=true`, **`continuous=false` 그대로**다.
이 시험은 복구 일치 검증이며 원래의 연결 공백·격리·partial을 정상 데이터로 바꾸지 않는다.
모든 과거 기간을 전부 조회해 비교했다는 뜻은 아니다.

새 상태 파일은 원래 운영 기록을 복사하지 않고 snapshot metadata와 manifest에서 하나의 연결을
복구했다. 기록은 `explicit_restore_extracted_and_fully_verified`이며 알 수 없는 원래
보관 시작·완료 시각을 null로 유지했다. [최종 검토](review.json),
[전체 복구 결과](recovery-evidence/recovery-result.json), [새 상태](recovery-evidence/isolated-state-final.json)

OS·Python 인터프리터까지 포함한 부팅 이미지가 아니며 실제 다른 PC의 설치·부팅 검증은 하지 않았다.

문서·근거 추가 전 할당량은 키트 289,214,464바이트, 시험 저장소·추출·복원·재백업 합계

PC 외부 암호 사본은 사용자의 선택대로 아직 후속이다. 같은 SSD의 분실·고장에 독립적인 구성은 아니다.

## 운영 보존과 수집 관측

복구 후 운영 코드·호스트 프로필·원래 manifest·운영 snapshot 7개의 파일명이 그대로임을 대조했다.
운영 상태는 `healthy=true`, 대기 사본 0, 검사 대기 0, checkpoint 오류 0이다.
17:35 운영 보관 작업도 17:35:11에 성공했으며 처리 0개 탐색이다.
[시험 중 운영 기록](production-during-recovery.json), [시험 후 상태](production-status-after.json)

격리 환경 밖의 호스트에서 별도 읽기 전용 관측으로 10초 간격 **325개 표본**을 남겼다.
두 스트림의 관측된 연결 오류·호가 동기화 손실/미재구성·체결 미복구 카운터 최대값은 모두 0이고,
관측 자체의 오류와 수집/flush 오류도 없었다. 두 스트림 모두 한 차례 정상 세션 교체를 관측했다.
기록상 수신 시각의 최대 경과는 depth 8.35초, aggTrade 19.47초다. 후자는 세션 교체 중
종료된 이전 세션(`complete`)을 본 표본이고 다음 표본은 새 세션 `running`이다.
이 관측만으로 전 구간 체결 ID·호가 연속성을 추가 감사했다고 주장하지 않는다.
[호스트 관측 원문](recovery-evidence/host-stream-monitor.jsonl)

격리 안의 기존 monitor는 원본 catalog가 보이지 않아 325회 `unable to open database file`을 남겼다.
원본을 숨긴 시험 조건에서 예상한 관측 오류이며 지우거나 성공 표본으로 집계하지 않았다.
실제 운영 수집 상태는 위 호스트 관측으로 확인했다. 수집 중단·재부팅·로그아웃 시험은 하지 않았다.
이번 수동 복구를 새 예약 날짜 성공으로 추가하지 않으며 기존 **3/3** 기록은 유지한다.

## 보관 정책과 실제 후보

정책·그룹·정리 조건은 [운영 문서](../../../docs/restic-transition-and-retention.md)에 구체화했다.
원본·revision 무기한 보존, 작업용 검증 사본 최근 3개 및 완료 후 72시간 보호,
restic 최근 3개와 일별 30개·주별 12개·월별 12개·연별 1개씩 기간 제한 없이 남기는 합집합이다.
초기 전환 복구 증거인 9/28·10/3 snapshot ID는 별도 보호한다.

| 현재 대상 | 개수 | 결정 |
|---|---|---|
| 10/1·10/2·10/3 작업용 사본 | 3 | 유지 |
| 9/27·9/28·9/29·9/30 작업용 사본 | 4 | 정리 후보 계산만 |
| 편입 이전 9/25 2개·9/26 1개 | 3 | 이번 정리에서 제외·보존 |
| restic 9/27~10/3 | 7 | 모두 보존, 정리 후보 0 |
| 시험 사본·복구 키트·이번 복구 결과 | 전체 | 이번 정리에서 제외·보존 |

네 작업용 후보의 논리 파일 크기는 55,545,277,325바이트다.
하드링크를 inode별로 계산한 회수 가능 일반 파일 블록은 **3,641,630,720바이트**,
디렉터리 블록은 **531,861,504바이트**로, 합계 **약 4.17 GB**다.
다른 사본이 계속 참조하는 16.33 GB를 회수량에 넣지 않았다.
이는 시점별 예상이며 실제 회수량은 **0바이트**다. [조사](retention-inventory.json),
[재현 스크립트](retention_inventory.py)

실제 metadata로 기본 `host,paths` 또는 전체 태그 그룹이 각각 7개로 갈리는 것을 확인했다.
향후에는 엄격히 선택한 단일 scope 안에서 그룹을 비워 날짜 규칙을 계산한다.
현재 7개의 날짜는 모두 일별 30개 범위이므로 이 확인에 `forget` 명령을 쓰지 않았다.
[그룹 대조](snapshot-group-review.json)

현재 프로그램은 저장 성공으로 기록한 snapshot이 없어지면 오류로 처리한다.
후속 restic 만료 기능은 정상 만료 기록·중단 후 재개·parent/검사/조회와의 연계를 먼저 구현해야 한다.
누락 검사를 완화하거나 기존 상태를 지워 통과시키지 않는다. 작업용 폴더 정리도 사용 중 사본 보호·
잠금·적용 직전 재대조를 구현하고 구체적인 첫 목록을 검토한 뒤 진행한다.

이번 결과는 **독립 복구 확인과 보관 정책·정리 범위의 검토 완료**다.
실제 정리·공간 절감 전환·PC 외부 암호 보관·새 VM 운용까지 완료한 것은 아니다.
검증 스크립트의 Ruff 검사와 형식 검사를 통과했으며 운영 Python 코드와 서비스 유닛은 바꾸지 않았다.
