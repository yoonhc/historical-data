| 기존 보존·원복 계약 | 추가 daily_reviews/예산을 포함한 저장소의 기존 backup·verify·restore와 중복 요청 재처리 검증. 원문·기존 Collector·저장·백업 코드는 바이트 유지 |

`daily_reviews`의 처리 기록은 관측·판정 이력이며 자료 자체를 승인하는 우회 경로가 아니다.
근거가 부족하거나 현재 충돌이 남아 있으면 reconcile은 거부한다. retry 승인도 strict gate,
서버 냉각, 다른 미해결 작업의 의존 관계를 해제하지 않는다.

추가 시도는 작업 실행 단위다. 준비/기존 냉각 때문에 요청 전에 보류하면 차감하지 않으며,
실행 기록 후 결과 불명·404·새 429·검증 실패도 사용한 시도로 남긴다. 기존 HTTP의 짧은 재시도는 그 안에서 유지된다.
운영자가 같은 요청을 반복해도 사용한 한도가 복구되거나 추가되지 않는다.

## 실제 운영 사본 미리보기

최종 기준: **10/11 00:11:38 KST**, HTTP 0건, 약 **101.28초**.

| 분류 | 작업 수 |
|---|---:|
| 기존 자료의 검증 근거가 있어 acquire 제외 | 156 |
| 실행 예정 시각 전 | 20 |
| 그 시점 즉시 due | 0 |
| 미리보기 HTTP | 0 |

20건은 최근 3일 refresh 18건과 metadata 관측 2건이다. 이 결과는 **자료별 예정 전 상태**이지
오늘 모든 자료를 이미 수집했다는 뜻이 아니다. 다음 실제 실행에서 최신 상태를 다시 평가한다.

최초 10/10 23:59 기준 미리보기에서는 같은 20건이 due였다. 자정을 넘어 KST 확인 주기가 바뀐 뒤의
최종 not_due와 구분한다. 이전 미리보기를 적용 때의 최신 판단으로 재사용하지 않는다.

원본 DB에는 `mode=ro`/`query_only=ON`으로 연결하고, 일관된 사본과 작업 사본을 `/tmp`에 두었다.
원본 파일 배치 잠금은 읽기 전용 FD의 공유 잠금이다. 실제 strace에서 HTTP 전송·원본 경로의
생성/삭제/이동 명령·운영 daily 테이블 생성은 없었고, 최종 정렬 임시 디스크 파일 생성도 0건이었다.
SQLite가 WAL/SHM을 읽기 조정용으로 O_RDWR로 여는 것은 따로 기록했다. 이를 업무 원장 쓰기나
“원본 파일에 어떠한 접근도 없음”으로 표현하지 않는다. 운영 수집이 계속되므로 원본 DB의 전후 전체 해시 일치는 요구하지 않았다.

최대 RSS는 **97,924KiB(약 95.6MiB)**였다. 이 시간·자원은 큰 카탈로그 복제와 strace가 포함된
미리보기 측정이며, 5분 timer의 처리 0건 비용이나 운영 수집 영향의 성능 인증이 아니다.

근거: [대상별 결과](operating-preview.json), [접근 검사](preview-access-check.json),
[자원 기록](preview-resources.txt), [압축 strace](preview-strace.log.gz).

## 실제 확인 중 보완한 점

최초 미리보기는 SQLite 정렬 임시 파일을 `/var/tmp`에 만들었다. 환경변수만 지정한 두 번째 시도에서도
실제 파일 경로가 바뀌지 않아 통과로 처리하지 않았다. 최종 후보는 **미리보기 연결별 temp_store=MEMORY**를 사용한다.
카탈로그 본체와 journal은 여전히 시험 디스크 경로에 있으며, 운영 SQLite 설정은 바꾸지 않았다.

앞선 두 개발 후보·시험/미리보기 기록은 `pre-temp-isolation/`, `pre-env-isolation/`에 보존했다.
최종 적용 대상으로 혼동하지 않는다. 격리 시험의 fixture 잠금 준비 및 pack 함수명 오기 수정도
운영 장애 또는 기존 수집 코드 결함으로 보고하지 않는다.
