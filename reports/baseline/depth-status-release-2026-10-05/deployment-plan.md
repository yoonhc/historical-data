# 호가 상태 공개 후보의 운영 적용 절차

대상은 `depth-status-20261005-7be8e3da868f9308`이며, [명세](release.json)의 파일별 해시가
최종 기준이다. **이 문서는 아직 실행하지 않은 운영 적용·되돌리기 절차다. 사용자 승인 후
호가 서비스에 한정해 수행한다.** 깨끗한 경로의 적용·역패치·167건 검사는 완료했다.

## 적용 직전 확인

배포 명세·묶음·패치의 해시와 대상 파일의 `before_sha256`을 확인한다. 새 파일 2개가
이미 있거나 기존 파일이 바뀌었으면 덮어쓰지 않고 새 차이를 검토한다. 작업 저장소의
다른 미커밋 작업은 유지하며 `git reset`이나 전체 checkout으로 정리하지 않는다.

설치된 호가 유닛과 실제 실행 명령·PID·시작 시각을 기록한다. 현재 읽어 확인한 유닛은
`/home/yoonhc/.config/systemd/user/marketdata-depth.service`이며 다음 설정이다.

| 항목 | 현재 유닛의 값 |
|---|---|
| 작업 경로 | `/home/yoonhc/projects/algoTrade/historical_data` |
| 실행 파일 | 해당 경로의 `.venv/bin/marketdata` |
| 수집 시간 | `SESSION_SECONDS=3600` |
| flush / 연결 교체 / REST 대조 | 5초 / 900초 / 10초 |
| 정상 top / 여유 공간 | 20 / 10 GiB |
| 종료 신호 / 중지 제한 | `SIGINT` / 120초 |
| 재기동 | `Restart=always`, 15초 대기 |

적용 때도 실제 유닛·drop-in·환경의 Python 경로 설정을 다시 확인한다. 유닛은 바꾸지
않으므로 `daemon-reload`가 필요한 배포가 아니다. 일시적인 저장 경합을 줄이기 위해
진행 중인 daily·정리 작업이 끝난 뒤 적용 시점을 잡는다. 다른 서비스를 중지하지 않는다.

## 호가 수집 종료와 파일 교체

1. 명시적으로 `systemctl --user stop marketdata-depth.service`를 실행한다. 자연 종료 뒤
   15초의 자동 재기동 틈에 파일을 바꾸는 방법은 사용하지 않는다. 명시적 stop이 완료된
   비활성 구간에서만 교체한다.
2. 기존 `SIGINT` 처리에 따른 버퍼 저장과 종료 보고서, `MainPID=0`·비활성 상태를 확인한다.
   중간에 끝낸 세션의 `interrupted`는 의도한 작업 경계로 보존한다. 이를 `complete`로
   바꾸지 않는다. 기존 유닛의 120초 중지 제한을 넘기거나 강제 종료·저장 오류가 보이면
   적용을 보류하고 기록을 확인한다. 추가 강제 종료나 호스트 재부팅을 하지 않는다.
3. 비활성 상태에서 대상의 이전 해시와 패치 적용 가능 여부를 다시 확인하고,
   고정한 `candidate.patch`의 5개 파일만 적용한다. 이전 바이트는 기준 묶음에 보존돼 있다.
4. 적용 뒤 5개 최종 해시를 명세와 대조하고 운영 가상환경의 새 인터프리터로 import 경로를
   확인한다. 운영이 editable 설치이므로 이 파일 교체 자체가 배포다. 실패하면 새 서비스를
   시작하지 않고 아래 절차로 되돌린다.

서비스를 중지한 사이의 실시간 증분은 수집하지 못한다. 기존의 연결 경계·partial 처리대로
남기며, 이 작업을 무중단 전환이나 과거 호가 공백 복구로 보고하지 않는다.

## 새 프로세스 기동과 운영 확인

`systemctl --user start marketdata-depth.service`로 호가 서비스만 시작한다. 이전 PID와
다른 새 PID·시작 시각·실행 경로, 적용 완료 시각과 전후 파일 해시를 기록한다. 그 사이
소스가 바뀌지 않았는지 확인하고 같은 환경의 import 경로와 함께 검증된 파일을 새
프로세스가 읽는 기동 경계를 남긴다. 기존 장기 실행 프로세스에 새 모듈이 자동 적용됐다고
가정하지 않는다.

첫 정상 저장 이후 1~2분 동안 새 수집 ID의 메시지 저장 진행, DB/CLI 상태, 수신 신선도,
JSON과 DB의 정상 갱신, 실행 오류·반복 재시작 여부를 확인한다. 한 번의 JSON 오류도
현재 후보에서는 `failed` 종료와 기존 서비스 설정에 따른 재기동으로 이어질 수 있다.
문제가 지속되면 반복 재기동을 관망하며 정상으로 기록하지 않고 원인을 확인한다.

새 수집의 첫 정기 종료는 기동 후 약 1시간 뒤 별도로 확인한다. 저장 건수·종료 보고서·
새 다음 수집의 시작을 대조하고, 그때까지 이 항목은 미완료로 둔다. 자연 발생한 품질
손실·네트워크 오류는 기존 정책대로 구분한다. 실패 공개 순서 자체의 근거는 격리 시험이며,
운영에서 일부러 호가 소진을 만들거나 재발을 기다리지 않는다.

## 되돌리는 절차

시작·import 오류, 저장 불일치나 이 배포에 기인한 반복 실패가 확인되면 새 호가 서비스를
같은 방식으로 중지한다. 실행 파일이 명세의 최종 해시와 같은지 확인한다. 다른 변경이
끼어 있으면 무조건 역패치를 실행하지 않는다.

중지 확인 뒤 같은 패치에 `git apply --reverse --check`를 하고 역패치를 적용한다.
실행 파일과 기존 테스트는 명세의 이전 해시로, 이번에 추가한 테스트 파일 2개는 없는
상태로 돌아오는지 확인한다. 이 절차는 깨끗한 경로에서 실제로 검사했다.
기준 코드를 새 인터프리터로 import한 뒤 호가 서비스만 다시 시작하고 정상 저장을 확인한다.

되돌리기는 5개 소스·테스트 파일에 한정한다. 데이터·카탈로그·이번 수집의 실패 보고서와
진단 필드를 지우지 않는다. 기존 조회·재생은 추가 진단 필드를 판정에 사용하지 않으며,
DB 스키마 변경도 없다. 다른 수집·daily·restic 예약과 설정은 유지한다.
