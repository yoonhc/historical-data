# 호가 일반 저장 오류 검증과 배포 후보 고정

2026년 10월 5일. **일반 저장 실패 경로에서 보고서의 수신 상태와 저장 상태가 섞이는
경우를 재현해 후보에서 보완했다. 고정한 배포본을 새 디렉터리에서 적용하고 호가 검사
167건을 통과시켰으며, 역패치로 기준 파일이 복원되는 것도 확인했다. 운영은 미적용이다.**

후보 ID는 `depth-status-20261005-7be8e3da868f9308`이다. 이전
[163건 검증 후보](../depth-status-candidate-2026-10-05/summary.md)와 그 산출물은 그대로
보존했고, 이번 작업은 별도 `/tmp/marketdata-depth-status-release-20261005`에서 진행했다.
운영 소스·서비스·요청 정책·Book·범위 채택·재생 판정은 변경하지 않았다.

## 일반 저장 실패에서 확인한 차이

기존 호가 테스트에는 `failure_notice`가 없는 일반 원문 저장의 지속 실패를 직접
확인하는 사례가 없었다. 실제 collector에 정상 Book을 유지하는 합성 입력을 주고,
정상 보고서 2개 증분·ID 102를 확정한 뒤 ID 103의 정기 flush에 오류를 주입했다.

첫 시험은 [4건 중 1건 실패](before-general-fix.xml), 3건 통과였다. 원문 저장과 종료
재시도가 모두 실패한 경우에만 문제가 나타났다. [당시 보고서·재생 결과](before-general-fix-record.json)는
다음과 같았다.

| 항목 | 당시 결과 | 해석 |
|---|---:|---|
| `messages` | 3 | 메모리에서 수신한 증분 수 |
| `persisted_messages`와 실제 저장 행 | 2 | 저장 건수 자체를 3으로 잘못 기록한 것은 아님 |
| 최상위 `last_update_id` | 103 | 아직 저장하지 못한 증분을 적용한 메모리 상태 |
| epoch의 Book ID | 102 | 이전 flush에서 만든 요약 |
| epoch의 적용 건수 / 저장 행 재생 적용 건수 | 3 / 2 | 메모리 보고서 일부가 이미 다음 증분까지 진행됨 |
| 최종 상태 / 재생 일치 | `failed` / `false` | 정상 자료로 승인되지는 않았지만 보고서 기준이 혼재 |

`messages`는 원래 수신 건수이고 `persisted_messages`는 저장 함수가 성공 반환한
건수다. 두 값이 다르다는 사실 자체를 버그라고 판단하지 않았다. 문제는 종료 재시도까지
실패한 뒤 **전체 메모리 보고서를 저장하면서 마지막 ID·epoch의 Book·적용 건수가
서로 다른 시점을 가리키는 것**이었다. `Session.summary()`가 반환한 `counts`는
메모리 카운터를 참조하므로 이전 epoch 요약 일부도 진행될 수 있다. 계산기나 이 요약
함수를 바꾸는 대신, 실패 종료에서 DB의 마지막 저장 보고서를 기준으로 삼았다.

## 추가한 보완

최종 flush가 실패하면 `failure_notice` 유무에 관계없이 `save_flush_failure()`로
종료 상태를 기록한다. 기존 선행 공개와 같은 DB 읽기·실패 상태 커밋·JSON 기록 경로를
사용하며, 메모리 전체 보고서를 저장하는 분기로 돌아가지 않는다.

마지막 DB 보고서의 건수·ID·수신 시각·epoch는 유지한다. 종료 직전 수신 정보는
`flush_failure_observation`에 따로 남긴다. 여기의 `messages_received`, `last_received_at`,
`book_update_id`, `persisted_messages`는 **종료 처리 당시 메모리의 관측값**이며,
최상위 상세 보고서의 확정 범위를 갱신하는 값이 아니다. 특히 내부 `persisted_messages`는
성공 반환한 저장 호출의 누적값으로, 부분적으로 진행된 모든 디스크 쓰기를 감사한 수치는 아니다.

손실·복구·연결 오류의 누적 카운터는 최댓값을 유지한다. 일반 디스크 오류에 가짜 호가
부족이나 `failure_notice`를 만들지 않는다. 이미 있는 호가 실패 관측의 재시도·최초 기록
시각·partial 보존은 이전 후보와 동일하다. 원문이나 과거 보고서를 수정하지 않았다.

정상 Book의 새 시험 결과는 다음과 같다.

| 조건 | 보완 후 결과 |
|---|---|
| 원문 저장·종료 재시도 모두 실패 | 실제 저장 2개·보고서 ID 102·epoch 적용 2회 유지, 진단 항목에 수신 3개·ID 103 기록 |
| 원문 저장 1회 실패 후 종료 재시도 성공 | 실제 저장과 보고서 모두 3개·ID 103, 최종 `failed` |
| 이벤트 저장 성공 후 상세 보고서 JSON 1회 실패 | DB에 확정한 3개·ID 103 보존, 최종 `failed`, JSON 재기록 성공 |
| 상세 보고서 JSON 지속 실패 | DB는 최종 `failed`와 저장 3개·ID 103, JSON은 정상 기준 ID 102로 남음 |

네 경우 모두 `failure_notice` 없음, 호가 손실 0회, 연결 1회·연결 오류 0회, 재연결 없음,
재생 일치 `true`·재생 `valid=false`다. 첫 경우의 재생 일치는 저장된 2개와 유지한 보고서가
일치한다는 뜻이며, 잃은 미저장 증분이 복구됐다는 뜻은 아니다.

[오류 처리 29건](fault-tests.xml)과 [후보의 호가 관련 167건](candidate-tests.xml)이
통과했다. 167건은 기존 163건에 위 네 경우를 더한 것이다. 원문 오류는 저장 호출의
쓰기 전에 주입했고 JSON 오류는 실제 DB 커밋 뒤에 주입했다. 모든 물리 디스크 장애
위치를 시험하거나 프로젝트 전체 테스트를 실행한 것은 아니다.

[구성기](build_release.py)는 위 묶음을 만드는 도구이며 운영에 설치하지 않는다.
[재현기](reproduce.py)는 묶음과 패치만 읽고 **존재하지 않는 `/tmp` 디렉터리**에
풀도록 제한했다. 기존 후보나 작업 저장소의 미커밋 테스트를 다시 참조하지 않는다.

[깨끗한 경로의 검증 결과](reproduction.json)에서 다음을 확인했다.

1. 기준 묶음 전체 해시 검사와 패치 적용 검사·적용 성공.
2. 실제 모듈 import가 `/tmp/marketdata-depth-status-clean-20261005`에서 이루어짐.
3. Ruff·형식 검사와 [호가 167건](reproduction.xml) 통과. 시작 13:34:51 KST, 약 12.81초.
4. 역패치 검사·실행 뒤 기준 파일 해시 복원 및 신규 테스트 파일 제거 확인.
5. 재적용 뒤 모든 최종 파일 해시가 검사한 배포본과 일치.

재현 명령은 다음과 같다. 목적지와 결과 파일은 새 경로를 지정해야 한다.

```bash
.venv/bin/python reports/baseline/depth-status-release-2026-10-05/reproduce.py \
  --destination /tmp/marketdata-depth-status-reproduce-new \
  --results /tmp/marketdata-depth-status-reproduce-new.json
```

독립성의 범위는 소스·테스트·재현 입력이다. Python 의존성은 기존 가상환경을 사용했다.
새 OS나 Proxmox VM에서 설치까지 재현했다는 의미는 아니다. `/tmp`가 사라져도
보고서 옆 기준 묶음·패치·명세·재현기로 소스와 검사를 복원할 수 있다.

## 운영 조회와 오류 처리의 의미

상태 판단은 **`depth-status` 또는 DB 조회를 우선**한다. `depth-latest.json`은 DB 커밋
뒤에 기록하는 보조 사본으로, JSON 쓰기가 실패하면 DB보다 오래될 수 있다. 저장소의
scripts·systemd 템플릿·Freqtrade 어댑터와 설치된 사용자 systemd 유닛에서 직접 JSON을
읽는 운영 소비자는 찾지 못했고, 직접 참조는 테스트에서 확인했다. 이 조사 범위 밖의
사용자 도구까지 없다고 단정하지 않는다.

이 후보는 **JSON 오류 한 번도 현재 수집을 최종 `failed`로 끝내는 보수적인 처리**를
유지한다. 종료 처리에서 쓰기 재시도가 성공하더라도 이번 수집을 성공으로 바꾸지 않는다.
설치된 호가 서비스는 `Restart=always`, `RestartSec=15s`이므로 실행 오류로 프로세스가
끝나면 기존 설정에 따라 다음 수집을 시작한다. 실제 배포 뒤 반복 재시작이나 지속적인
저장 오류가 없는지는 따로 확인해야 한다. 이번에는 운영에 오류를 주입하지 않았다.

DB 기록 자체가 실패하면 즉시 외부에 실패를 알릴 수 없다는 한계도 유지한다. 기존
신선도 조건에 걸리기 전까지 이전 정상 상태가 남을 수 있다. 별도 감시 서버나 새로운
호가 소비 경로를 추가하지 않았다.

## 운영 반영 전 남은 결정

[적용과 되돌리기 절차](deployment-plan.md)에 정확한 대상 파일·버전·호가 서비스의
종료와 기동·확인 기준을 정리했다. **현재 단계는 배포 준비 완료이며 운영 반영은 별도 승인
대상이다.** 운영 소스·설치된 서비스와 이전 근거 77개 파일의 해시 보존, 문서·산출물
검사는 [최종 확인](validation.json)에 남긴다.

실제 새 프로세스의 정상 수집·상태 조회·첫 세션 종료 확인은 배포 후 항목이다.
aggTrade·OI·daily·restic 설정과 원본·기존 백업은 이번 작업에서 변경하지 않았다.
checkpoint 정리 후 새 daily와 예약 restic 연결 확인도 이 후보 검증으로 완료된 것으로
집계하지 않는다.
