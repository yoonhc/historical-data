# 호가 복구 보강 재검토 — 2026-09-26

검토 결론은 **이미 수신한 이벤트를 재동기화에 사용하지 못하던 원인을 고친 타당한 구현**이다.
확인한 범위에서 실패를 숨기거나 ID 연결 조건을 완화하는 경로, 잘못된 복원 후보를 채택하는
정확성 결함은 발견하지 않았다. 다만 급격한 가격 이동으로 스냅샷의 알려진 범위가 소진되는
경우는 남으며, 모든 호가 공백이 해결됐다는 의미는 아니다.

이번 검토에서는 운영 복원 코드를 추가 변경하거나 서비스를 재시작하지 않았다.
독립 기준 계산 테스트 33개와 실제 원문 재검토 스크립트·기록을 추가했다.
기존 배포 파일 7개의 해시는 [배포 당시 기록](../depth-history-2026-09-26/release.json)과 같다.

## 원인과 해결 범위

| 문제 | 기존 동작 | 이번 구현의 판단 |
|---|---|---|
| REST 검증 스냅샷의 ID가 현재 호가보다 뒤처짐 | 이미 받은 증분이 있어도 비교 불가로 남고 범위 갱신을 못 함 | 최근 증분으로 같은 ID까지 정렬하고 상위 N호가가 정확히 일치할 때 갱신하는 것은 원인에 맞는 수정 |
| 같은 소켓에서 새 기준 스냅샷을 받을 때 필요한 연결 증분이 이전 epoch에 있음 | 이미 처리한 증분을 다음 복원 구간에서 쓸 수 없어 재동기화가 다시 실패 | 해당 소켓의 최근 증분과 소진을 유발한 증분을 보존하므로 이 원인을 해소 |
| 가격이 알려진 범위를 빠르게 벗어남 | 다음 갱신 전에 한쪽 호가가 없어져 복원이 중단됨 | 남아 있는 가용성 한계. 버퍼 보강만으로 예방된다고 주장할 수 없음 |

새 연결에서 실제 증분을 받은 다음 최초 REST를 요청하는 앞선 수정과 이번의 최근 이력
보존은 별개다. 전자는 접속 시작 순서, 후자는 이미 받은 데이터의 수명과 재사용 범위를 고친다.

공식 USD-M 절차의 첫 연결 조건 `U <= lastUpdateId <= u`, 이후 `pu == 직전 u`, 절대 수량과
0 수량 삭제 규칙을 그대로 유지한다. Spot의 연결 규칙과 혼동하거나 선물 ID가 매번 1씩
증가한다고 가정하지 않는다.
[공식 로컬 호가장 절차](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/websocket-market-streams/How-to-manage-a-local-order-book-correctly)

## 코드에서 확인한 안전 조건

- `History.align`은 별도 후보 호가장을 만든다. 중간까지 적용한 뒤 연결이 끊기면 후보 전체를
  버리며, 기존 호가장에 일부만 섞지 않는다.
- 지연된 check는 현재와 같은 업데이트 ID, 충분한 양쪽 상위 N호가, 가격·수량의 정확한
  일치가 있어야 범위를 교체한다. 같은 ID에서 값이 다르면 동기화 실패로 처리한다.
- 같은 소켓의 범위 소진·지연 스냅샷 재시도만 이력을 이어받는다. 새 연결·계획 회전·단절 후
  재접속에서는 새 버퍼를 사용한다. 새 소켓에 과거 연결의 증분을 이어 붙이지 않는다.
- 이력은 이벤트 수·가격 수량 쌍·직렬화 크기의 세 한도로 제한한다. 필요한 연결 증분이
  밀려났다면 정렬을 거부한다. 버퍼 한도가 Python 프로세스 전체 메모리의 상한은 아니다.
- 복구 후에도 이전 epoch의 오류, 미복원 메시지 수, 수집의 `partial` 판정은 보존한다.
  같은 과거 이벤트를 새 수신 건수에 더하지 않는다.
- 새 정책은 보고서에 버전과 한도를 남긴다. 정책이 없는 과거 자료는 종전 규칙으로 재생한다.
  수집과 재생의 정책 선택을 공유하되, 검증에서는 아래의 별도 기준 계산도 사용했다.

검토 대상: [복원 상태와 이력](../../../packages/marketdata/src/marketdata/depth.py),
[수집·재동기화 경로](../../../packages/marketdata/src/marketdata/depth_stream.py),
[원문 검사](../../../scripts/verify_depth_capture.py).

## 이번에 추가한 검증

실시간 수집과 재생은 같은 `Book`/`Session`을 사용한다. 둘의 결과가 같다는 것만으로는
공통 구현 오류를 배제할 수 없으므로, **운영 복원 엔진으로 정답을 계산하지 않는 검사**를 추가했다.

[새 테스트](../../../tests/test_depth_reference.py)는 가상의 거래소 전체 호가장을 먼저 변경하고,
그 상태에서 REST 스냅샷과 증분 메시지를 생성한다. 32개 고정 seed에서 총 5,120개의 증분을
만들어 최초 stale 이벤트, 증분 중간 ID의 스냅샷, 지연·선행 스냅샷, 중복, ID의 비연속 정수
증가, 이력의 128개 제한, 같은 소켓 재동기화를 결합했다. 복원된 알려진 범위 전체와 상위
호가를 생성기의 정답 상태와 비교했다. 후보가 일부 진행한 뒤 실패해도 기존 상태를 보존하는
검사 1개를 더해 **33개가 모두 통과**했다.

기존 depth·bootstrap·history 테스트 **64개도 재실행해 모두 통과**했다. 이번 검토의 실행은
합계 97개이며, 앞선 배포 시 전체 256개 통과 기록과 구분한다. 새 파일의 lint·format도 통과했다.
JUnit 요약과 파일 해시는 [검증 기록](validation.json)에 보관한다.

과거 실제 실패 6개 epoch의 **18,892행**을 원문과 다시 대조했다. 이전에 기록한 새 정책의
시나리오 최종 상태가 재현됐으며, 이력 정렬이 성공한 4개 지점은 생산 `Book.apply`를 호출하지
않는 별도 원문 계산으로 알려진 범위 전체의 가격·수량을 비교해 일치했다.

| 원문 기반 추가 대조 | 결과 |
|---|---|
| 지연 check 3개 | 현재 업데이트 ID와 알려진 범위의 모든 가격·수량 일치 |
| 같은 소켓의 지연 anchor 1개 | 이전 epoch의 증분 2개로 연결한 전체 결과 일치 |
| 사용 데이터의 시점 | 모든 증분의 sequence와 수신 시각이 해당 스냅샷 처리·수신보다 앞섬 |
| 급격한 범위 소진 2개 | 기존과 같은 이벤트에서 실패, 오류를 정상으로 바꾸지 않음 |

이는 실제 기록된 스냅샷 수신 순서와 epoch 경계를 고정한 경로별 검사다. 독립 거래소 원천의
추가 관측이나 변경 후 운영 실패율의 측정은 아니다. ‘4/6 개선율’로 해석하지 않는다.
기존 시장 데이터·카탈로그 보고서·실패 판정은 수정하지 않았다.

## 남은 한계와 다음 판단

REST 스냅샷은 양쪽 최대 1,000호가를 제공한다. 현재 추가 갱신의 최소 간격은 5초이며,
실제 미해결 사례는 정상 갱신 약 3.636초와 4.474초 후 범위가 소진됐다. 이 경로는 최근 이벤트
버퍼로 예방되지 않는다. 단순히 대기 시간을 없애기보다는 향후 소진 빈도, 남은 가격 범위,
스냅샷 수신 지연과 요청 한도를 함께 측정해 선제 갱신 정책을 조정할 문제다.
[공식 REST 한도](https://developers.binance.com/en/docs/catalog/core-trading-derivatives-trading-usd-s-m-futures/api/rest-api/market-data#order-book),
[첫 실제 사례](../depth-coverage-2026-09-25/summary.md),
[다음 실제 사례](../observation-2026-09-26/summary.md)

또한 128개 이력은 시간 단위 보장이 아니다. 장기 REST 지연·버퍼 초과·실제 소켓 단절에 대해
무손실 복원을 보장하지 않는다. REST와 저장은 수신 처리 루프에서 동기적으로 수행되며,
WebSocket 내부 큐가 이를 받쳐 주는 구조다. 이번 검토로 극단적인 네트워크 지연·디스크 정지의
내성을 새로 입증한 것은 아니다. `received_at`은 실제 패킷 도착이 아닌 애플리케이션 수신
반환 시각이라는 기존 의미를 유지한다.

KST **12:54:33 조회**에서는 배포 후 약 16분 동안 업데이트 9,323개를 수신·보존했고,
스냅샷 대조 92회가 모두 일치했다. 동기화 실패·범위 소진·지연 스냅샷은 0회였다.
이 운영 구간에서 새로운 이력 정렬 분기가 실제 발동한 것은 아니므로 급변장 검증이나
24시간 통과로 해석하지 않는다. 다음 판단 시점은 **9/27 12:40 KST 이후**의 24시간 관찰이다.
점검 예약이나 알림을 추가한 것은 아니다.
