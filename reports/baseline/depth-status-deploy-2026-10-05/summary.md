# 호가 실패 상태 공개 운영 반영

2026년 10월 5일 **14:01 KST에 승인한 배포본을 적용하고 새 호가 수집을 시작했다.**
14:04 초기 점검에서 1,350개 수신·저장 일치, REST 대조 13회 일치, 동기화 손실·연결
오류·미재구성 증분 0개, DB/CLI `healthy=true`를 확인했다. **첫 정기 세션 종료는 아직
미완료이며 15:05 KST 이후 확인한다.**

적용 버전은 `depth-status-20261005-7be8e3da868f9308`이다. 이전
[배포본 검증](../depth-status-release-2026-10-05/summary.md)의 기준 묶음·패치·파일 해시와
깨끗한 경로의 167개 검사 결과를 그대로 사용했다. 이번 작업은 실제 설치·기동 검증이며
동일한 전체 회귀 검사를 이유 없이 다시 실행하지 않았다.

## 적용 전 확인과 종료

배포 전에는 13:10 백업과 13:15 정리가 진행 중이어서 즉시 호가를 중지하지 않았다.
백업은 13:58:02에, 이를 기다리던 정리는 13:59:08에 정상 완료됐다. 해당 서비스들이
종료된 상태를 확인한 뒤 배포했다. 데이터 갱신 서비스의 기존 실패 표시는 별도로
보존했으며 아래에 구분한다.

설치된 유닛·실제 명령·작업 디렉터리와 프로세스 환경을 확인했다. 운영은 기존 가상환경의
editable 설치이며, 기존·새 프로세스 모두 `SESSION_SECONDS=3600`이고 후보 경로로
우회하는 `PYTHONPATH`·`PYTHONHOME` 설정은 없었다. 유닛의 drop-in도 없었다.
관련 기록은 [이전 서비스](services-before.json), [이전 프로세스](process-before.json),
[새 프로세스](process-started.json)에 있다.

| 시점 KST | 실제 수행과 결과 |
|---|---|
| 14:01:45.733 | 호가 서비스만 명시적으로 stop 요청, 이전 PID `1413508` |
| 14:01:47.828까지 | 기존 SIGINT 처리로 종료, 수신·저장 각각 17,522개, flush 오류 없음 |
| 14:01:47.962까지 | 패치 적용과 최종 파일 해시·새 인터프리터 import 경로 확인 완료 |
| 14:01:47부터 | 호가 서비스 start, 새 PID `1421578` |
| 14:01:48.123 | 새 수집 `2903de655fe94ecc9922e4aa3f529f01` 시작 |

이전 수집 `91d0a5fd78d146d2843741354ab7a534`는 `KeyboardInterrupt`에 따른
`interrupted`로 남겼다. [종료 보고서](collection-stopped.json)에 저장 건수 일치와
`complete=false`, `synchronized=false`가 보존돼 있다. CLI 종료 코드 130을 현재
유닛이 성공 종료 코드로 지정하지 않았으므로, **수동 중지 직후 systemd의 상태는
`failed`, `ExecMainStatus=130`이었다.** PID가 0이고 SIGINT 종료 보고서·저장 완료가
확인되는 예상 경계로 판단했으며 강제 종료나 중지 시간 초과는 없었다. 재기동 뒤
서비스는 정상 `active/running`이다. 유닛의 성공 코드 설정을 바꾸지는 않았다.

[배포 실행 기록](deployment.json)의 서비스 변경 명령은 호가 stop·start 각 1회뿐이다.
[실행기](deploy.py)는 고정 버전·전후 파일 해시를 검사하고, 유지보수 종료를 확인한 뒤
명시적 중지 구간에서만 패치를 적용했다. 준비 과정의 서비스 조회는 샌드박스 사용자
버스 제한 때문에 권한을 받아 실행했으며, 운영 적용 자체는 사용자의 승인을 받아 수행했다.

## 적용 범위와 기동 경계

실행 파일은 `depth.py`, `depth_stream.py` 두 개다. 함께 고정한 기존 회귀 테스트 하나와
새 시험 도구·테스트 두 개를 포함해 총 5개 파일을 적용했다. 전후 해시는
[배포 명세](../depth-status-release-2026-10-05/release.json)와 일치한다.
서비스 유닛·의존성·DB 스키마·Book 계산·범위 채택·요청 예산·최소 간격은 유지했다.

파일 교체 완료 뒤 새 PID가 시작됐고, 명령·작업 경로·환경과
[새 인터프리터의 import 경로](import-origins.json)를 대조했다. 기존 장기 실행 프로세스에
파일 변경이 자동 적용됐다고 가정하지 않았다. 새 코드로 바뀐 부분은 앞서 검증한
실패 상태 선행 커밋과 저장 실패 시 마지막 DB 보고서 보존이다.

[수신 경계 기록](boundary.json)에서 이전 마지막 수신과 새 첫 증분의 애플리케이션 수신
시각 차이는 **2.651571초**였다. 이는 `recv()` 반환 시각 간 차이이며 정확한 거래소 품질
손실 기간·패킷 도착 간격을 측정한 값은 아니다. 중지 구간을 과거 REST로 채우거나
연결이 연속됐다고 처리하지 않았다.

## 초기 운영 확인

실제 운영 CLI로 [첫 조회](status-first.json)와 [후속 조회](status-second.json)를 수행했다.
저장 증분은 600개에서 1,350개로 증가했다. 14:04:10의
[초기 관측 요약](initial-observation.json)은 다음과 같다.

| 항목 | 결과 |
|---|---:|
| 수신·저장 증분 | 각각 1,350개 |
| CLI 종료 코드·상태 | 0, `running`, `healthy=true` |
| 마지막 저장 수신 시각의 경과 | 약 4.14초 |
| REST 대조 / 일치 / 대기 | 13 / 13 / 0 |
| 동기화 손실 / 연결 오류 / 미재구성 증분 | 0 / 0 / 0 |
| DB 보고서와 JSON 보조 사본 | 동일 |

14:10의 [최종 조회](status-final.json)에서도 같은 수집의 수신·저장 **4,850개** 일치,
`healthy=true`, 동기화 손실·연결 오류 0회를 확인했다. 이 시점에도 수집은 실행 중이다.

별도 [서비스 조회](services-observed.json)에서도 PID `1421578`, `active/running`, 새 기동
후 `NRestarts=0`을 확인했다. [journal](depth-journal.jsonl)은 같은 PID에서 동기화 상태와
저장 진행이 이어지는 것을 보여준다. aggTrade는 기존 PID `1416652`를 유지했다.

운영에서 호가 부족이나 저장 오류를 인위적으로 만들지 않았다. 실패가 발생했을 때
대량 저장보다 먼저 거부 상태가 보이는 순서는 격리 시험의 근거이며, 이번 정상 수집
관찰만으로 그 오류 경로가 운영에서 실제 발생했다고 주장하지 않는다.

상태 판단은 DB/CLI를 우선한다. JSON은 갱신 실패 시 오래된 보조 사본일 수 있고,
DB 기록 자체가 실패하면 신선도 제한에 걸리기 전까지 이전 상태가 남을 수 있다.
단일 JSON 오류도 수집을 `failed`로 끝내는 선택과 기존 15초 서비스 재기동 정책은 유지한다.

## 별도로 남긴 기존 상태

`marketdata-daily.service`는 12:25 실행의 종료 코드 2와 재시도 한도로 배포 전부터
실패 상태였다. 당시 [데이터 갱신 보고서](existing-daily-latest.json)는 10/4 선물 거래 봉·
mark 봉·index 봉과 OI 아카이브의 `waiting_source`를 기록했다. 오류 목록은 비어 있고
미수집 분량은 각 1분 봉 1,440행, OI 288행이다. 이를 이번 배포의 장애로 집계하거나
해결됐다고 표시하지 않았다. 추가 거래소 요청·서비스 재시도·설정 변경은 하지 않았다.

데이터 갱신 서비스와 정기 백업 서비스는 별개다. 13:10
[정기 백업](existing-maintenance-daily-latest.json)은 무결성 1,033,153건 통과 후 새 사본
`46f4734b48f7e81c4ef805479c8d2c7b605215c6881b3d6b38a0a3a80d19bc1b`를 정상 완료했다.
[시간별 정리](existing-maintenance-hourly-latest.json)도 정상 완료했다. 14:05 정기 restic
작업은 서비스 조회 당시 실행 중이었으며, 해당 새 사본의 저장·검사 완료는 이 배포
보고서에서 확정하지 않는다. 기존 백업·시험 사본과 다른 예약 설정은 유지했다.

## 남은 확인과 되돌리기

새 수집의 요청 시간이 3,600초이므로 첫 정기 종료는 약 **15:02 KST**, 다음 확인은
**15:05 KST 이후**로 잡는다. [후속 항목](followup.json)에 새 수집 ID와 미완료 상태를
남겼다. 해당 ID의 종료 보고서·수신과 저장 건수·품질 상태·다음 새 수집의 기동을 실제
기록으로 대조해야 한다. 이 초기 관찰을 한 시간 운영 완료나 장기 안정성 검증으로
대신 세지 않는다. 새 감시 타이머는 추가하지 않았다.

되돌리기는 [승인된 절차](../depth-status-release-2026-10-05/deployment-plan.md)에 따라
호가만 중지하고, 설치 파일 해시를 확인한 뒤 같은 패치의 역패치를 적용하고 다시
기동한다. 기존 원문·카탈로그·실패 보고서는 보존한다. 이번 적용에는 되돌리기가
필요하지 않았다. 최종 파일·유닛·근거 보존과 문서 검사는 [검증 기록](validation.json)에 남긴다.
