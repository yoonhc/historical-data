# 이벤트 파일 묶음 저장·무기한 보관 검증

사용자가 선택한 정책은 **원문·표준 데이터의 무기한 보존**이다. 종료된 aggTrade·depth의
개별 파일 3,826개를 ZIP_STORED 묶음 6개로 전환했다. 묶음의 모든 멤버를 검증한 뒤 동일한
개별 사본을 정리했으며, 논리 데이터나 수집 이력은 삭제하지 않았다.
[정책·명령·동시 실행·복구 절차](../../../docs/file-packing-and-retention.md)

## 실제 저장소 적용

대상은 기존에 종료된 수집의 이벤트 세그먼트 1,913개와 연결된 원문 1,913개다.
기존 캔들·OI 파일은 묶음 대상으로 선택하지 않았다. 적용 전 실행 중인 이벤트 수집은 없었다.

| 항목 | 적용 전 | 적용 후 |
|---|---:|---:|
| 대상의 물리 파일 | 3,826개 | ZIP 6개 |
| 논리 파일 | 3,826개 | 3,826개 |
| 파일 내용 크기 | 113,382,315바이트 | 114,398,433바이트 |
| 파일시스템 할당량 | 121,192,448바이트 | 114,409,472바이트 |
| 원래 위치의 개별 사본 | 3,826개 | 0개 |
| 삭제한 논리 데이터 | 0개 | 0개 |

물리 파일은 3,820개 줄었다. ZIP 헤더 때문에 내용 크기는 약 1.02 MB 늘었지만, 작은 파일의
할당 여유가 줄어 대상 파일들의 할당량은 6,782,976바이트 감소했다. 디렉터리·SQLite·기존 백업·
복원 시험 사본의 크기는 이 표에 포함하지 않는다. 전체 작업 공간의 파일 수 감소량을 뜻하지 않는다.
[적용 전](physical-before.json), [적용 후](physical-after.json), [선택 계획](plan-summary.json)

각 ZIP에는 원문의 gzip/JSON과 Parquet 바이트가 그대로 들어 있다. source ID, 파일 해시,
수신 시각, 오류 기록, 세그먼트 ID와 원래 경로는 유지된다. 물리 위치만 별도 카탈로그 테이블로
관리한다. 이벤트 수집 이력 18개, 세그먼트 1,913개, 연구 스냅샷 20개의 카탈로그 내용은
전후 SHA-256이 정확히 일치했다. [전](live-catalog-before.json), [후](live-catalog-after.json)

묶음 생성·검증·등록은 약 1.53초, 개별 중복 사본 정리는 약 3.63초였다. 이는 명령 전체 시간이며
writer 잠금 유지 시간만을 측정한 값은 아니다. 데이터셋·UTC 날짜별로 묶었으며 기본 경계는
원본 합계 64 MiB 또는 1,024개 멤버다. 3,826개 대상에 필요한 묶음은 6개였다.
[묶음 기록](live-pack.json), [정리 전 계획](live-prune-plan.json), [정리 결과](live-prune.json)

## 검증 순서와 결과

먼저 이전 백업 `backups/stream-soak-2026-09-23`를 새 경로에 복원하고 그 복원본에서 시험했다.
묶음 생성·사본 정리 후에도 기존 카탈로그의 모든 논리 테이블이 이전 백업과 같았다.
그 상태를 새 format 2 백업으로 만들고 또 다른 경로에 복원해 다시 검사했다.

| 검사 | 결과 |
|---|---|
| 기존 네 depth 표본 재생 | 총 43,327행, 보고서 전체가 기존 결과와 일치 |
| 과거 실패 표본 | 당시의 `valid=false`와 오류가 그대로 재생됨 |
| 1시간 aggTrade 감사 | 12개 조회 구간, 총 90,009건의 결과가 기존과 일치 |
| 연구 스냅샷 | 20개 manifest와 카탈로그 참조 보존 |
| 시험 복원본의 등록 파일 무결성 | 14,440건 통과 |
| 시험 백업의 파일 수 | 같은 논리 자료에서 14,461개 → 10,641개 |
| 실제 저장소에 만든 묶음 | 시험 복원본의 ZIP 6개와 SHA-256이 전부 같음 |

[시험 적용 검사](pilot-check.json), [시험 백업](pilot-backup.json), [시험 복원](pilot-restore.json),
[복원 후 검사](roundtrip-check.json), [사용한 검사 스크립트](verification-script.txt)

실제 저장소 적용 후에는 원래의 1시간 수집 자료를 다시 감사했다. 새로 1시간 수집한 것은
아니다. 체결 90,009건의 연속성, depth 35,349행의 재생과 원문 가격·수량 쌍 5,846,784개가
모두 통과했다. 독립 호가 대조 117회의 기록도 그대로 유지됐다. 이 중 지연된 REST 1회는
기존과 동일하게 사후에 일치하며, 원래 `verification_complete=false`도 보존했다.
[재감사 결과](soak-after-summary.json), [원문 대조](soak-after-depth-source-parity.json)

실제 저장소의 등록 자료 무결성 14,692건과 ZIP 전체·멤버 검증도 통과했다.
수집별 보고서에는 묶음의 공유 할당량을 중복해서 합산하지 않고 `allocated_bytes=null`과
참조 ZIP ID를 남겼다. 논리적인 원문·Parquet 바이트는 이전과 같다.
[현재 저장소 무결성](live-integrity.json)

기존 운영 대상 9개는 적용 전후 모두 정상이며 REST OI 최신 라벨도 UTC 21:20에서
21:25로 진행했다. 기존 타이머와 Freqtrade 설정을 변경하지 않았다.
[적용 전 운영](operations-before.json), [적용 후 운영](operations-after.json)

## 백업과 자동 검사

실제 저장소의 새 백업은 `backups/packed-events-2026-09-23`에 만들었다.
10,893개 파일, 991,586,006바이트이며 카탈로그 고정 시 writer 잠금은 약 0.078초였다.
이 백업은 이후 도착한 OI 자료도 포함하므로 이전 시험 백업과 총 행 수·크기를 직접 비교하지 않는다.
ZIP과 멤버·카탈로그 참조까지 검증한 완료 백업이다. [새 백업](live-backup.json)

검증용 경로는 다음과 같다.

- 최초 시험 복원본: `restore-checks/packing-pilot-2026-09-23`
- format 2 시험 백업: `backups/packing-pilot-2026-09-23`
- 시험 백업을 다시 복원한 경로: `restore-checks/packing-roundtrip-2026-09-23`

백업과 복원본은 같은 파일시스템에 있다. 과거 format 1 백업은 수정하지 않고 실제 복원에
사용했다. format 2의 조회·복원에는 묶음 기능을 포함한 코드를 사용해야 한다.

전체 테스트 **185개**가 통과했다. 새 검사 17개는 원문·조회·재생·카탈로그 보존, 백업 왕복,
실행 중·최근 수집 제외, 손상 감지, 공간 부족·fsync 실패, 중단 후 재실행, 반복 게시,
백업·조회 중 정리 차단, 오래 열린 SQLite 조회의 물리 위치 해석을 포함한다.
Ruff 검사·포맷과 diff 공백 검사도 통과했다. [테스트](tests.xml), [소스·근거 해시](validation.json)

## 다음 운영 단계

무기한 보관 정책에는 기간 기준의 데이터 삭제가 없다. 공간 부족 시에도 자동 삭제하지 않는다.
명령 기본값은 계획 조회이며, 묶음 등록과 중복 사본 정리는 각각 `--apply`로 실행한다.
등록된 묶음 자체와 이를 읽는 카탈로그는 계속 보존한다.

이번 단계에서는 상시 스트림이나 유지보수 타이머를 활성화하지 않았다. 다음은 정기적으로
닫히는 수집 세션, 묶음·검증·백업 작업 예약, 용량·inode 경보를 함께 구성하는 작업이다.
외부 백업·저장소 증설도 무기한 보관의 후속 운영 과제로 남아 있다.
