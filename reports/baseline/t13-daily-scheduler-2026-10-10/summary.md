## 구현된 동작

| 대상 | 최초 실행 가능 시각(KST) | 미공개 재확인 |
|---|---|---|
| 현물 봉·확정 펀딩·현물/선물 metadata | 12:20 | 예상 아카이브 404는 20:00·22:00, 통신 오류는 별도 제한 재시도 |
| 선물 거래봉·마크봉·지수봉·archive OI | 18:00 | 미완료 대상만 20:00·22:00 |

예약 시각은 설정이며 공개 보장 시각이 아니다. 기존 `marketdata-daily.service` 한 개가 실행할 작업을 고른다. 후보 timer는 5분마다 실행기를 깨우지만 **due 작업이 없으면 HTTP 요청을 하지 않는다**. `RandomizedDelaySec=30s`가 있으므로 정확한 초 단위 실행을 약속하지 않는다. 이 timer는 아직 설치하지 않았다.

작업 ID는 dataset·market·symbol·interval·series·UTC 날짜와 목적/확인 주기로 고정된다. `acquire`와 최근 3일의 `refresh`를 분리한다. 미확보 날짜는 3일을 넘어도 유지하고, 최초 실행 가능 시점부터 3일 이상 지난 미공개는 점검 표시와 다음 날 같은 그룹 시각 재확인으로 전환한다. 놓친 여러 예약을 연속 재생하지 않는다.

새 날짜의 수정 확인이 생겨도 이전 미완료 수정 확인의 재시도 시각·한도를 우회하지 않는다. 같은 자료·날짜의 실제 검증 성공 하나로 그 시점에 확인할 수 있었던 중복 목적을 해소한다. 다음 날의 별도 수정 확인까지 미리 완료시키지는 않는다.

Metadata는 해당 실행에서 받은 실제 관측 시각을 저장한다. 놓친 과거 관측은 `missed_observation`으로 남기며, 오늘 응답으로 어제 정오 상태를 복원했다고 표시하지 않는다.

## 오류·중단·완료 계약

| 상황 | 후보 동작 |
|---|---|
| 구성된 예상 ZIP/CHECKSUM URL의 404 | `waiting_source`; REST의 404는 이 분류에 포함하지 않음 |
| 네트워크·일시적 서버 오류 | 기존 HTTP 계층 최대 4회 요청, 작업 차원의 최대 3회 시도·최소 300초 대기 후 점검 필요 |
| 429/418 | 즉시 재전송하지 않고 호스트별 냉각을 SQLite에 보존. Retry-After와 최소 900초를 함께 적용 |
| 검증 실패 | ZIP·CHECKSUM·관측 시각을 보존, 최대 2회 작업 시도 후 점검 필요 |
| 기존 revision과 내용 충돌 | 기존 처리대로 점검 필요. 정상 revision을 승인 없이 교체하지 않음 |
| 실행기 잠금 경합 | `deferred_lock`; 수집 HTTP 시도 없음 |
| 기존 엄격한 시각 시작 검사 거부 | 본 실행기 미기동. 기존 waiter·journal에서 사유 확인하고 기존 재시도/다음 timer로 재평가 |
| 저장 후 완료 상태 기록 전 중단 | 해당 원문·카탈로그·표준 파일의 해시/범위/내용을 확인해 재다운로드 없이 완료 복구 |
| 다운로드만 된 상태의 중단 | 완료 불인정. 중단 이력·재시도 횟수와 대기 시각을 보존 |

작업·시도 claim과 실패 상태/횟수 변경은 각각 같은 SQLite transaction으로 저장한다. 실제 SIGKILL과 상태 transaction 실패도 시험했다. `needs_review`는 자동 예산 초기화나 매일 무한 재다운로드로 풀지 않는다. 원인·저장 근거를 점검한 뒤 별도 처리 결정을 내릴 상태이며, 이번 후보에는 관리자 재시도 승인을 자동 생성하는 기능이 없다.

완료는 검증된 raw/query/revision 근거에 연결한다. 매 실행에서 완료 플래그만 신뢰하지 않고 카탈로그 참조와 현재 coverage를 대조한다. 매 5분마다 모든 파일을 다시 해시하는 설계는 아니다. 완료 확정·중단 복구 시 해당 파일을 검증하고, 보존 중 전체 무결성 검사는 기존 validate/backup 경로가 맡는다.

`runner_ok`와 `data_complete`는 다르다. 미공개/예정 전/제한 재시도 대기여도 실행기 자체는 정상 종료할 수 있다. 정오 네 대상의 완료만으로 전체 daily를 완료시키지 않는다. `review_required`, 상태별 건수, 개별 pending 이유·다음 시각·시도 이력을 함께 확인한다. 과거 놓친 metadata 등 이력은 현재 완료와 별도로 보존한다.

새 상태의 기준은 `marketdata.daily_schedule status`와 `state/daily-scheduler-latest.json`이다. **기존 `marketdata status` 호환도 연결했다.** 작업 상태가 바뀌면 기존 `sync_runs`에 사실에 맞는 새 집계 행을 추가한다. 과거 partial/failed 행은 수정하지 않으며, 처리 0건의 동일 상태 재확인으로 성공 시각을 계속 갱신하지 않는다. 기존 `state/daily-latest.json`은 과거 `update` 실행 보고서로 보존한다.

## 공개 시각 관측

별도 목적의 HEAD 관측기를 구현했다. 고정 UTC 대상 날짜 1–7일, 최대 선물 네 종류, ZIP/CHECKSUM 각각 5분 이상 간격, 기본 14:30–21:30 KST 범위다. 본문 다운로드·데이터 등록·완료 credit을 주지 않는다. 응답 상태·헤더·실제 관측 시각, 마지막 404와 최초 200을 각각 기록한다. 첫 관측부터 200이면 하한 미확인, 창 종료까지 200이 없으면 상한 미확인이다.

이는 관측자 경로의 404→200 구간이며 원본 서버의 정확한 최초 공개 시각이 아니다. 실행 중인 본수집·시각 gate·네트워크 지연에 따라 관측 간격이 벌어질 수 있다. 429 냉각은 본수집과 공유한다. **예제는 `enabled=false`이고 실제 외부 관측은 0회**다. 활성화할 날짜·시간 창을 적용 승인 때 고정해야 한다.

최종 고정 소스를 깨끗한 `/tmp/t13-daily-final-20261010`에 재구성했다. 기준 139개 파일과 새 7개 파일의 해시를 확인하고 패치 적용, `uv sync --frozen --no-editable`, `python -I`의 실제 설치 import를 확인했다.

**178개 통과 = 신규 47개 + 기존 관련 회귀 131개**, 실패/skip 0개. 개발 중 반복 실행은 이 숫자에 더하지 않았다. Ruff 통과. 후보 유닛의 읽기 전용 `systemd-analyze --user verify`도 통과했다. 처음 샌드박스 내 검사에서 나온 소켓 접근 경고와 샌드박스 밖의 정상 검사 결과를 모두 보존했다.

실제 Collector·SQLite·원문/Parquet·checksum·기존 checkpoint 생성/검증/복원을 사용했으며 HTTP는 대역 응답이다. 미완료 작업만 있는 백업과 자료가 저장된 백업을 각각 복원했다. 이전 Collector가 새 원장을 가진 저장소에 자료를 추가해도 원장을 삭제하지 않고 완료 근거를 대조할 수 있다.

기존 수집/pack/backup/restic 코드 139개 파일은 기준과 동일하다. 이번에는 운영 daily 실행, 외부 공개 시각 조사, 운영 checkpoint/restic 추가 실행, 실제 서비스 배포/재시작을 하지 않았다. 따라서 이 후보 자료의 **실제 운영 백업 편입까지 완료한 것은 아니다**. 실제 설치 경로·소유권·실효 유닛과 첫 정오/저녁 이월·후속 백업 편입은 운영 적용 이후 확인할 항목이다.
