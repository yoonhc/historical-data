# 호가 초기 동기화 개선 — 2026-09-25

첫 WebSocket 증분이 도착하기 전에 REST 스냅샷을 요청하던 경로를 수정했다.
실제 첫 증분을 받아 원문으로 보존한 뒤 즉시 스냅샷을 요청하고, 받은 증분을 원래 수신
시각으로 journal에 적용한다. 첫 메시지 대기는 최대 2초이며 고정 2초 지연을 넣지 않는다.
ID 연결 조건·호가 재생기·기존 실패 기록·15분 연결 교체·1시간 세션 설정은 유지했다.

## 진단

UTC 2026-09-23 23:00 이후 저장된 수집의 실패 epoch에서 스냅샷 연결 실패 24건,
가격 범위 소진 3건을 확인했다. 완료·진행 중 세션을 포함하는 조회이며 고정 24시간 실패율은 아니다.
최근 실패 표본 8건의 anchor와 첫 update를 직접 읽었다. 7건은 거래소 T 시각 차이가
103~120ms, 1건은 1,546ms였다. 이는 두 이벤트의 거래소 시각 차이이며 네트워크 지연 측정은 아니다.
각 표본에서 첫 증분 U가 snapshot lastUpdateId보다 컸다.

기존 구현은 소켓의 내부 큐를 열었지만 실제 첫 메시지의 도착을 기다리지 않고 REST를 호출했다.
동기화 조건을 완화하지 않고 요청 순서를 바꾸었다. [Binance 공식 규칙](https://developers.binance.com/en/docs/products/derivatives-trading-usds-futures/websocket-market-streams/How-to-manage-a-local-order-book-correctly)
및 [진단 근거](diagnosis.json)를 참고한다.

## 최종 구현 검증

- 전체 테스트 **232개 통과**. 기존 호가 테스트 33개와 초기 수신 관련 7개 사례도 통과했다.
- Ruff 검사·형식 검사·diff 검사 통과.
- REST 요청 전 실제 메시지 수신, 수신 시각 보존, 429·Ctrl-C 때 초기 원문 보존,
  무응답 시간 제한, 한 메시지만 꺼내고 후속 메시지를 큐에 유지하는 동작을 검사했다.
- 실행 시간 제한이 초기 수신 중 끝나도 이미 받은 메시지는 journal에 남긴다.
- 초기 원문은 `depth_bootstrap`으로 등록된다. REST가 실패하면 이 원문은 남지만
  snapshot이나 완전한 journal을 확보했다고 판정하지 않는다.

운영 수집을 유지한 상태에서 별도 저장소에 최종 버전을 180초간 실행했다.
UTC **02:11:14~02:14:16**에 15초마다 연결을 교체하고 10초마다 독립 스냅샷을 대조했다.

| 항목 | 결과 |
|---|---:|
| 연결 / epoch | 11 / 11 |
| 수신·저장된 증분 | 1,549 / 1,549 |
| 스냅샷 포함 journal 행 | 1,570 |
| 연결 오류 / 동기화 실패 / 범위 소진 | 모두 0 |
| 스냅샷 지연 / 미복원 증분 | 모두 0 |
| 독립 스냅샷 대조 | 10회 일치, 비교 불가·불일치 0 |
| 초기 수신 원문 | 11건 모두 journal과 메시지·수신 시각 일치 |
| 파일 무결성 | 117개 항목 통과 |

모든 epoch에서 첫 증분을 받은 뒤 REST를 요청했으며 그 간격은 약 **5~28ms**였다.
저장된 행의 원문 ID·시각·가격·수량을 대조했고 재생 결과는 당시 상태와 일치했다.
`valid=true`, `replay_matches_live=true`지만 연결 전환이 있으므로 **`continuous=false`**다.
이 표본으로 하루 전체의 실패율 감소나 무손실 수집을 확정하지 않는다.

최종 표본 ID는 `20f59ce98e9542d08442038cc0165904`이고 실제 자료는 프로젝트의
`reports/depth-bootstrap-2026-09-25/first-event-pilot/`에 남긴다. 이 별도 표본의 수집은 종료했다.
사전 6분 시험에서는 고정 2초 버퍼를 사용해 연결 12회·3,309증분·3,343행 재생과
스냅샷 대조 22회가 통과했다. 초기 호가 복원을 불필요하게 늦추지 않도록 최종안은
첫 메시지 수신 즉시 요청하는 방식으로 바꾸고 위 시험을 별도로 수행했다.

## 적용 범위와 후속 관찰

이번 변경은 새 연결의 초기 스냅샷 요청 순서를 개선한다. 거래소 스냅샷이 계속 뒤처지거나
첫 메시지보다 오래되면 여전히 실패로 표시하고 기존 원문 보존·10초 재시도를 수행한다.
가격 범위 소진과 연결·프로세스 교체 경계의 공백도 남는다. 과거 partial 기록을 고치거나
미수집 구간을 정상으로 바꾸지 않았다. 운영 적용 후 다음 24시간의 연결 수·실패 원인·
미복원 증분을 같은 기준으로 다시 비교하는 것이 다음 단계다.

한국 시각 **11:16:46**에 운영 호가 서비스를 SIGINT로 정상 종료 후 재시작했다.
이전 수집은 수신·저장 25,702건을 보존하고 `interrupted`로 마감했으며 기존 동기화 실패
1건도 남겼다. 이전 마지막 수신과 새 첫 수신의 시각 차이는 약 **2.55초**로 기록했고,
그 경계의 호가를 복구했다고 표시하지 않았다. 새 수집에서 초기 정책 적용·동기화와
`healthy=true`를 확인했으며 aggTrade와 유지보수도 정상이다. [적용 근거](deployment.json)
