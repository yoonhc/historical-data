# 첫 작업용 checkpoint 수동 정리와 사후 확인

2026-10-05 KST 기록. 사용자가 승인한 **9/27~10/1 작업용 사본 5개를 수동 정리**했다.
10/2~10/4 최신 사본 3개와 편입 전 사본 3개는 남았으며, 운영 restic **8개 snapshot의
전체 ID·메타데이터는 그대로**다. 원본 시장 자료·revision·시험 산출물·복구 키트는 정리 대상에
넣지 않았다. 기존 수집·daily·restic 예약을 유지하고 자동 checkpoint 정리·restic `forget`·
`prune`은 적용하지 않았다.

## 잠금·수집과 남은 사본 확인

적용 직전 [reader 표본](20261004T180904Z-be841c1fd08b493f8afb2e0d5dc2a0be/reader-check.json)에서
조회 가능한 같은 사용자 프로세스의 checkpoint 파일·작업 디렉터리 참조와 부모 잠금은 없었다.
접근 제한 PID 1189·1201은 systemd·`(sd-pam)`으로 대조했다. 모든 사용자·향후 외부 읽기나
다른 Python 프로세스의 import 메모리까지 증명하는 검사는 아니다.

03:15 정기 파일 정리는 maintenance 잠금을 **440.84초 기다린 뒤**, checkpoint 정리가 잠금을
해제한 03:22:21에 시작해 03:23:26 정상 완료했다. 기존 대기 기능이 동작했으며 수집 서비스나
대기 작업을 재시작하지 않았다. [해당 정기 실행 결과](pack-after-retirement.json)를 보존했다.

적용 중 20초 간격의 [39개 표본](20261004T180904Z-be841c1fd08b493f8afb2e0d5dc2a0be/monitor.jsonl)에서

수신으로부터의 최대 경과시간은 5.24초·6.67초였다. 표본 관측이며 새 24시간 품질 감사는 아니다.

## 정리 이후 archiver와 예약 결과

[수동 archiver 실행](manual-archiver-after-retirement.json)은 정상 종료·처리 0개였고,
[실제 저장소 메타데이터](live-snapshots-after.json)는 적용 전 8개와 전체 비교에서 일치했다.
[상태 조회](post-status.json)는 `healthy=true`, 미보관·미해결 오류·검사 미포함 지점 0이다.
로컬 상태 조회 자체는 저장소를 직접 읽지 않으므로 실제 저장소 확인은 별도 snapshots 명령
근거와 구분한다. [사후 대조 결과](post-check-results.json)에 이 구분과 근거 해시를 남겼다.

03:35부터 08:35까지 **실제 예약 11회가 모두 성공·처리 0개**였다.
[대조 스크립트](verify_scheduled.py)는 [예약 receipt 사본](scheduled-receipts/)의 현재 start Job
타이머 근거와 [journal](post-service-journal.jsonl)의 PID·invocation·완료 메시지, archive 원본
결과를 연결했다. [집계 결과](post-scheduled-results.json)에 실행별 ID·시각·근거 해시를 보존했다.
수동 실행과 이 11회 탐색은 새 사본의 예약 저장·검사 성공으로 세지 않는다.
기존 서로 다른 날짜 관찰 **3/3(9/29·9/30·10/1)**과 복구 검증은 별도 과거 증거로 유지한다.

08:54 무렵 [서비스 조회](systemd-after.txt)에서 수집 둘은 running, 기존 타이머 셋은 enabled·waiting,
마지막 daily·restic·파일 정리는 success였다. 그 표본의 다음 예약은 restic 09:05,
파일 정리 09:15, daily 13:10이다. 예약 시각을 실행 성공으로 기록하지 않는다.

## 아직 확인하지 않은 항목

**10/5 정리 후 첫 새 daily 사본 생성 → 사본 검증 → 같은 backup ID의 예약 restic 저장·전체
읽기 검사**는 아직 발생 전이다. 오늘 **14:15 KST 이후**에 실제 완료 기록·ID 연결·미해결 오류·
중복 여부를 확인한다. 실행 중이면 완료를 기다린 뒤 판단한다.

자동 checkpoint 정리, restic 보관 지점 만료·`prune`, 시험 산출물 정리, PC 외부 복구 키와
데이터 사본, 실제 Proxmox VM 복구·재개는 별도 후속이다. 이번 승인으로 이 항목까지 적용하지 않는다.
다음 삭제는 기존 완료 계획을 확대하지 않고 당시 조건으로 만든 새 목록·계획을 검토한다.

운영 코드는 수정하지 않았다. 기존 434개·후속 14개 테스트를 반복 실행한 결과로 보고하지 않으며,
이번 근거는 실제 적용·사후 검증과 report 스크립트 검사다. 기록 추가 후 새 commit은 아직 하지 않았다.
