# restic 병행 보관 구현·수동 검증 — 2026-09-27

기존 daily가 만든 완료 사본을 새 restic 저장소에 추가 보관하는 도구를 구현했다.
기존 백업 대체·보관 기간 확정·중복 사본 정리는 이번 결과에 포함하지 않는다.
**별도 타이머는 설치하거나 활성화하지 않았다.**

## 정책과 식별 기준

1·2단계에서는 어떤 사본도 삭제하지 않는다. 원본·revision 보존 정책과 날짜별 백업 복구 지점의
보관 정책은 분리하며, 최종 보관 기간과 작업용·중복 사본 정리는 3단계에서 결정한다.

snapshot time은 검증된 manifest의 `checkpoint_finished_at`을 UTC로 환산한 값이다.
실제 보관 시작·완료 시각을 별도로 기록한다. `archive_scope`는 안정된 선택 범위이며
backup/attempt 태그는 개별 식별자다. 상대 경로 `.`로 저장해도 절대 paths가 남는 것을 실제로
확인했다. parent와 보관 그룹은 별개이며, 현 도구에 forget/prune 실행 경로는 없다.

## 검증 범위

최종 코드로 관련 테스트 **70개 통과, 실패·건너뜀 0개**. 기존 백업·증분 백업·restic 시험 검사와
새 병행 보관 검사 29개를 포함한다. 전체 프로젝트 테스트를 다시 실행한 것으로 표현하지 않는다.

새 도구의 주요 검증은 다음과 같다.

- 과거 서로 다른 두 날짜의 사본을 하루에 보관해도 각각의 UTC snapshot time과 소수초 유지.
  서로 다른 절대 paths·개별 태그와 동일 archive_scope를 실제 metadata에서 확인.
- 마운트·UUID·저장소 ID·암호·권한·여유 공간 오류, 잘못된 source root·manifest·입력 파일 거부.
- 기존 성공의 중복 실행 방지, 최대 처리 개수와 미완료 폴더 구분, 전용 잠금 경합.
- 정상 snapshot 생성 직후 성공 기록이 유실되면 실제 추출·전체 검증 후 같은 ID 채택.
- 실제 읽기 권한 오류로 restic 종료 코드 3과 불완전한 snapshot을 생성해 실패로 보존하고 재시도.
  유효한 manifest만 있는 미확인 불완전 사본은 채택하지 않음.
- 저장소 check 실패 시 저장 사실은 보존하고 추가 저장 차단. verify 성공 뒤 재개.
- 상태 분실·검증된 중복 후보·기존 성공 snapshot 유실을 구분.
- 원래 완료 사본 폴더와 상태 기록 없이 명시적 ID로 추출·프로그램 복원·조회·전체 검증·
  새 전용 독립 백업 생성·검증. 옛 manifest/source root와 재백업 출처 검사를 유지.
- 마운트가 없을 때 상태 조회는 오류와 알 수 없는 대기 개수(null)를 표시하고 상태 파일을 만들지 않음.

원래 완료 사본 4개의 manifest SHA-256과 기존 사용자 systemd 유닛 14개의 해시가 실행 전후 같았다.
시장 데이터 패키지와 기존 systemd 소스 파일에도 변경이 없다.

수동 실행 구간의 10초 간격 표본은 총 13개다. aggTrade·depth 모두 같은 세션에서 running으로
관측됐고 연결·flush 오류는 없었다. 수신 시각 경과의 최대 표본값은 aggTrade 약 4.74초,
depth 약 2.43초였으며 depth는 전 표본 synchronized=true·sync_losses=0이었다.
이는 짧은 실행 구간의 표본 관측이다. 미보고 값은 null로 보존하며 24시간 연속성이나 장기 안정성을
입증한 결과로 확대하지 않는다.
